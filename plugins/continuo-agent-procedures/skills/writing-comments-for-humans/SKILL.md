description: continuo が起動した run で、人間が読むコメント（計画・確認・判断票・報告・途中経過）を書く前と、pull request を作る・題名と本文を書く前に呼ぶ。ほかのスキルがこの名前を指したときにも読む。
---

- **印の行より前には、1文字も置きません。**印はそのコメントの節の見本のものをそのまま使います。
- 1つの run で書くコメントは、原則として「finishing-run」の「runの終了を宣言する」の報告の1件です。
- どのコメントにも、pull request の本文にも、手元の絶対パス・資格情報・社内だけで引けるホスト名を書きません。
- 計画・判断票・報告は、8つの見出しで書きます。本文はファイルへ書いて `--body-file` で渡します。

## 人間へ質問・報告するコメントの書き方

### 1つの run で書くコメントは1件

その1件は、「finishing-run」の「runの終了を宣言する」の何をしたかの報告です。書きたいことが出たら、その報告の中に書きます。何件も並ぶと人間が読みづらくなります。
別のコメントにしてよいのは、次の表のものだけです。

| コメント | 別にする理由 |
| --- | --- |
| 計画（「writing-plan」。印は `<!-- continuo:plan -->`） | 設計レビューの前に issue に在る必要があります。continuo は計画の印のコメントを成果から外し、あなたは2回目の試行でこの印を目印に計画を探します |
| 何をしたかの報告（「finishing-run」の「runの終了を宣言する」） | これが、その run の1件です。計画のあとの人間確認もこれで訊きます。continuo は run の開始より後に作られたコメントだけを成果と数えるので、毎回新しく1件書きます |
| 途中経過（「reporting-progress」の「<進捗の間隔（分）>分以上黙らない」） | いちばん下の1件が自分の途中経過なら書き足し、途中で別のコメントが書かれたら新しく1件にします |
| 判断票（「posting-review-verdict」） | run をまたいで1件に書き足すので、issue と pull request に1件ずつ持ちます。新しく1件にする場合は「posting-review-verdict」の「判断票の貼り方」にあります |
| まとめて直したときの、ほかの issue への説明（「finishing-run」の「まとめて直したとき」） | 書く先が別の issue です |

### 公開の場へ書かないもの

**どのコメントにも、pull request の本文（「implementing-and-pushing」の「段2. draft で作る」と「finishing-pull-request」の「段3. 実装が終わったら、題名と本文を書き直す」）にも、次の3つを書かないでください。**

    手元の絶対パス          ファイルはリポジトリの根からの相対パスで書きます（`src/app.ts` のように）。
                            範囲や叩いた場所を書くときだけ、`~/` から書きます（「running-review-loop」の「レビューの回し方」）
    資格情報                API キー・アクセストークン
    社内だけで引けるホスト名

- **コマンドの出力をそのまま貼るときは、混ざっていないかを見ます。**コメントは編集履歴が残るので、書いたら取り消せません。
- **資格情報を書いてしまったときは、消す前にそれを無効化してください。**消せたかどうかに関わらず。

### 8つの見出しで書く

人間とのやりとりは1往復ごとにコメント1件と continuo の巡回の待ちがかかるので、聞き直されないよう最初のコメントに全部揃えます。

当てるのは、人間に読ませる次の3つです。

    計画               「writing-plan」（issue へ）
    判断票             「posting-review-verdict」（計画のレビューは issue へ、実装のレビューは pull request へ）。周ごとの <details> の中に書きます
    何をしたかの報告   「finishing-run」の「runの終了を宣言する」（issue へ）。blocked で終えるときの理由も、「対応しない」と決めた理由も、削除の要約も、ここに書きます

次の2つには当てません。形が別に決まっています。

    途中経過の報告             「reporting-progress」の「<進捗の間隔（分）>分以上黙らない」。1行足すだけの決まりです
    まとめて直したときの報告   「finishing-run」の「まとめて直したとき」。先頭の1文と足す行の形が決まっています

書き方:

1. 返信したい内容ごとに `## ` の節を立てます。題名は一言で中身が想像できるものにします。
2. 節の中に、次の8つをこの順で書きます。2つ目から8つ目は `###` の見出しで置きます。
3. 引用はコメントの先頭へまとめず、その節が答えている原文だけを、その節の中で引きます。

| 順 | 見出し | 中身 |
| --- | --- | --- |
| 1 | （見出しは付けません） | 引用。その節が答えている原文だけを、行頭の `> ` で引きます。1文だけ引かないでください |
| 2 | `### 何が言いたいのか` | その節で伝えたいことを1行で |
| 3 | `### 三行まとめ` | 3行以内で結論 |
| 4 | `### 前提` | その話が成り立つために要る条件 |
| 5 | `### 単語の説明` | その節で使う語が何を指すか。issue と pull request の番号には題名を添えます |
| 6 | `### 既存の構造がどうなっているか` | いまどう作られていて、何がどの順で起きるか |
| 7 | `### 何が問題なのか` | 症状と、放っておくと何が起きるか |
| 8 | `### 詳細` | 根拠・仕組み・データ |

- 判断票では、指摘をまとめた表を1つ `### 詳細` の中に置き、使い捨てのプランファイルから写した要点（「running-review-loop」の「レビューの回し方」の「直す前に書くこと」）を表の下に、指摘ごとの小見出しで置きます。
- 説明には図を多用します。`flowchart` か `sequenceDiagram` で、仕組みや順序は `sequenceDiagram` にします。
- 渡すもの・受け取るものは、型名や変数名ではなく、実際に流れる値で書きます（`--permission-mode auto` や `author_association: "NONE"` のように）。具体を詰めると設計の穴が出ます。
- 技術用語は英語のまま書きます。`worktree` / `pane` / `hook` / `branch` / `commit` を訳しません。

### 人間に決めてほしいことを訊く

- 質問1つにつき1つの節を立て、8つで説明してから訊きます。表で訊きません。
- 選べる案は段落を分けて並べ、案ごとに、選ぶと何が起きるかと選ばないと何が続くかを書きます。最後に推奨とその理由を書きます。
- 人間に操作を頼む案には、そのまま貼れるコマンドを添えます。

### 印を先頭に置き、ファイルで渡す

**印の行より前には、1文字も置かないでください。**8つは印の行の下に書きます。引用を冒頭へ置くと印が先頭から外れ、continuo はそのコメントを数えず（「writing-plan」と「finishing-run」の「runの終了を宣言する」）、CI の検査も数えません（「posting-review-verdict」）。

骨組み。印の行は、そのコメントの節の見本のものをそのまま使ってください。下の見本の印は、計画のコメントのものです。

```markdown
<!-- continuo:agent -->
<!-- continuo:plan -->
# 計画

## <一言で中身が想像できる節の題名>

> （その節が答えている原文だけを引く）

### 何が言いたいのか

### 三行まとめ

### 前提

### 単語の説明

### 既存の構造がどうなっているか

### 何が問題なのか

### 詳細
```

**`--body "…"` で渡さないでください。**引用には backtick とドルの記号が混ざります。ファイルへ書いて `--body-file` で渡します（「writing-plan」の「段1. 計画を書く」と同じです）。

「このプロジェクトの決まり」と、そこが読ませている文書がコメントの形を決めているなら、それにも従ってください。
