# プランファイルの書き方

## 絶対条件：節ごとに「言いたいこと」を先に置く

**節の冒頭に、その節で言いたいことを3行以内で書く。そのあとに結論、最後に詳細を書く。**

```markdown
### 3-16. 着手の手順の順番を固定する

**言いたいこと。**この順番でないと、途中で落ちたとき同じ worktree に Claude Code が2つ立つ。
印を先に付け、Status を次に書く。実体を作るのはそのあとである。

**採る順番。**
（表や箇条書き）

**なぜこの順番か。**
（根拠）
```

**「言いたいこと」を読むだけで、その節が何を決めたのかが分かる状態にする。**
読み手が詳細まで読むかどうかを、そこで判断できるようにする。

## 置くもの — 3つだけ

| 何を | 内容 |
| --- | --- |
| **最新の仕様** | いまどう作るか。**過去にどう書いていたかは書かない** |
| **その選定根拠** | なぜそう決めたか。実測値・仕様の引用・制約 |
| **比較した案の概要と、その否定根拠** | 検討した他の案が何で、なぜ採らなかったか |

## 書いてはいけないもの

| 書いてはいけない | 代わりにどうするか |
| --- | --- |
| **修正の履歴**（「2026-08-18 に◯◯した」「以前は A だったが B に変えた」「撤回する」） | **古い記述を消して新しい記述に置き換える。**差分を残さない |
| **調査の経緯**（何をどの順に調べたか） | 結論と根拠だけ書く |
| **同じ説明の繰り返し** | 1箇所を正とし、残りは参照にする |
| **前置きの長い説明** | **結論を先に書く。**理由はそのあと |

**例外。**実測した日付は残してよい（その値がいつ時点のものかを示すため）。**ただし「以前は違った」を添えない。**

## 絶対条件：何かを書くと書いたら、パスと中身のサンプルを必ず添える

**「ファイルに書く」「記録する」「保存する」と書いたら、次の3つを必ずセットで示す。**

| 何を | 例 |
| --- | --- |
| **具体的なファイルパス** | `<worktree>/.continuo.json`（`workspace.identity_file` で変えられる） |
| **中身のサンプル**（実際に書ける形） | ```json … ``` の実物 |
| **誰がいつ書くか** | 「continuo が着手の段6で書き、段7で追記する」 |

**これが無いと、読み手は内容を判断できない。**「身元ファイルを置く」だけでは、何が書いてあるのか・
どこにあるのか・自分で開けるのかが分からない。**要約版にもサンプルを載せる。**サンプルが無いと人間がレビューできない。

**同じことが設定・状態・識別子にも当てはまる。**

| 書くと言ったもの | 添えるもの |
| --- | --- |
| 設定ファイル | パスと、実際の YAML / JSON |
| メモリ上の状態 | **Go の型の定義**（`map[string]…` など）と、何が入るかの例 |
| 外部サービスに書く値 | どのフィールドに、どんな文字列が入るかの例 |
| コマンドで作るもの | **実行するコマンドそのもの** |

## 詳細版と要約版の2本立てにする

**長い設計文書は分ける。**

| ファイル | 誰が使うか | 誰が更新するか |
| --- | --- | --- |
| **詳細版**（`*_design.md`） | **AI が読む。**判断の根拠・実測値・比較した案が全部ある | **AI が更新し続ける。これが正である** |
| **要約版**（`*_design_slim.md`） | **人間がレビューする** | **人間のレビューが要るたびに、詳細版から再生成する** |

1. 設計を変えたら**詳細版を直す。**要約版はその時点では触らない
2. **人間のレビューを求めるとき、要約版を再生成する**（手で差分を当てない。作り直す）
3. **要約版で分からないことは詳細版にある前提で読んでもらう。**要約版に全部を書こうとしない
4. **食い違ったら詳細版が正。**要約版の冒頭にそう明記する

## 長さ

**長い文書は読まれない。読まれない文書は無いのと同じである。**

- **1つの節は、画面1〜2枚で読み切れる長さにする**（目安50行以内）
- **表は列を4つまでにする。**それを超えるなら表を分ける
- **同じことを2箇所に書かない**
- **文書全体が長くなったら、要約版を別ファイルに作る。**元は残す

## 参照

- ファイルパスは markdown link 形式で書く（`[path:12-34](path#L12-L34)`）。backtick で囲まない
- 節を指すときは番号で（`3-16`）。**存在しない節を指していないか、書き終えたら機械的に確かめる**
- **文書を指すときは呼び名ではなくファイルパスで示す。**「設計文書」では、自分たちの決定か外部の仕様かが区別できない

## 絶対条件：設計文書へ1行でも足したら、そこを指すリンクを全部検算する

**行を足すと、その後ろを指すリンクが全部ずれる。**

**2026-09-04 に実測した。**PR #215（ボードの操作を AI が行う形へ規則と設計を直す（並び順の段は、そもそも書かれていなかった））で、
`docs/plans/continuo_design.md` へ3行足したところ、**13本のリンクが同時にずれた。**
**うち3本は「主張の逆」を書いた行に着地した。**しかもその commit は「行番号のずれを揃え」と名乗っていた。
**8周のレビューのうち3周が、同じ原因である。**

**書き終えたら、次を叩く。**

```sh
D=docs/plans/continuo_design.md
git grep -oh 'continuo_design\.md#L[0-9]*' -- '.claude/' 'CLAUDE.md' 'docs/plans/' \
  | sed 's/.*#L//' | sort -un | while read L; do
  T=$(sed -n "${L}p" "$D")
  case "$T" in
    "")          echo "空行     L$L" ;;
    "| --- |"*)  echo "区切り行 L$L" ;;
    *)           printf 'ok       L%s  %.48s\n' "$L" "$T" ;;
  esac
done
```

**`git grep` はリポジトリの追跡ファイルしか見ない。**
**pull request の本文にも同じリンクを書いているので、そちらは別に検査する。**

```sh
gh pr view <番号> --json body --jq .body \
  | grep -o 'continuo_design\.md#L[0-9]*' | sed 's/.*#L//' | sort -un | while read L; do
  printf 'L%s  %.48s\n' "$L" "$(sed -n "${L}p" docs/plans/continuo_design.md)"
done
```

**本文に書いた数値も、commit のたびに測り直す。**`git diff --shortstat origin/main...HEAD` の値、
触ったファイルの本数、節の行数は、**1 commit 足すだけでずれる。**

**2026-09-04 に、この2つ目を飛ばして High を1件、数値の測り直しを飛ばして Medium を1件出した。**
実ファイルの48本は全部合っていたのに、**本文の2本だけが残った。**

**`空行` と `区切り行` が出たら、そのリンクはずれている。**
**`ok` でも中身が意図と違うことがある。**行の頭48文字が出るので、目で確かめる。

**範囲リンク（`#L12-L34`）の開始行が表のヘッダや空行になるのは、正しいことがある。**
表の全体を指すときは、ヘッダ行から始めてよい。
