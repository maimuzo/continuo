# 設計のレビュー

## 絶対条件：設計が固まったら、実装の前にレビューを通す

**issue の作業は、この順番で進める。段を飛ばさない。**

| 段 | 何をするか |
| --- | --- |
| **1** | **設計を固める** |
| **2** | **決めた設計を issue のコメントに書く**（実装の前に） |
| **3** | **設計をサブエージェントにレビューさせる** |
| **4** | **指摘を直す。直したことも issue に書く** |
| **5** | **実装する** |
| **6** | **draft の PR を作る** |
| **7** | **`/code-review` を実施し、結果を PR のコメントに貼る** |
| **8** | **指摘に対応する** |
| **9** | **`gh pr ready` で draft を外す** |

**設計のレビューを飛ばして実装に入らない。**
**実装してからの手戻りは、設計を直すより高くつく。**

**実例。**PR #112（1台で continuo を複数動かす）は設計をレビューせずに実装へ入った。
**コードのレビューを3回回して、毎回15件前後。**
**あとから設計を architect に見せたら90件出た。**うち2件は、その直前に足した節への Critical だった。

---

## 誰にレビューさせるか

**`maimuzo-from-ecc:architect`。**

**設計をファイルに落として渡すこと。**`gh issue view` で読ませない。

**理由。**architect の道具は `Read` / `Grep` / `Glob` だけで、**Bash が無い。**
2026-08-31、issue のコメントを読ませようとして1文字も読めず、
**既に確定していた2点を「未確認」として指摘された。**

```
設計を scratchpad のファイルへ書き、そのパスを指示に入れる。
「このファイルを Read で読んでください」と書く。
```

**Bash が要るレビューは、`code-reviewer` か `code-architect` へ回す。**そちらは持っている。

---

## レビューに渡す4つの観点

- **実装すると壊れる記述**
- **実装しても目的を達しない記述**（守りが1箇所だけ抜けている、など）
- **名乗っていることと、実際にやることが違う記述**
- **2つの節が矛盾している記述**

**主張1つにつき、ファイル名と行番号、原文の引用を必ず添えさせる。**
**「無い」ことの主張には、検索パターンと対象パスを添えさせる。**
**読むだけ。ファイルの変更・削除・作成を禁じる。**

## 回す回数

**最大3回。**[.claude/rules/reporting.md](reporting.md) の「レビューループ」と同じ扱いである。

| 回 | どうするか |
| --- | --- |
| 1回目のあと | **直して2回目を回す。**訊かない |
| 2回目のあと | **直して3回目を回す。**訊かない |
| **3回目のあと** | **収まっていれば進む。収まっていなければ人間に確認する** |

**2回で止めてよいかを訊かない。**規則が上限を決めているのだから、そこまでは訊かずに回す。

---

## 飛ばしてよい場合

| 何 | 例 |
| --- | --- |
| **文書だけの変更** | README の言い回し、規則の文書 |
| **1行の修正で、他に影響しないことが明らか** | 定数の値、typo |

**迷ったら飛ばさない。**

## 設計そのものを疑う

**「そもそも対応するか」を、設計を書く前に確かめる。**

**実例。**issue #65（サブエージェントの実行中に人間へ引き渡される）で、
**設計を v4 まで書き、3回のレビューで41件を潰したあと、
人間が「非対応でよい」と判断した。**変えるファイルは19個から2個になった。

**確かめる順番。**

| 順 | 何を問うか |
| --- | --- |
| **1** | **そもそも対応するか。**非対応と明記して文書に書くだけで済まないか |
| **2** | **利用者が自分で回避できるか。**できるなら、その手順を文書に書くだけで足りないか |
| **3** | **continuo が持つべき仕組みか。**持つと何ファイル触るか |

**3で「19ファイル」と出たら、1へ戻る。**
