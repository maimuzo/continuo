# 設計のレビュー

## 絶対条件：設計が固まったら、実装の前にレビューを通す

**issue の作業は、この順番で進める。段を飛ばさない。**

| 段 | 何をするか |
| --- | --- |
| **1** | **設計を固める** |
| **2** | **決めた設計を issue のコメントに書く**（実装の前に） |
| **3** | **設計をサブエージェントにレビューさせる** |
| **4** | **指摘を直す。直したことも issue に書く** |
| **5** | **実装する** |
| **6** | **draft の PR を作る** |
| **7** | **`/code-review` を実施し、結果を PR のコメントに貼る** |
| **8** | **指摘に対応する** |
| **9** | **`gh pr ready` で draft を外す** |

**設計のレビューを飛ばして実装に入らない。**
**実装してからの手戻りは、設計を直すより高くつく。**

**段6〜9 は [CLAUDE.md](../../CLAUDE.md) の「PR を出すときの絶対条件」の手順そのものである。**
**正はあちらで、ここは段1〜5 とのつながりを示すために並べているだけである。**

**実例。**設計をレビューせずに実装へ入った PR で、コードのレビューを3回回して毎回15件前後が出た。
**あとから設計を architect に見せたら90件出た。**うち2件は、その直前に足した節への Critical だった。

---

## 設計を書く前に、設計そのものを疑う

**確かめる順番。**

| 順 | 何を問うか |
| --- | --- |
| **1** | **そもそも対応するか。**非対応と明記して文書に書くだけで済まないか |
| **2** | **利用者が自分で回避できるか。**できるなら、その手順を文書に書くだけで足りないか |
| **3** | **そのソフトウェアが持つべき仕組みか。**持つと何ファイル触るか |

**3で「19ファイル」と出たら、1へ戻る。**

**実例。**設計を4版まで書き、3回のレビューで41件を潰したあと、
人間が「非対応でよい」と判断した。**変えるファイルは19個から2個になった。**

## 設計文書に既に決定が無いかを、先に探す

**設計を書く前に、対象のファイル名・関数名・エラーの文面で設計文書を grep する。**

**実例。**設計文書が「番兵エラーを新設する」と決めているのに、
「文面そのものは直さない」と逆のことを書いた。**探さずに書いた。**

## 誰にレビューさせるか

**`maimuzo-from-ecc:architect` に渡す。**

### 設計はファイルに落として渡す

**`gh issue view` のようなコマンドで読ませない。**

**理由。**設計を見る役のエージェントは、道具が `Read` / `Grep` / `Glob` だけで
**Bash を持たないことがある。**
実際に、issue のコメントを読ませようとして1文字も読めず、
**既に確定していた事実を「未確認」として指摘されたことがある。**

```
設計を一時ファイルへ書き、そのパスを指示に入れる。
「このファイルを Read で読んでください」と書く。
```

### 渡す4つの観点

- **実装すると壊れる記述**
- **実装しても目的を達しない記述**（守りが1箇所だけ抜けている、など）
- **名乗っていることと、実際にやることが違う記述**
- **2つの節が矛盾している記述**

**主張1つにつき、ファイル名と行番号、原文の引用を必ず添えさせる。**
**「無い」ことの主張には、検索パターンと対象パスを添えさせる。**
**読むだけ。ファイルの変更・削除・作成を禁じる。**

## 回す回数

**3回ごとに issue と実装を突き合わせ直す。連続10回で完全に止まる。**

**「収まっている」の定義、何周回すか、3・6・9回目に通す6段は、どれも
[CLAUDE.md](../../CLAUDE.md) の「回数を数える」にある。ここには写さない。写すと食い違う。**

**要点だけ。**issue と実装を比べ、issue に無いものの合理的理由を敵対的レビュワーへ説明し、
**説得できなかったものは、削除する内容を対になる issue のコメントへまとめてから消す**（対になる issue が無ければ、その pull request のコメントへ）。
**人間へは経緯を報告し、返答は待たない。**そのうえで実装を止め、設計内容を敵対的レビューしてから実装し直し、次のレビューを回す。

**2回で止めてよいかを訊かない。**規則が突き合わせ直す回を決めているのだから、そこまでは訊かずに回す。

### 絶対条件：3・6・9回目で突き合わせ直す。どんな理由があっても10回で止まる

**下の「3回で収まらなかったとき」へ入っても、この決まりは消えない。**
**そこで通す6段のあとに設計から直して回し直すので、その回数も同じ勘定に入れる。**
**3回・6回・9回で収まらなければ、そのつど [CLAUDE.md](../../CLAUDE.md) の「回数を数える」にある6段を通す。**
**そのまま4回目・7回目・10回目を回してはならない。**
**10回目で収まらなければ、そこで完全に止まり、人間の返事を待つ。**

**2026-09-04 のユーザー指摘。**

> **3,6,9回のあとは、issue記載の内容と実装内容を比べ、issueに無い内容が必要となる合理的理由をまとめて、
> 敵対的レビュワーを説得する。説得できない内容は削除し、次のレビューを行う。この経緯を人間に報告する。
> 人間の返答を待つ必要はなく次のレビューに進むこと**

**数え方と、止まったときに人間へ見せるものは、
[CLAUDE.md](../../CLAUDE.md) の「絶対条件：3回ごとに issue と実装を突き合わせ直す。連続10回で完全に止まる」にある。ここには写さない。**
**写すと食い違う。**

## 3回で収まらなかったとき

**入るのは3回目だけではない。6回目・9回目でも同じ段へ入る。**
**3・6・9回目に通すのは [CLAUDE.md](../../CLAUDE.md) の「回数を数える」にある6段である。ここには写さない。写すと食い違う。**

**要点だけ。**指摘を1件ずつ潰すのをやめ、**目的の確認役・実装担当者・敵対的レビュワーの3者で
「いるか / いらないか」を判定する。**判定したら**人間の判断を待たずに、
設計のレビューからやり直す。**「削りますか」と訊かない。

**いらないと判定したときだけ、削除する仕様を先に issue のコメントへ残す。**
**何が消えたかが人間の目に触れないまま進むのを防ぐためである。**

**結果として「いまのまま」になることもある。**それでよい。

### なぜこの段が要るか

**3回で収まらないこと自体が「設計があやふや」の証拠である。**

**実測**（2026-09-01、maimuzo/continuo の3件）。**レビューの回数と設計の大きさが比例した。**

| 何 | 1回目の案 | 3回目の案 | 3回目の指摘 |
| --- | --- | --- | --- |
| ログの水準を上げる件 | **ログ1行** | **17ファイル** | Critical 1 |
| エラーの文面を直す件 | **文面1本** | **11ファイル** | Critical 2 |
| 非対応を文書に書く件 | **文書のみ** | 文書＋検査の仕組み | **Critical 7** |

**指摘は「守りが1箇所抜けている」という形で来る。**
素直に答えると、穴を埋めるものが1つ増える。**3回回せば3層になる。**

**より強いモデルに解決方法を頼んでも、この向きは変わらない。**
**強いモデルほど精密に答えるので、むしろ膨らむ。**
**効くのは「捨てられるものを挙げろ」と問うことである。**

## 飛ばしてよい場合

| 何 | 例 |
| --- | --- |
| **文書だけの変更** | README の言い回し、規則の文書 |
| **1行の修正で、他に影響しないことが明らか** | 定数の値、typo |

**迷ったら飛ばさない。**
