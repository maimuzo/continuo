# 並列で進める

## 絶対条件：指示が無いときは、workflow と git worktree で並列に進める

**人間が「これをやれ」とだけ言ったときも、既定で並列にする。**
**「並列にしてよいか」を訊かない。**

| 何 | どうするか |
| --- | --- |
| **作業の場所** | **issue ごとに git worktree を1つ作る。**本体では作業しない |
| **調査・レビュー・実装** | **Workflow か Agent で並列に走らせる** |
| **自分がやること** | **設計を書く / 結果を検査する / 人間へ報告する** |

---

## 直列にしてよいのは、依存があるときだけ

| 何 | 並列にできるか |
| --- | --- |
| **別々の issue** | **できる。**worktree を分ける |
| **同じ issue の設計 → 実装** | **できない。**設計が終わらないと実装できない |
| **同じファイルを触る2つの作業** | **できない。**片方の成果が消える |

**「同じファイルを触るか」は、着手の前に確かめる。**
**触らないなら並列にする。**

---

## よくある間違い

**レビューを並列にして、修正を直列にする。**

**2026-09-01、3つの issue を並行して進めていたが、
レビューは並列に回し、その結果を1つずつ順番に直していた。**
**1つを直している間、残り2つは止まっていた。**

ユーザー指摘: **「まさか直列に作業するつもりじゃないよね?」**

**修正も並列にする。**設計を書くのが自分の仕事でも、
**3つ分を順番に書くのではなく、走らせられるものを先に走らせてから書く。**

---

## 走らせる順番

1. **いま走らせられるものを全部走らせる**（レビュー・調査・実装）
2. **その間に、自分にしかできないことをやる**（設計を書く・結果を検査する）
3. **返ってきたものから順に処理する**

**全部が返るのを待たない。**
