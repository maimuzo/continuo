# 報告・返答のルール

## 絶対条件：何への返答かを明記する

**返答の冒頭で「どの依頼・どの質問への返答なのか」を必ず名指しすること。**

複数の依頼が並行しているとき、結果だけを渡されても人間には何の話か分からない。特に workflow を並行実行していると、**報告が届く順序と依頼した順序が一致しない**ため、対応関係が失われる。

### 守ること

1. **返答の冒頭で対象を名指しする**
   - 「ご質問の『position は外部から変更できるか』についてお答えします」
   - 「todo #2（ticket_project のファクトチェック）が完了しました」
   - 「トラック4（operator の試用手順）の結果です」

2. **並行して複数の依頼が動いているときは、他の依頼の状態も併記する**
   - どれが完了し、どれが実行中で、どれが未着手か

3. **依頼された順に返せないときは、順序が前後した理由を一言添える**
   - 例：workflow の完了順が依頼順と違う

4. **1つの返答で複数の依頼に答えるときは、依頼ごとに見出しを分ける**
   - まとめて書かない

5. **依頼は必ず TaskCreate / TaskUpdate で追跡する**
   - 返答時に todo の状態を示せば、対応関係が明示される
   - 依頼を取りこぼしたまま別の作業に移らない

---

## 絶対条件：返答の冒頭に「何が言いたいのか」を置く

**返答には必ず「## 何が言いたいのか」という見出しの節を置く。例外なし。**

### その節に書くこと

- **「結局どうなのか」を書く。**調べた過程は書かない
- **読む側が次に何をすればいいか、何が変わったか**を書く
- **専門用語や新しい呼び方を、この節で初めて出さない。**出すなら同じ節の中で1行で説明する

### 節のあとに続ける順序

1. まず「何が言いたいのか」で結論を3行にまとめる
2. 次に「何が問題か」
3. 続いて具体的な内容

調査結果をそのまま貼らない。**このリクエストは何を求めているか、だからどう報告するかを考えてから書く。**

### なぜ必要か

2026-08-16、報告の冒頭に「1つめ。作業ツリーになるのは project add 方式だけです」と書いた。ユーザー指摘: **「project add方式ってなに？何が言いたいの？ 全く理解できない」**

**結論だけを、前提抜きで書いていた。**読む側は「project add 方式」が何を指すか知らない。結論を先に書くことと、前提を省くことは別である。

---

## 絶対条件：番号ラベルを人間に見せない

**`条件3` `X2` `R1` `W4` のような番号だけのラベルを、報告の中で使ってはならない。**列見出しでも、セルの中身でも、本文でも、箇条書きでも、すべて禁止。

読む側は番号と内容の対応表を覚えていない。番号を書くのは「調べ直せ」と言っているのと同じ。

### なぜ繰り返し違反が起きるか（対策の前提）

1. **条件そのものに短い名前が無いと、番号が唯一の識別子になる。**そうなると番号で書くのが自然になり、ルールだけでは止まらない
2. **worker（subagent / workflow）への指示文やスキーマに番号を書くと、worker が番号で返してくる。**それを中継すると番号が再生産される

だから対策は次の3点をセットで行う。

- **条件には必ず短縮名を定義し、プランファイルの条件表に「短縮名」列を持たせる**
- **worker への指示文・スキーマにも短縮名だけを書く。**番号を渡さない
- **報告では短縮名だけを使う**

**短縮名だけでは足りないと感じたら、括弧で1行の補足を添える。**それでも番号は書かない。

**新しく番号を振りたくなったら、その時点で短縮名も同時に定義する。**短縮名の無いものを作らない。

## 自分で調査せず、worker にやらせて検査する

**オーケストレーター（自分）は調査作業をしない。**grep も build も実行しない。worker にやらせ、その報告が正しいかを検査するのが仕事である。

### worker への指示に必ず入れること

**主張1つにつき、次を全部つけさせる。**

| 種類 | 添えさせるもの |
| --- | --- |
| コードの挙動 | ファイル名と行番号、コード片（原文のまま） |
| 実行して確かめたこと | 実行したコマンドと、その出力（原文のまま） |
| **「無い」ことの主張** | **検索パターン・対象パス・対象コミットの3点** |

### 検査で落とすもの

- 根拠が付いていない主張
- 根拠が主張を支えていない（引用がずれている）
- **検証していない強い断定**（「1バイトも無い」「必ず」「絶対に」）
- 「〜のはず」「たぶん」「不定」で終わっているもの

### 不備があったら

**自分で調べ直さない。その worker にやり直させる。**やり直しの指示には「どの主張のどこが根拠不足か」を具体的に書く。

**worker どうしの報告が食い違ったら、決着させる worker を立てる。**自分で判定しない。

---

## 同じものを2つ以上の呼び方で呼ばない

**1つの対象には1つの呼び方だけを使う。**言い換えは読み手にとって別物に見える。

実例（2026-08-16）: 同じ「npm で配布されているビルド」を、1つの報告の中で「公開版」「配布版」「npm 版」「公開ビルド」と4通りに呼んだ。ユーザー指摘: **「公開版ってなんだよ。常に初見で理解できるように説明しろ」**

### 守ること

1. **新しい言葉を使うときは、最初に1回だけ定義する。**「npm で入れたもの＝`npm install -g` で入るもの」のように、何を指すかを具体物で示す
2. **定義したら、以後その呼び方だけを使う。**文章の見栄えのために言い換えない
3. **対比するものが複数あるときは、表で並べて定義する。**「npm で入れたもの」と「ソースからビルドしたもの」のように
4. 「番号ラベルを人間に見せない」と同じ考え方である。**識別子は1つに固定する**

### 英語の技術用語を、自分の判断で日本語に直訳しない

- **利用者が使った言葉をそのまま使う。**言い換えない
- **すでに通用している英語の技術用語（worktree, commit, branch, merge など）は英語のまま書く。**日本語に直訳すると、**同じものに名前が2つできる**
- **日本語にしてよいのは、日本語のほうが通じる場合だけ。**迷ったら英語のまま
- **漢語に置き換えるのも直訳である。**「作業ツリー」のようなカタカナ訳だけでなく、漢字2文字の造語も同じ問題を起こす

### 訳してはいけない語（実例で確定したもの）

| 書く | 書いてはいけない |
| --- | --- |
| worktree | 作業ツリー / ワークツリー |
| foreground | **前景** |
| バックグラウンドプロセス | **背景**（別の意味になる） |

実例（2026-08-16）: 利用者が「worktree」と書いたのに、報告では「作業ツリー」と直訳した。ユーザー指摘: **「作業ツリーとgit worktreeは同じことを指しているの？ もしそうならworktreeと表現しろ。なんでも日本語に直訳するな」**

実例（2026-08-17）: `foreground` を「前景」と書いた。ユーザー指摘: **「言葉が不自然。前景がfore groundの指すなら、英語で表記しろ」**。**「前景」は絵画や写真の手前側を指す語であり、プロセスの実行形態を指す語ではない。**自分で訳語を作らないこと。

**判断に迷ったときの基準。**その日本語を単独で見せたとき、**元の英単語を知らない人が別の意味に取りうるなら、訳してはいけない。**

## 名前を出すときは、その場で実体を示す

**略した呼び方（「○○方式」など）を報告に出すときは、同じ返答の中で「実際に何をするものか」を示すこと。**

### 示し方

**実行するコマンド・ファイルのパス・具体的な操作のいずれかで示す。**抽象的な説明ではなく、**具体物**を書く。

### 2つ以上を対比するときは表にする

| 呼び方 | 実際に何をするか | いま使えるか |
| --- | --- | --- |
| project add 方式 | `gh-symphony project add <ディレクトリ>` を実行して設定を作る | まだリリースされていない |

### 実例

2026-08-16、「project add 方式」とだけ書いて理解されなかった。正しくは、コマンドと状態をその場で書く。

> 「project add 方式」＝ `gh-symphony project add <ディレクトリ>` を実行して設定を作るやり方。まだリリースされていない

---

## 集計の数字を、内訳なしで見せない

**「素10 / 設定3 / 改修1」のようなバケツごとの件数だけを報告に書かない。**読む側には何の条件がどこに入ったのか分からず、意味を持たない。

- **数える前に、何をどう数えたかを名前で示す。**「複数ボード監視が改修扱いになった」のように、動いた項目を名指しする
- 内訳を示せないなら、その集計表は報告に載せない
- 集計の件数を順位づけの根拠にしない

---

## 表の書き方

- **`<br>` で改行しない。**表として成立しない
- **列数を増やしすぎない。**画面幅に収まらないと縦積みに崩れて読めなくなる。列が多い場合は表を分割する
- 縦積みの羅列（`項目: X` `判定: ○` …）は表ではない
- 上の「番号ラベルを人間に見せない」は表にもそのまま適用される

---

## ファイルパスの参照

- **markdown link 形式で、行番号を含める**：`[docs/plans/foo.md:12-34](docs/plans/foo.md#L12-L34)`
- **backtick で囲むのは禁止**
- **フルパスを求められたらフルパスで書く**

---

## 事実の扱い

- **実コードまたは一次情報で確認してから書く。**推測で断定しない
- **worker（subagent / workflow）の報告をそのまま人間に流さない。**リクエストに合致しているかを自分で判断し、足りなければ追加調査させる
- **「コードが存在する」と「機能している」を区別する。**呼び出し元が無い関数、値が常に null になる変数はデッドコードとして「無い」と扱う
- 確認できなかったことは「確認できなかった」と明記する

---

## 訂正

- 過去の報告が誤っていたと分かったら、**訂正を明示する**。黙って上書きしない
- 何をどう間違えたか、正しくは何かを書く

## 機械で検査する：Stop hook

**ここに書いた規則が守られなかったので、turn を終える直前に機械で検査することにした。**

検査するのは [.claude/hooks/check-reply-structure.py](.claude/hooks/check-reply-structure.py)。
[.claude/settings.json](.claude/settings.json) の `hooks.Stop` から呼ばれる。

### 何を検査するか

**200文字以上の返答**に、次の5つがすべて含まれているかを見る。1つでも欠けたら `{"decision":"block"}` を返し、書き直させる。

| 段 | 検査する形 |
| --- | --- |
| 引用で対象を宣言する | 行頭の `> ` で始まる行が1行以上ある |
| 三行まとめ | `## 三行まとめ`（`3行` `３行` も可） |
| 何が言いたいのか | `## 何が言いたいのか` |
| 結果 | `## 結果` |
| 詳細 | `## 詳細` |

### 検査しない場合

- **200文字未満の返答。**短い確認や相槌に構成を強いると冗長になるだけである
- **`stop_hook_active` が真のとき。**block した結果の再実行なので、そのまま通す（無限ループを避ける）

閾値の200文字は利用者が指定した値である。

### 壊れたときの振る舞い

**例外が出たら黙って通す（fail-open）。**hook が壊れて全部の turn が止まるのを避けるためである。
