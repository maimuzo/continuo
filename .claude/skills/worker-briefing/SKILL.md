# worker-briefing

**worker へ渡す前置きは、ここにある。プロンプトへ書き写さない。**

**「worker」とは、オーケストレーター（人間と話しているエージェント）が調査や実装のために立てる
subagent / Workflow の agent のことである。**continuo が issue ごとに起動する Claude Code のことではない。

## 呼ぶ側が何をするか

**プロンプトへ前置きを貼らない。このファイルを読ませ、固有の情報だけを書く。**

worker のプロンプトは、次の2つだけで組む。

| 何 | どう書くか |
| --- | --- |
| **1. このファイルへの案内** | 「作業を始める前に `<リポジトリの絶対パス>/.claude/skills/worker-briefing/SKILL.md` を Read で開き、書いてあることを全部守れ」 |
| **2. その作業に固有の情報** | 下の「4. 呼ぶ側が渡すこと」の表の行、全部 |

**Read で開かせる。**worker が Skill ツールを持っているとは限らないうえ、
`user-invocable: false` なので人間の `/` からは呼べない。**パスを直接渡すのが確実である。**

**そのパスは絶対パスで書く。相対パスで書かない。**
**worker は、呼ぶ側とは別のディレクトリで走ることがある。**Workflow の agent は
`.claude/worktrees/<名前>/` に作られた worktree の中で走るので、相対パスはそこを起点に解決する。
**その worktree がこのスキルより前の commit から作られていると、ファイルは在らず、Read は「無い」で返る。**

**呼ぶ側も worktree に居る。**[.claude/rules/parallel-work.md](../../rules/parallel-work.md) が
「本体では作業しない。issue ごとに worktree を1つ作る」と定めているためである。
**だから `git rev-parse --show-toplevel` だけでは足りない。**
**worktree の中では、それは自分が居る worktree を返す。**
**そこにこのファイルが無ければ、渡したパスは worker の手元で「無い」になる。**

**在ることを確かめてから渡す。**次を叩くと、在るほうのパスが1行で出る。

```bash
S=".claude/skills/worker-briefing/SKILL.md"
G="$(git rev-parse --path-format=absolute --git-common-dir 2>/dev/null)"
case "$G" in /*) MAIN="$(dirname "$G")" ;; *) MAIN="" ;; esac
P=""
for d in "$(git rev-parse --show-toplevel)" "$MAIN"; do
  [ -n "$d" ] || continue
  if [ -f "$d/$S" ]; then P="$d/$S"; break; fi
done
if [ -n "$P" ]; then echo "$P"; else echo "見つからない。渡す前に自分で探すこと"; fi
```

**`case` で先頭が `/` かを確かめているのは、`--path-format` が git 2.31 以降にしか無いためである。**
**古い git では、そこが空になる。**`dirname ""` は `.` を返すので、確かめずに使うと
**カレントディレクトリを起点にした相対パスが worker へ渡る。**

**2つ目は本体の作業ディレクトリである。**`--git-common-dir` は worktree の中でも本体の `.git` を返すので、
**その親が本体の作業ディレクトリになる。**
**bare repository や `--separate-git-dir` を使った checkout では、この関係が成り立たない。**
**そのときは `-f` が偽になって「見つからない」と出る。**壊れたパスを黙って渡すことは無い。

**実測（2026-09-05）。**このスキルが入った commit の親から worktree を作り、その中で叩いた。
**自分の worktree には無く、本体のパスが返った。**同じ worktree で `ls` を叩くと
`No such file or directory` である。
**`--path-format` を失敗させる git を `PATH` の先に置いて、同じ場所でもう一度叩いた。**
**「見つからない」と出た。**相対パスは1度も出ていない。

**worker 側は、Read に失敗したらそこで止まり、呼ぶ側へ「前置きが読めない」と報告する。**
**黙って本題へ進まない。**進むと、前置きを1つも知らないまま成果物を作ることになり、
**受け取る側には、それが見分けられない。**

**worker がさらに worker を立てるときも、同じ2つを渡す。**前置きは何段下がっても効く。

## 1. この製品は何か

**この段落をそのまま worker へ渡す。要約しない。**
**worker は前提知識を持っていない。**これが無いと、何を作っているのか分からないまま手を動かす。

> **continuo は、GitHub のカンバン（GitHub Projects v2）1枚を見張り、
> issue ごとに git worktree を用意して、その中で Claude Code を対話モードで起動し、
> 完了までを面倒見る常駐プロセスです。Go で書かれています。**
>
> **利用者は `continuo init` で WORKFLOW.md という1枚のファイルを受け取ります。
> 上半分（`---` に挟まれた front matter）が continuo の設定、
> 下半分（本文）が Claude Code へそのまま送られるプロンプトです。
> continuo はこのファイルを勝手に書き換えません。**

**この段落は、worker が受け取る入力である。worker が報告へ書き写す文ではない。**
**worker は本当に初見だが、その報告を読む人はこの製品を作っている当人である**
（[.claude/rules/reporting.md](../../rules/reporting.md) の「読み手をどう仮定するか」）。
**だから報告に製品の紹介文を書いてはならない。**下の 2-2 に書いてある。

## 2. どの作業でも効くルール

**この節に並べたものは、調査でも実装でもレビューでも文書でも効く。**

### 2-1. レビューが3回で収まらないのは、設計があやふやだから

**指摘を1件ずつ潰すのをやめて、設計を疑う。**

**なぜそうなるか。**レビューの指摘は「守りが1箇所抜けている」という形で来る。
**素直に答えると、穴を埋めるものが1つ増える。**3回回せば、それが3層に積み上がる。
**層が増えても、抜けの元になった設計は変わっていない。**だから4回目も同じ場所から指摘が出る。

**2026-08-30 のユーザー指摘。**

> **穴だらけのまま実装したんだろ。3回で収まらないのは当たり前だ。設計を疑え**

**入るのは3回目だけではない。6回目・9回目でも同じ段へ入る。**
**3・6・9回目に通すのは [CLAUDE.md](../../../CLAUDE.md) の「回数を数える」にある6段である。**
**ここには写さない。**
**写すと食い違う。**

### 2-2. 初見でも正しく理解できるように、問題の定義から丁寧に説明しろ

**例外は無い。**「今回は短くてよいか」を判断しない。

**報告の読み手は、この製品を作っている当人だと仮定する。**
**continuo が何をするソフトウェアかは知っている。製品そのものの定義を報告に書いてはならない。**
**上の「1. この製品は何か」は、worker が受け取る入力であって、worker が書き写す文ではない。**

**読み手が何を知らないかは、
[.claude/rules/reporting.md](../../rules/reporting.md) の「読み手をどう仮定するか」にある。**
**そこに挙がっている4つ**（issue と PR の番号 / 設定のキー / AI が付けた記号 /
その返答で初めて出す仕組みやファイル）**に、初出で1行ずつ意味を貼る。**
**ここには写さない。写すと食い違う。**

**実際に測った（2026-09-02）。**行番号は正確に書いてあったのに、
**その行が何なのかを一度も書いていなかった。**
**位置は示せているのに、そこに何があるかを言っていない**——これがいちばん多い落ち方である。

**「問題の定義」に何を書くかは、
[.claude/rules/reporting.md](../../rules/reporting.md) の
「絶対条件：初見の人が分かる形で、問題の定義から書く」にある。**
**そこにある3つ**（何が起きているか / なぜそれが困るか / いま何を決めるのか）
**が1つでも欠けたら、まだ書き終えていない。**

### 2-3. 方向調整の内容とその理由を渡す

**worker がさらに worker を立てるなら、自分が受け取った方向調整を、そのまま下へ渡す。**
**渡し方は下の「「人間が出した指示（原文で）」には、方向調整を全部入れる」と同じである。**

**自分が守れているかどうかと、下の worker が守れるかどうかは別である。**
**受け取った側で止めると、そこから下は方向調整を1つも知らないまま走る。**

**2026-09-02 のユーザー指摘。**

> **なんで方向調整の内容とその理由をworkerに伝えないんだ。伝えないから同じ間違いを何度もするんだろうが。**

**このスキル自体が、その実践である。**前置きを1箇所へ置いたのは、
**渡し忘れを「書き写し忘れ」ではなく「パスを1行書き忘れ」にまで小さくするためである。**

### 2-4. 指示に書かれたことだけで判断しない

**着手する前に、作業に効く場所を自分で探して読む。**
**指示に名前が出ているものを辿るだけでは足りない。**
**呼ぶ側が落とすのは、まさに「名前を出さなかったもの」だからである。**

**2026-09-03 のユーザー指摘。**

> worker側でも指示されたファイルに関わらず、関連ファイルなどを読んで状況を把握して
> 自分でも判断できる準備ができてから、作業に取り掛かること

- **触るファイルを開き、その呼び出し元と、対応するテストを読む**
- **触るファイルの名前・関数名・設定のキー名で、issue と pull request と設計文書を検索する。**指示に番号が出ていなくても探す
- **読む手段が無いときは、読まずに進めてよい。**そのかわり「何を読めなかったか」を最初の報告に書く

**読んだ結果が指示と食い違ったら、最初の報告に書いて、指示のとおり進める。**
**ただし「人間が却下した案を、指示が復活させている」と分かったときだけは、着手せずに止めて報告する。**
**それが、この規則が防ごうとしている失敗そのものだからである。**

**この節は、どの作業でも効く。**文書だけの変更でも、1行の修正でも飛ばさない。
**探す範囲は、触るファイルとその周りだけである。**設計文書を頭から読むことではない。

### 2-5. 1件だけ見て終わるな。同じものが他に無いかを数える

**指摘する前・直す前に、その主張が当てはまる場所を全部数える。**
**1箇所を見て報告し、同じ誤りが同じファイルの3行下に在る、が実際に5周で出た。**

**2026-09-04 のユーザー指摘。**

> worker側でも、指示された内容について、他にも同じような問題がないか確認することを徹底させて

**やること。**

| 順 | 何をするか |
| --- | --- |
| **1** | **見つけた誤りの、いちばん短い特徴的な文字列を決める**（見出しの名前・コマンド・設定のキー・言い回し） |
| **2** | **その文字列で、決めた範囲を全部検索する。**範囲は呼ぶ側が絶対パスで渡す。渡されていなければ、`git rev-parse --show-toplevel` が返すディレクトリの下を全部見る。**Bash が無く、範囲も渡されていなければ、読める範囲を数えたうえで「範囲を渡されていないので、開けたファイルだけを数えた」と報告に書く。****相対パスで数えない。**worker は呼ぶ側と別の checkout で走ることがあり、同じ文字列が0件と1件に割れる。**2-4 の「触るファイルとその周り」は着手前の下読みの範囲であって、ここの範囲ではない。ここは絞らない** |
| **3** | **出た行を、1行も切らずに最後まで読む。**当たりかどうかを行ごとに判定し、判定した結果を数に入れる（下の「数えた出力を切って読まない」） |
| **4** | **出た件数と、叩いた検索パターンと範囲を報告に書く。****範囲は `~/` から書く**（この行は公開の pull request のコメントへ貼られる）。1件なら「**1件だけだった**」と書く。**書かないと、数えていないのと同じである。**ただし文字列で特徴づけられない指摘（構造の食い違い・ファイルの混入）は、「文字列では数えられない。理由は〜」と1行書けばよい。それも数えた証拠として扱う |
| **5** | **2件以上なら、全部を1つの指摘としてまとめる。**1件ずつ別の指摘にしない。出現ごとにレベルが違うときは、いちばん重いレベルで1件にまとめ、内訳を指摘内容へ書く |

**段3 を飛ばすと、段2 を叩いた意味が消える。**

#### 絶対条件：数えた出力を切って読まない

**`cut` / `head` / `tail` / `--max-count` / `| head -n` を、数えた出力へ当ててはならない。**

**なぜか。**当たりかどうかを決める文字列は、行のどこにあるか分からない。
**表の行は長いので、切ると判定に要る部分がいちばん先に消える。**
**そして、切って読んだことは出力からは分からない。**行は出ているので、読んだつもりになる。

**2026-09-11 に実測した**（maimuzo/continuo の issue #263（continuoを使って始めたタスクでも途中で人間がチャットで進めて切りが良くなったらcontinuoに制御を戻したい）の10周）。
**検索の出力を切って読んだ命令は、1本のセッションの中で4回あった**（自分が叩いた Bash の命令だけを、`grep` の下流に `cut` / `head` / `tail` があるかで数えた）。
**これは事故ではなく、既定の書き方になっていた。**

**そのうちの1回。**

```
grep -n "起動を断る\|起動前に要求\|起動前に断る\|起動しなくなる" \
  docs/plans/continuo_design.md docs/FAQ.md docs/upgrading.md | cut -c1-140
```

**当たりだった2行は、判定に要る部分が140字を超えていて、1文字も画面に出なかった。**
**全部見えていた行だけを読んで「当たりではない」と判定し、先へ進んだ。**
**その2行が、次の周で High 1件になった。**

**長すぎて読みにくいなら、切るのではなく、当たりだけを機械で絞る。**

```bash
# 良い: 当たりの行だけを、切らずに出す
git grep -n "起動前に要求" -- docs/

# 悪い: 全部出してから目で選ぶ（切ると判定できない）
git grep -n "起動" -- docs/ | cut -c1-140
```

**件数を数えるだけなら `-c` を使ってよい。**それは読む作業ではない。

#### 段2 の「ここは絞らない」には、自分がいま編集している節も入る

**これは新しい決まりではない。**段2 が既に「絞らない」と書いている。
**破られ方だけを、ここに記録しておく。**

**2026-09-11 に実測した**（issue #263 の8周目から9周目）。
**512行の1節を11に分けたあと、数える範囲をその11節の中に固定した。**
**節の外にあった写しが4つ残り、次の周の High 4件になった。**
**絞ったことは、報告の「範囲」の欄に正直に書けてしまう。**読む人は、絞られたことに気づけない。

**この失敗は、規則が足りなかったから起きたのではない。**段2 を読んでいれば止まった。
**だから下の「機械で止める」を見る。**

#### 「既存の仕組みが解いてある」と書く前に、その仕組みを自分で開く

**これも新しい決まりではない。**[.claude/rules/reporting.md](../../rules/reporting.md) の
「実コードまたは一次情報で確認してから書く」が、**設計文書・プランファイル・コードのコメントを名指ししている。**
**破られ方だけを、ここに記録しておく。**

**2026-09-11 に実測した**（同じ issue の9周目のあと）。
**敵対的レビュワーの「既存の関門の記録が『1回だけ』も『消す規則』も持っている」を、そのまま設計へ写した。**
**その判定より前に、自分でその実装を開いた回数は0だった。**
**実際には、消す側の関数のコメント自身が「案内を書いた事実は残す」と宣言していた。**
**次の周の High 1件になった。**

**出どころが人間でも同じである。**人間の「〜だったよな?」は確認の問いであって、確定した事実ではない。
**問いのまま受け取り、一次情報を数えてから答える。**
**2026-09-11、人間の「この機能は不要と明確に返信したよな?」を確かめずに事実として扱い、
規則ファイルへ実例として書き込んだ。全コメントを数えると、そんな返信は1件も無かった。**

**開いたことを、報告に1行で書く。**「`<ファイル>:<行>` を開いて確かめた」。
**書いていないものは、開いていないものとして扱う。**

#### 機械で止める

**規則へ書くだけでは守られない。**[CLAUDE.md](../../../CLAUDE.md) が
「**規則に書くだけでは守られなかった**」と書いて、pull request のレビューの門を hook と CI の3箇所へ移した前例を持っている。

**この節の3つのうち、2つは機械で判定できる。**

| 何を | どう止められるか | いま在るか |
| --- | --- | --- |
| **切って読む** | `PreToolUse` の hook で、`grep` / `git grep` の下流に `cut` / `head` / `tail` があるときだけ落とす | **まだ無い。**人間へ提案する |
| **範囲を絞る** | 報告に書かせる「範囲」が `git rev-parse --show-toplevel` の出力と一致するかを比べる | **まだ無い。**同上 |
| **一次情報に当たらずに書く** | **機械で判定できない。**「開いた」と「読んで理解した」を機械は見分けられない | — |

**3つ目だけは、規則と報告の1行でしか止められない。**

### 2-6. レビューを頼まれたら、1回で全部挙げる

**この節は、コードレビューや設計レビューを頼まれた worker に効く。**

**同じものを別のレビュワーへ渡したら、まったく同じ結果になるくらい徹底的に洗い出すこと。**
**1回で全部挙げるつもりでやること。**

**次の周で新しい指摘が増えたとき、2つに分かれる。**

| どちらか | 誰の責任か |
| --- | --- |
| **前の周に既に存在していた誤りが、いま初めて出てきた** | **前の周のレビューが足りなかった。**数え方は 2-5 にある |
| **直しが持ち込んだ誤り**（前の周には存在していなかった） | **誰の責任でもない。**その周で初めて生まれたものなので、前の周には見つけようがない。**そう書くには、前の周の commit でその行が違っていたことを示すこと** |

**どちらなのかを、指摘に1行添えること。**
**前の周の対応表も、前の周の commit も渡されていなければ、分類できない。**
そのときは「**前の周の情報を渡されていないので分類していない**」と報告に書く。
**分からないまま「直しが持ち込んだ」と書かない。**自分の見落としが、それで免責される。

**やり方は 2-5（1件だけ見て終わるな。同じものが他に無いかを数える）にある。ここには写さない。**

### 2-7. 指摘1件ごとに、なぜ直す必要があるのかの合理的根拠を書く

**根拠は「直さなかったときに誰が何を失うか」で書く。**
**「規約に反する」だけでは根拠にならない。**

**呼ぶ側は、その根拠を否定できるなら直さない。**だから**否定できる形で書くこと。**
前提・範囲・既に別の場所で担保されているかどうかが、読んで判定できるように書く。

**2026-09-04 のユーザー指摘。**

> **レビュワーにもっとちゃんと徹底的にレビューしろと伝えろ。**
> **たとえば、同じ内容を別のレビューワーに依頼したら、まったく同じ内容になるぐらい徹底的に洗い出せ。**
> **修正してレビューしたらさっき指摘されなかった指摘が増えているのは、レビューの仕事がいい加減だからだ。**
> **修正→レビュー→修正→レビューのサイクルが長すぎる。一回で全部漏らさず指摘するつもりでやれ。**
>
> **また、レビュワーからも、なぜ修正する必要があるのかの合理的根拠をまとめてもらえ。**
> **メインエージェント側は、その合理的根拠を否定できるなら修正する必要はない。**

**実測（2026-09-04）。**PR #215（ボードの操作を AI が行う形へ規則と設計を直す（並び順の段は、そもそも書かれていなかった））で
**10周を要した。**10周目で初めて Critical と High が0件になった。
**「前の周で直したはずのものが、もう1箇所に残っている」形が、何周で出たかは数えていない。**
**この節を足した直後の PR #217（レビューを1回で全部挙げさせ、根拠を否定できるなら直さない規則を足す（10周かかった反省））では、1周目で17件が挙がった。**

## 3. 言葉づかいと制約

**中身はここに写さない。**写すと、元の規則を直したときに食い違う。
**下のパスを開いて、そこに書いてあるとおりにすること。**

| 何 | どこにあるか |
| --- | --- |
| **ファイルの書き換えは、同じディレクトリの一時ファイルへ書いてから `os.Rename` で差し替える** | [CLAUDE.md](../../../CLAUDE.md) の「ファイルの書き換えは「一時ファイルへ書いてから差し替える」」 |
| **このリポジトリは PUBLIC。**個人の絶対パス・tailnet のホスト名・トークンを書かない | [CLAUDE.md](../../../CLAUDE.md) の「公開してよい情報かを常に判断する」 |
| **英語の技術用語（worktree / branch / commit / hook / pane）を日本語に直訳しない** | [.claude/rules/reporting.md](../../rules/reporting.md) の「英語の技術用語を、自分の判断で日本語に直訳しない」 |
| **番号には issue か PR かの別と、本物の題名を添える** | [.claude/rules/reporting.md](../../rules/reporting.md) の「絶対条件：名札は、単独で書かない」 |
| **日本語では「カンバン」と書く**（「ボード」と書かない） | [docs/spec/translation-glossary.md](../../../docs/spec/translation-glossary.md) の2 |

**この5つは、worker が何を作っていても効く。**
**調査だけの worker にも効く。**報告の文章が成果物だからである。

**主張に根拠を添える形は、
[.claude/rules/reporting.md](../../rules/reporting.md) の
「worker への指示に必ず入れること（根拠の付け方）」にある。**
**呼ぶ側はそこも渡すこと。**

### 注入されていても、[CLAUDE.md](../../../CLAUDE.md) は Read で開く

**Claude Code は CLAUDE.md を自動で注入するが、その写しは古いことがある。**
実際、この節を書いた worker へ注入された写しには、
同じ pull request が足した「continuo で continuo 自身を直すとき、hook の挙動が変化する変更を実装する前に、その変更によりどんな影響があるかを深く検討し、実装してよいか人間に確認する」の規則が入っていなかった。
**worker が worktree の中で走るときは、注入されるのもその worktree の写しである。**worktree が古ければ規則も古い。
**正は作業ディレクトリのファイルであって、注入された写しではない。**
**だから worker は、上の表のパスを Read で開いて確かめる。**「注入されているから読まない」としない。

## 4. 呼ぶ側が渡すこと

**ここから下は、このファイルには書けない。作業ごとに違うからである。**
**呼ぶ側が、下の表の行を全部プロンプトへ書く。**

| 何 | 例 |
| --- | --- |
| **目的** | 「エージェントへ送る指示書が長すぎて読み取れないので、短くして並べ直す」 |
| **経緯** | 「この pull request は4周のレビューを受け、毎回同じ箇所から指摘が出ている」 |
| **人間が出した指示（原文で）** | 「着手しろ。人間に確認必要ならすぐに確認しろ」 |
| **決めた理由と、却下した案の却下理由** | 「エージェントに書かせる。**continuo に時計を持たせる案は採らない。**いま何をしているかを continuo が知らないためである」 |
| **関連するファイル** | 「/Users/…/continuo/docs/plans/continuo_design.md の 9388-9427 行に、採らなかった4案とその否定根拠がある」（**絶対パスと行番号**） |
| **その作業でだけ効く判断** | 「この検証用の仕組みは開発中にしか使わないので、最低限でよい」 |
| **確かめてほしいこと** | 「別の worker の報告なので、自分で確かめること」 |
| **過去のコメントを全部読ませる指示と、その理由** | 「この issue と pull request のコメントを、1件残らず、省略せずに読むこと」＋なぜ全部読むのか（[.claude/rules/design-review.md](../../rules/design-review.md) の「過去のコメントを全部、省略無しで読む」）。**レビューを頼むときは必ず入れる。**入れないと、レビュワーは呼ぶ側が要約した資料だけを読み、**落ちているところが呼ぶ側と同じになる** |
| **数える範囲**（絶対パス） | 「/Users/…/continuo の下全部」「/Users/…/continuo/internal/ と docs/ だけ」（2-5 の段2 で使う。渡さないと worker が別の checkout を数える） |
| **前の周の対応表**（2周目以降のレビュー） | pull request のコメントに貼ってある `<!-- code-review-result -->` のもの。**渡さないと、否定した指摘が毎周また挙がる**（[.claude/rules/design-review.md](../../rules/design-review.md) の「絶対条件：合理的根拠を否定できるなら、直さない」） |

**この表の行を、序数（2番目 / 4番目）で指さない。**行を1つ足した瞬間にずれる。
**指すときは行の名前を書く。**

**「関連するファイル」は絶対パスで、行番号まで書く。**
**worker がどこで走っているかは呼ぶ側には分からず、1万行の文書を「この中にある」と渡すのは渡していないのと同じである。**

**2026-09-03 のユーザー指摘。**

> workflowを使った時にworker側に十分にコンテキストがわたってないせいで、worker側の判断を間違うことが多発している。
> 目的、経緯、決定や否定の理由、関連するファイルなどをworkerへの指示内容に十分含めること

### 「人間が出した指示（原文で）」には、方向調整を全部入れる

**「方向調整」とは、人間が「そっちではない」と言って進む向きを変えさせた指示のことである。**

**その作業に至るまでに出たものを、1つ残らず入れる。**
**渡さないと、既に否定された方向へ worker が進む。**

**原文のまま貼る。要約しない。**
**要約すると、人間が名指しで取り下げた案が復活する。**

**方向調整が出た理由（AI が何を間違えたか）も、同じ場所に書く。**
**指示だけでは、なぜ守るのかが分からない。**分からないまま守ると、別の形で同じ間違いをする。

### 「確かめてほしいこと」が、いちばん落とされる

**worker どうしの報告を鵜呑みにさせないためのものである。**

**worker には、それが誰の言葉なのかが見えない。**
**呼ぶ側が「これは別の worker が言ったことで、まだ確かめていない」と書かない限り、
worker はそれを確定した事実として扱い、その上に結論を積む。**
**間違いは、積んだ結論の全部に伝わる。**

**だから、渡す材料の1つ1つに「確かめてあるか / 確かめていないか」を書く。**

### 「その作業でだけ効く判断」は、このファイルへ足さない

**「その作業でだけ効く判断」は、プロンプトに書く。このファイルには書かない。**

**判断がここに入ると、次の作業の worker が、関係の無い前提を持って走り出す。**
**実際に、1つの issue にだけ当てた判断を汎用のルールとして worker へ渡し、
人間から2件とも取り下げになった（2026-09-02）。**

**足してよいかの線引き。**

| 足してよい | 足してはいけない |
| --- | --- |
| **どの作業でも、どの issue でも、同じ答えになるもの** | **「今回は」「この issue は」が付くもの** |
| **人間が「ルールに加えておけ」と言ったもの** | **人間が特定の場面について述べた判断を、AI が一般化したもの** |

**迷ったら足さない。**プロンプトに書けば済む。

### 読んだうえで答えさせる問いを添える

**読んだふりを防ぐ。**このファイルを Read させただけでは、読めたかどうかが呼ぶ側に見えない。

```markdown
**読んだうえで、次に自分で答えてから作業に入ってください。**

1. **この作業は、上のどの規則に当てはまりますか**
2. **飛ばしてよい段はありますか。あるなら、どの文書のどの記述が飛ばしてよいと言っていますか**
3. **公開してよくない情報を、成果物に書きうる場面はありますか**
4. **作業に効く場所をどうやって探し、何を読みましたか。読めなかったものは、その理由も書いてください**

**答えを、最初の報告に書いてください。**
```

**公開してよくない情報の問いは、公開リポジトリで作業するときに必ず入れる。**
**探した跡の問いは、「2-4. 指示に書かれたことだけで判断しない」を実際にやったかを見るためのものである。**
**「ありません」だけの答えは受け取らない。**
**どう探したか（叩いた検索、開いたファイル）を書かせる。**
**呼ぶ側は、自分が何を渡し忘れたかに気づけない。**
**だから「本当に無かったか」を呼ぶ側が判定するのではなく、worker に探した跡を出させる。**
**問いは作業の種類によって変える。**上に並べた中身は、どれも落とさない。

## 5. 不可逆な操作は worker に渡さない

**worker には、調べること・書くこと・レビューすることを渡す。**

| 何 | 誰がやるか |
| --- | --- |
| **PR のマージ** | **メインエージェント**（[CLAUDE.md](../../../CLAUDE.md) の「絶対条件：PR のマージは、メインエージェントが自分で行う」） |
| ファイルやディレクトリの削除 | メインエージェント |
| **本番のカンバンへの書き込み** | メインエージェント |
| release の作成 | メインエージェント |

### 検査するコマンドを渡すときは、自分で試してから渡す

**メインエージェントが書いたコマンドの誤りは、worker には見抜けない。**
**渡す前に1回叩き、通ってはいけないものが通らないことも確かめる。**

**実例は [.claude/skills/pr-review-and-merge/SKILL.md](../pr-review-and-merge/SKILL.md) の
「絶対条件：段6 は worker にやらせない」にある。**
そこにあるとおり、**レビュー結果の数え方は自分で書き直してはならない。**

## 6. 走っている worker に SendMessage を送ると、実行が二重になる

**実例。**2026-09-01、2人の worker が「割り当てが逆では」と報告してきたので、
**`SendMessage` で訂正を返した。**
その後、2人とも「自分は書いていないのに、ファイルが増え続けている」と報告してきた。

| 何 | 実測 |
| --- | --- |
| `issue144_branch_and_push.md` | 1004 → 1028 → 1085 → 1123 → 1190行 |
| `issue134_136_140_blocked_notice.md` | 611 → 714行 |

**書いていたのは、その worker 自身の別の実行である。**
**`SendMessage` は「Resuming agent」と返すが、元の実行が止まっているとは限らない。**

| 何 | どうするか |
| --- | --- |
| **走っている worker への訂正** | **送らない。**完了を待ち、返ってきた結果を見て次を投げる |
| **どうしても止めたいとき** | `TaskStop` で workflow ごと止める |
| **worker が質問してきたとき** | **答えが要るなら送る。**ただし**送った時点で二重に動きうると織り込む** |

**二重に動いたときの見分け方。**worker が「他人が書いている」と報告してくる。
**その「他人」は、その worker 自身の別の実行であることが多い。**
`lsof <ファイル>` は空を返す（書き込みは一瞬なので掴めない）。
**`git worktree list` と、走っている workflow の一覧を突き合わせる。**

## 落とし穴

| 何 | どうなるか |
| --- | --- |
| **前置きをプロンプトへ書き写す** | **写した時点の内容で固まる。**このファイルを直しても、写したほうは古いまま |
| **「1. この製品は何か」を省く** | **worker は前提知識を持っていない。**何を作っているのか分からないまま手を動かす |
| **方向調整を要約して渡す** | **人間が名指しで取り下げた案が復活する。**原文のまま貼る |
| **「確かめてほしいこと」を書かない** | **worker は別の worker の報告を確定した事実として扱う。**間違いが結論の全部に伝わる |
| **その作業でだけ効く判断を、このファイルへ足す** | **次の作業の worker が、関係の無い前提を持って走り出す** |
| **目的 / 経緯 / 決めた理由と却下理由 / 関連するファイル のどれかを落とす** | **worker は指示に書いてあることだけで判断する。**却下済みの案を出し直し、1万行の文書を渡されて何も読めない |
| **Skill ツールで呼ばせようとする** | **worker が Skill ツールを持っているとは限らない。**Read でパスを開かせる |
| **相対パスで案内する** | **worker が古い worktree で走っていると、そこにこのファイルは無い。**Read は「無い」で返り、誰も気づかない |
| **走っている worker へ訂正を送る** | **元の実行が止まっているとは限らない。**同じ worker が二重に走り、同じファイルを書き合う |
| **不可逆な操作を worker に渡す** | **やり直せない。**2026-09-01、worker が2本をレビュー未実施のままマージした |
