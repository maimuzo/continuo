## 仕様から外れている箇所（2026-08-18 に判明）

**[SPEC.md](../spec/symphony/SPEC.md) と設計文書を全文突き合わせて見つかったもの。**
**別のコンテキストの検証担当が原文で当たり直し、11件すべてが引用・行番号とも正確だと確認した。却下は0件。**

**外れていること自体は必ずしも悪ではない。**continuo は Codex ではなく Claude Code を動かすので、
仕様の第10節（Codex のプロトコル）のように**そもそも適用外**の部分がある。
下の表は「適用外」ではなく**気づかずに落としている**ものだけを載せている。

| 短縮名 | 何が起きるか | どう直すか |
| --- | --- | --- |
| **候補取得が Ready だけに絞られている** | 仕様は「作業中の状態の全部で候補を取れ」と定めるのに、取得クエリが `status:Ready` の1値だけになっている。**このまま実装すると `In Progress` の item は一度も候補に現れず、設計の柱である「再起動後は特別な復旧処理が要らない」が成立しない** | 取得クエリを `active_states` 全値の OR にする。複数 Status の OR が1リクエストで取れることは実測済みなのでコストは増えない |
| **「読むだけ」宣言と Status 書き込みの併存** | 同じ文書の中で「continuo は Status を書かない」と「continuo が書く」が同時に成立している。**両方実装すると、エージェントが `In Review` へ動かした直後に continuo が失敗状態へ上書きする競合が起きる** | 「読むだけ」という表現を撤回し、**continuo が書く3か所**（dispatch 時・打ち切り時・再起動の孤児処理）を一覧にして、誰が勝つかの優先順位を書く |

### 信頼キーの求め方

**`git -C <worktree のパス> rev-parse --path-format=absolute --git-common-dir` を実行し、返り値の末尾が `/.git` ならその親ディレクトリを取る。**これが `~/.claude.json` の `projects` のキーになる。

### hook を受ける socket の置き場所

**設計文書の `/run/continuo/hooks.sock` は macOS で起動できない。**`/run` が存在せず、ルートが読み取り専用なので作ることもできない。`/var/run` は権限で拒否される。

**採る規則。**上から順に、最初に見つかったものを使う。

| 順 | 置き場所 |
| --- | --- |
| 1 | 環境変数 `CONTINUO_RUNTIME_DIR`（運用者の逃げ道） |
| 2 | `$XDG_RUNTIME_DIR/continuo`（Linux の本番。ただし**コンテナ内では設定されないことがある**ので必須にしない） |
| 3 | macOS なら `$TMPDIR/continuo`（既にユーザー専用で `drwx------`） |
| 4 | どれも無ければ `~/.continuo/run` |

**パス長の上限を必ず検査する。**macOS は**絶対パス103バイトまで**で、104バイト以上は `bind: invalid argument` になる（1バイトずつ伸ばして境界を特定した実測値。ヘッダの `sun_path[104]` と一致）。Linux は107バイトまで。**両対応のため103バイトを上限にし、設定を読んだ時点で落とす。**

> **この作業に使ったスクラッチパッドのパス自体が既に上限を超えていた。**「一時ディレクトリは長いから危ない」は抽象論ではなく、実際に起きた。

**権限は2段構え。**ディレクトリを `0700` にするのが本体で、socket ファイルの権限だけに頼らない。Go が作る socket の権限は umask 次第で、既定の環境では `0755`（誰でも接続できる）になることを実測した。ディレクトリを作ったあとに `Chmod` を必ず呼ぶ（`MkdirAll` は既存ディレクトリの権限を直さない）。

**異常終了で残った socket の始末。**残骸があると `bind: address already in use` で起動できない。**Listen に失敗したらそのパスへ Dial してみる。**つながれば本当に二重起動、つながらなければ残骸なので消してやり直す。

### 設定値の展開規則

**`os.ExpandEnv` を使ってはいけない。**実測した落とし穴。

| 入力 | `os.Expand` の結果 |
| --- | --- |
| 未定義の変数 | **黙って空文字。**設定の誤りに気づけない |
| `${UNCLOSED`（閉じ忘れ） | `UNCLOSED` になる。**独自の写像を渡しても検出できない** |
| `price is $100` | `price is 00` になる |
| `literal $$ dollar` | `literal  dollar` になる |
| `${VAR:-default}` | 変数名が `VAR:-default` という文字列になる |

**採る規則。**

- **自前の小さなパーサを書く。**`$$` / `${NAME}` / `$NAME` の3つだけを受け付け、それ以外の `$` は設定エラーにする
- **未定義の環境変数はエラー。**「設定されているが空」もエラー。無人運用では、原因の分からないエラーで落ちるより、設定を読んだ時点で名指しで落ちるほうがよい
- **チルダの展開は先頭の `~` または `~/` だけ。**`~user` 形式はエラーにする。展開の実体は `os.UserHomeDir()`
- **展開を適用するキーを限定する。**パスと接続先を表す3つだけ（herdr の socket / worktree の置き場所 / hook を受ける socket）。**テンプレート文字列や、Claude Code へ渡す環境変数には適用しない**

**展開しないと本当に `~` という名前のディレクトリが作られることを実測で再現した。**

## worktree の置き場所（2026-08-18 に調査）

**人間の疑問3つに答えるための調査。**結論から書く。

| 疑問 | 答え |
| --- | --- |
| **symphony の規則どおりに作る必要があるか** | **必要は無い。ただし置き場所を continuo が明示的に決める必要はある。**herdr 任せにすると issue 番号がパスに現れない |
| **ghq の既定パスに合わせれば問題は起きないのでは** | **その前提が成立しない。ghq に worktree の機能が無い** |
| **同じ issue を同時に処理しない限りパスは重複しないのでは** | **成り立たない。**6つの重複・失敗の経路を実測で確認し、**うち5つは「同時処理」と無関係に起きる** |

### ghq には worktree の機能が無い

**原理。**ghq は「リモートリポジトリのクローンを決まった場所に整理するツール」であって、worktree を作る機能を持たない。

**確かめ方と結果。**`ghq --help` のサブコマンドは `get` / `list` / `rm` / `root` / `create` / `migrate` の6つだけで、
`worktree` という語は**0件**（`ghq --help | grep -ci worktree` → `0`）。公式ドキュメントでも同じ回答を得た。

**では前身の herdr-symphony は何を使っていたのか。**ghq と **gwq** の2つを、役割を分けて使っていた。

| ツール | 役割 |
| --- | --- |
| **ghq** | `owner/repo` からローカルのクローン先を**引く**（探すだけ） |
| **gwq** | **worktree を作る。**置き場所は `~/worktrees/{{.Host}}/{{.Owner}}/{{.Repository}}/{{.Branch}}` |

**実測した gwq の設定。**`worktree.basedir = ~/worktrees` / `naming.template = {{.Host}}/{{.Owner}}/{{.Repository}}/{{.Branch}}`。
**つまり worktree の置き場所を決めていたのは gwq であって ghq ではない。**

### ghq 配下を置き場所にすると、封じ込め検査が破れる

**この機械の `~/ghq/github.com/maimuzo/` の中身は、全8件ともシンボリックリンクである。**
実体は `~/Sources/github/<name>` にある。

**そして git はシンボリックリンクを実体に解決して返す**（実測）。

**何が起きるか。**`workspace.root` を `~/ghq/...` の下に置くと、設定上のパスは `~/ghq/...` なのに
git が返すパスは `~/Sources/github/...` になる。**「worktree が置き場所の内側にあるか」を素朴な文字列比較で検査すると、
必ず「外にある」と判定されて落ちる。**

### herdr は path を指定できる。省略すると herdr が決める

**確かめた結果。**`herdr worktree create` は `--path <PATH>` を受け取る（socket API のスキーマでも `path` は `string | null` で必須ではない）。

| path をどうするか | worktree がどこにできるか |
| --- | --- |
| **continuo が渡す** | continuo が決めた場所 |
| **省略する** | `<herdr の worktrees.directory>/<repo>/<ブランチ名のスラグ>`。既定は `~/.herdr/worktrees` |

**省略した場合の問題。**パスに現れるのは**リポジトリ名とブランチ名だけ**で、issue の識別子が入らない。
設計文書 [continuo_design.md:389](continuo_design.md#L389) が「**worktree のパスに issue 番号を含める**」を
再起動時の復元の第2の経路として要求しているので、**herdr 任せではこの要求を満たせない。**

### パスが重複・失敗する6つの経路（すべて実測）

| 経路 | 「同じ issue の同時処理」で説明できるか | 実測の結果 |
| --- | --- | --- |
| **別々の issue がサニタイズ後に同じ名前になる** | **できない**（別の issue である） | `a/b#1` `a_b_1` `a_b#1` `a/b_1` の4つが `a_b_1` の1つに潰れた。**ハッシュ接尾辞を付けると衝突0件** |
| **前回の worktree が残ったまま同じ issue を再処理する** | **できない**（同時ではない） | `fatal: '...' already exists` で失敗 |
| **ブランチ名が重複する** | できない | `fatal: 'b1' is already used by worktree at '...'` |
| **人間が手で作ったディレクトリと衝突する** | **できない**（continuo の外の出来事） | **空なら git が黙って乗っ取る。**1バイトでもファイルがあれば失敗 |
| **登録は残っているが実体が消えている** | できない | `fatal: '...' is a missing but already registered worktree`。**`git worktree prune` を先に実行しないと回復しない** |
| **複数の continuo が同じボードを見る** | **同時処理を防ぐ機構がそもそも無い** | claim はメモリ上にあるのでプロセス間で共有されない |

### あわせて見つかった2件

**worktree の作成に失敗すると branch だけが残る。**
`git worktree add -b <名前> <パス>` は**ブランチを先に作ってからパスを検査する**ので、
パスの検査で落ちてもブランチは残る。実測では4回の失敗で孤児ブランチが4本残った。
**「worktree と branch を本体が片付ける」という要件が、失敗経路で崩れる。**

**複数の continuo を防ぐ仕組みが無い。**
claim はメモリ上にあるので、2つ目の continuo は1つ目が処理中の `In Progress` の issue を掴む。
**扱うボードが1枚に凍結されていることは、この問題を防がない。**両方が同じ issue 集合を見るので衝突が最大になる。
symphony は単一プロセスを前提にしているので、**多重起動の防止は continuo 独自の要件になる。**

### 採る案

**symphony の規則を土台にしつつ、herdr へ `--path` を明示的に渡す。**

| 手順 | 内容 |
| --- | --- |
| 1 | `workspace.root` は**実体のパスの下**に置く（`~/continuo/worktrees` のままでよい。**`~/ghq` 配下にはしない**） |
| 2 | ディレクトリ名は issue の識別子から導く。許可文字以外を `_` に置換し、**置換で文字列が変わったときだけ**ハッシュ接尾辞を付ける |
| 3 | `worktree.create` に `path` を**明示的に渡す** |
| 4 | 作る前に検査する。登録が残って実体が無ければ `git worktree prune`、実体も登録もあれば**再利用**、実体はあるが登録が無ければ**エラーにして人間へ報告**（空ディレクトリの黙った乗っ取りを避ける） |
| 5 | 作成に失敗したら、**その場で孤児ブランチを `git branch -D` する** |

**なぜこの案か。**

- **ghq に合わせる案は物理的に不可能。**worktree の機能が無い
- **herdr 任せの案は問題を移動させるだけ。**一意性の責任がブランチ名へ移り、しかも命名規則が herdr 側にあるので continuo が検証できない
- **この案だけがサニタイズ衝突を設計で消せる。**実測で確認済み
- **`--path` を渡しても herdr は worktree を workspace として開く**ので、削除に必要な ID は取れる（削除 API は `workspace_id` が必須）

## 敵対的レビューで見つかった矛盾（2026-08-18）

**`architect` に設計文書・実装プラン・仕様の写しを全文読ませ、敵対的に矛盾を探させた結果。**
既知の欠陥を除外指定したうえで、**新たに43件**が出た。**実装を止める3件は、わたし自身が実ファイルで検算済みである。**

### 実装を止める3件

#### worktree を消す契機が3通りある

**原理。**設計文書の中に、worktree をいつ消すかの答えが3つあり、互いに両立しない。

| 場所 | 何と書いてあるか |
| --- | --- |
| [continuo_design.md:474](continuo_design.md#L474) | 「issue が **active でなくなった時点**で片付けを始める」 |
| [continuo_design.md:617](continuo_design.md#L617) | 「worktree を消す契機は **`Done` だけ**にする。`In Review` と `Blocked` では消さない」 |
| [continuo_design.md:794](continuo_design.md#L794) | `on_states: ["Done"]` |

**噛み砕くと。**`active_states` は `Ready` と `In Progress` の2つである。だから「active でなくなった」とは
**`In Review` に入った瞬間**を指す。つまり [行 474](continuo_design.md#L474) のとおり実装すると、
**エージェントが成果をコメントして `In Review` へ動かした直後に、worktree と branch が消える。**
これは [行 617](continuo_design.md#L617) が「作業成果が失われる」と名指しした失敗そのものである。

**さらに参照が壊れている。**[行 511](continuo_design.md#L511) は「worktree を消す契機は独立した設定で持つ（3-9）」と
3-9 を指しているが、**3-9 に独立した設定は無く、そこにあるのは [行 474](continuo_design.md#L474) の逆の規則である。**

**仕様も 617 側である。**[SPEC.md:886](../spec/symphony/SPEC.md#L886) に
*"Successful runs do not auto-delete workspaces."*（**訳:** 成功した実行は workspace を自動削除しない）とある。

**直し方。**[行 474](continuo_design.md#L474) を「Status が `cleanup.on_states` に入った時点」に書き換え、
「active でなくなった」という条件を文書から消す。[行 511](continuo_design.md#L511) の参照先を設定キーの名前に置き換える。

#### 5分の無音打ち切りが、正常に働いている turn を殺す

**原理。**設定は `stall_timeout_ms: 300000`（5分）である（[continuo_design.md:773](continuo_design.md#L773)）。
仕様の stall 検知は「**最後にイベントを見てからの経過時間**」で測る。

**噛み砕くと。**準拠元の symphony は Codex から絶え間なくイベントが流れてくる前提だが、
**continuo が受け取るのは `Stop` フックだけである。**そして `Stop` は turn の終わりにしか来ない。
**つまり「1つの turn が5分を超える」と、その turn は stall と判定されて殺される。**
実際のコーディング作業で5分を超えない turn はまれである。

**同じ状況に、設計文書は逆の指示も出している。**[行 354-362](continuo_design.md#L354-L362) は
「`background_tasks` が空でない → **まだ動いている。何もしない**」と書いている。
**片方は「何もしない」、もう片方は「5分で殺してリトライを積む」である。**

**実測で分かっていること。**[hooks_probe の記録](../evidence/hooks_probe_20260817.jsonl)を数え直したところ、
**`PreToolUse` と `PostToolUse` は実際に発火している。**したがって中間の hook を liveness の更新に使える。

**直し方の選択肢。**下の「判断をお願いしたいこと」に3案を挙げる。

#### 未信頼のリポジトリで、起動を止めるのか issue を飛ばすのか

**原理。**Claude Code は信頼していないフォルダで hook を保留する。だから信頼の検査が要る。
**その検査に失敗したとき何をするかが、2通り書かれている。**

| 場所 | 何と書いてあるか |
| --- | --- |
| [continuo_design.md:429](continuo_design.md#L429) + [436](continuo_design.md#L436) | 起動時の検査。**「1つでも失敗したら起動を止める」** |
| [continuo_design.md:708](continuo_design.md#L708) + [807](continuo_design.md#L807) | **「未承認のリポジトリは dispatch しない」**。設定は `on_untrusted: skip_and_comment` |

**噛み砕くと。**片方は「常駐プロセス全体が起動しない」、もう片方は「その issue だけ飛ばして走り続ける」である。
**ボードには5つのリポジトリが載っているので、1つでも未承認なら前者では continuo が二度と起動しない。**

**そもそも起動時の検査としては実行できない。**「対象リポジトリ」の集合はボードを読むまで分からない。
起動した時点では対象が確定していないので、起動時検査の表に置くこと自体が成立しない。

**直し方。**信頼の検査を起動時検査から外し、**dispatch の直前検査（issue ごと）**に移す。

## クラッシュしたときに壊れる箇所と、その対策（2026-08-18）

**`architect` に「任意の瞬間に落ちたとき壊れないか」だけを見させた結果。**
**重大な3件はわたしが実ファイルで検算済みである。**そのうえで対策を決めた。**人間の判断は要らない。**

### 落ちると壊れる箇所（重い順）

#### 着手の手順の順番が決まっていない — 同じ worktree に Claude Code が2つ立つ

**原理。**issue に着手するとき continuo がやることは複数ある。
ボードの Status を `In Progress` へ書く／worktree を作る／branch を作る／pane を作る／Claude Code を起動する。
**この順番が [continuo_design.md](continuo_design.md) のどこにも書かれていない**（`dispatch` を検索して15件出たが、順番を定めた記述は0件）。

**噛み砕くと。**pane を先に作る実装を選ぶと、pane を作った直後に落ちたときボードは `Ready` のまま残る。
再起動した continuo は復元のときに `In Progress` の issue しか見ない（[continuo_design.md:405](continuo_design.md#L405)）ので、
**この issue は「まだ誰も手を付けていない」ものとして次の巡回で拾われ、同じ worktree でもう1つ Claude Code が起動する。**
入力を待たない権限モードで動くので、2つが同じファイルを同時に書く。

**決めたこと。ボードの Status を `In Progress` へ書くのを、必ず最初の段にする。**
worktree・branch・pane・Claude Code の作成はすべてその後に置く。
**こうすると、途中で落ちたときに残るのは「Status だけ進んで実体が無い」状態に限定される。**
その状態は `In Progress` が候補に含まれるので、次の巡回で自然に拾い直される。

#### worktree のパスから issue へ戻れない — 完了の見張りが成立しない

**原理。**ディレクトリ名は issue の識別子から作るが、**使えない文字を潰す処理は一方向である。**
潰した結果から元の識別子は復元できない。ハッシュ接尾辞は「別々の issue を区別する」ためのもので、
「元の issue を復元する」ためのものではない。**この2つは別の性質である。**

**噛み砕くと。**設計は「worktree を列挙して、対応する issue の Status を取り直す」という見張りを持つことにした。
**ところがディレクトリ名から issue に戻れないので、この見張りが実装できない。**

**決めたこと。worktree の中に、その worktree が誰のものかを書いたファイルを置く。**

| 記録する項目 | 何のために |
| --- | --- |
| issue の URL | 逆引きの主キー |
| project item の ID | ボードを ID 指定で取り直すため |
| branch 名 | 片付けのとき消す対象を確定するため |
| herdr の workspace の ID | worktree を消す API がこの ID を要求するため |
| 作成時刻 | 古い残骸の判別 |
| 引き継いだ回数 | 落ちるたびに turn 数が 1 に戻るので、無限に turn を消費しないための上限 |

**そのリポジトリの `.git/info/exclude` に登録して、commit されないようにする。**

#### Claude Code のセッション UUID を復元していない — 引き継いだ run の通知が捨てられる

**原理。**hook から届く通知がどの run のものかは、セッション UUID で判別する。
その UUID は continuo のメモリにしかないので、落ちると消える。

**復元する手段は既に文書にあるのに、復元の手順が使っていない。**
[continuo_design.md:226](continuo_design.md#L226) は「pane の `agent_session` から Claude Code のセッション UUID が取れる」と書いているのに、
復元手順（[同:402-411](continuo_design.md#L402-L411)）はそれを読まない。

**決めたこと。復元の手順に「pane の `agent_session` からセッション UUID を取る」段を追加する。**

### そのほかに落ちると壊れるもの

| 短縮名 | 何が起きるか | 決めたこと |
| --- | --- | --- |
| **turn の終わりの通知が一度きり** | continuo が落ちている間に届いた `Stop` は再送されない。回復手段が壊れている stall 検知しか無い | **再起動の直後に、引き継いだ run すべてについてボードを1回取り直す。**hook を待たない |
| **片付けに必要な ID が失われる** | worktree を消す API は herdr の workspace の ID を要求するが、それを再起動後に取り直す方法が書かれていない | **所有情報ファイルに書く**（上の表） |
| **孤児 branch の後始末がプロセスの中にしか無い** | worktree の作成に失敗すると branch だけが残る。その場で消す対策は書いたが、`kill -9` では走らない | **起動時の掃除に、`continuo/` で始まり対応する worktree も走行中の issue も無い branch を加える** |
| **push していない commit を消しうる** | 片付けは未コミットの変更しか守らない。commit 済みで push 前の成果は `git branch -D` で消える | **branch を消す前に、すべての commit が upstream に到達しているか確かめる。**到達していなければ消さずに issue のコメントへ branch 名を残す |
| **落ちるたびに turn 数が 1 に戻る** | 20回未満の turn ごとにクラッシュすると、打ち切りが一度も発火しない | **引き継いだ回数を所有情報ファイルに記録し、上限を設ける** |
| **`In Review` へ移った直後に落ちると Status を巻き戻す** | 復元の手順が「突き合わせが付かない → Ready へ戻す」なので、エージェントが動かした結果を巻き戻す | **Status を書き換える前に必ずボードを ID 指定で取り直す。**もう作業中の状態でなければ書かない |
| **hook を受ける socket のパスが起動のたびに変わりうる** | 探索順が環境に依存するので、別の起動方法で立て直すと別のパスになる。走行中の Claude Code は前回のパスを持ったままなので通知が届かない | **決めたパスを所有情報ファイルに書き、再起動時はそれを優先する** |

### 二重起動の防止 — `ps` は使わない

**人間から「`ps` で既に起動していれば新しく起動させない、という制限でよい」という方針をもらった。
ただし `ps` には落とし穴がある。**

**原理。**hook を届けるサブコマンドは、**本体と同じ実行ファイルの名前で起動する**
（[continuo_design.md:333](continuo_design.md#L333) の `continuo hook --socket ...`）。
`ps` の出力を実行ファイル名で照合すると、**turn が終わるたびに一瞬だけ現れるこのプロセスに当たる。**

**噛み砕くと。**クラッシュ直後の自動再起動と、どこかの turn の終わりが重なると、
「既に起動している」と誤判定して起動を拒否する。**間欠的にしか起きないので原因の特定が難しい。**

## 実測: statusline に渡されるデータでトークンの計上が取れるか

**言いたいこと。**statusLine の JSON には**セッション累計のコスト（USD）はあるが、セッション累計のトークン数は無い。**
トークンは「直近の1回の API 応答のスナップショット」だけで、走行全体を出すには各 fire を足す必要がある。
**その fire は取りこぼす。**実測で 9 回の API 応答に対し fire が 1 回しか届かなかった。**走行ごとのトークン計上は transcript から取る。**

### 結論

| 欲しいもの | statusLine で取れるか | 取り方 |
| --- | --- | --- |
| 走行ごとのコスト（USD） | **取れる** | `cost.total_cost_usd` はセッション累計。走行の前後で差を取る |
| 走行ごとの入力・出力トークン | **取れない** | fire が落ちるので合算できない。`transcript_path` の JSONL を読む |
| セッションの識別子 | **取れる** | `session_id`（UUID） |
| プロンプト単位の識別子 | **取れる** | `prompt_id`（UUID。ユーザー入力1回ごとに変わる） |
| レートリミットの残量 | **取れる** | `rate_limits.five_hour` / `rate_limits.seven_day` |

**したがって continuo は、走行ごとのトークン使用量を statusLine 経由では取らない。**
statusLine は **`transcript_path` と `session_id` と `prompt_id` と累計コストを拾う経路**として使い、
**トークンの実数は `transcript_path` が指す JSONL の `.message.usage` を集計して出す。**

### 累積かスナップショットか（実測）

`context_window.total_input_tokens` は**累計ではない。**直近1回の API 応答の
`input_tokens + cache_creation_input_tokens + cache_read_input_tokens` に一致する。

```
$ tail -1 statusline-input.jsonl | jq '{tit:.context_window.total_input_tokens, sum: (.context_window.current_usage.input_tokens + .context_window.current_usage.cache_creation_input_tokens + .context_window.current_usage.cache_read_input_tokens), tot:.context_window.total_output_tokens, out:.context_window.current_usage.output_tokens}'
{
  "tit": 38619,
  "sum": 38619,
  "tot": 7,
  "out": 7
}
```

一方 `cost.total_cost_usd` は**セッション累計で単調増加する。**同一セッションの fire を時系列で並べた実測値。

```
$ jq -c '{n:input_line_number, prompt_id, cost_usd:.cost.total_cost_usd, tit:.context_window.total_input_tokens}' statusline-input.jsonl
{"n":1,"prompt_id":null,"cost_usd":0,"tit":0}
{"n":2,"prompt_id":"c75afcee-0fd9-46e8-ba07-99e675407212","cost_usd":0.140698,"tit":36680}
{"n":3,"prompt_id":"c75afcee-0fd9-46e8-ba07-99e675407212","cost_usd":0.161462,"tit":36849}

```

`prompt_id` はユーザー入力1回ごとに変わり、その入力の処理中に起きる複数の fire では同じ値になる（2行目と3行目）。
**走行の区切りに使える。**

### fire は落ちる（決定的な実測）

statusLine のスクリプトを `sleep 3` を挟む遅いものに差し替えて、逐次の Bash tool 呼び出しを 8 回させた。

| 見たもの | 速いスクリプトのとき | `sleep 3` のスクリプトのとき |
| --- | --- | --- |
| その走行の API 応答の件数（transcript の assistant 件数） | 7 | **9** |
| その走行で届いた statusLine の fire | 7 | **1** |

`sleep 3` のときの実測。走行の前後で件数を数えた。

```
$ echo "fires before slow test: $(wc -l < statusline-input.jsonl)"
fires before slow test:       11
$ echo "assistant msgs before slow test: $(jq -c 'select(.type=="assistant")' "$T" | wc -l)"
assistant msgs before slow test:       10

（プロンプト送信後）

$ echo "fires after slow test:  $(wc -l < statusline-input.jsonl)"
fires after slow test:        12
$ echo "assistant msgs after:   $(jq -c 'select(.type=="assistant")' "$T" | wc -l)"
assistant msgs after:         19
```

**9 件の API 応答に対して fire は 1 件しか残らなかった。**残ったのは最後の1件である。
公式ドキュメントの記述と一致する。原文と訳を併記する。

> Claude Code debounces updates at 300ms, so rapid changes batch together and your script runs once after the changes stop. If a new update triggers while your script is still running, Claude Code cancels the in-flight script.
>
> （訳）Claude Code は更新を 300ms でまとめるため、短い間隔の変化は束ねられ、変化が止まったあとに1回だけスクリプトが走る。**スクリプトの実行中に次の更新が起きると、Claude Code は実行中のスクリプトを打ち切る。**

**速いスクリプトなら 1対1 で届いた**（この検証では API 応答 10 件に対し fire 10 件、burst でも 7 件に対し 7 件）。
ただし **300ms のまとめ込みは速いスクリプトでも効く。**取りこぼしが起きない保証は無い。

### 公式ドキュメント

statusLine の入力スキーマは公開されている。**「Full JSON schema」のアコーディオンに全文がある。**

- https://code.claude.com/docs/en/statusline （旧 https://docs.claude.com/en/docs/claude-code/statusline から 301 で転送される）

ドキュメントが挙げるフィールドのうち、continuo に効くもの。

| フィールド | ドキュメントの説明（要旨） |
| --- | --- |
| `cost.total_cost_usd` | クライアント側で計算したセッションの推定コスト。実際の請求とは異なりうる。`/clear` で 0 に戻る |
| `context_window.total_input_tokens` / `total_output_tokens` | **直近の API 応答時点で**コンテキストウィンドウに入っているトークン数。入力にはキャッシュの読み書きを含む |
| `context_window.current_usage` | 直近の API 呼び出しのトークン内訳。**最初の API 呼び出しの前と `/compact` 直後は `null`** |
| `session_id` | セッションの一意な識別子 |
| `prompt_id` | 処理中のユーザープロンプトを指す UUID。**Claude Code v2.1.196 以降** |
| `transcript_path` | 会話の transcript ファイルのパス |
| `rate_limits.*` | **Claude.ai の Pro/Max 契約でのみ**、かつセッション最初の API 応答の後に入る |

### continuo の設計への反映

1. **走行ごとのトークン使用量は `transcript_path` の JSONL を集計して出す。**statusLine の fire を足さない
2. **statusLine は「transcript の場所と走行の区切りを知る」ために使う。**`session_id`・`prompt_id`・`transcript_path`・`cost.total_cost_usd` を拾う
3. **statusLine スクリプトは必ず速く終わらせる。**遅いと自分の fire を自分で潰す。追記だけして即 exit する
4. **`rate_limits` は必ず入るとは限らない。**契約と、セッション最初の API 応答の後という条件がある。欠損を前提に読む
5. **`context_window.current_usage` は `null` になりうる。**セッション開始直後と `/compact` 直後

## 実測: Stop hook が turn を差し戻せるか

**言いたいこと。**差し戻せる。`{"decision":"block","reason":"…"}` を標準出力に出すと turn は終わらず、
`reason` が **`Stop hook feedback:` を頭に付けた user メッセージ**として Claude に届き、Claude はその指示どおり動いた。
無限ループの回避は **`stop_hook_active` を見る**のと、**Claude Code 側の「連続8回で打ち切り」**の二段で効く。

**実測日 2026-08-18。**Claude Code 2.1.234 / herdr 0.8.0 / macOS。
Claude Code は herdr の pane に `--settings <使い捨て> --permission-mode dontAsk` で起動した。

### 結論

| 確かめたこと | 結果 |
| --- | --- |
| `decision: "block"` で turn は継続するか | **継続した。**同じ turn の中で Claude が Bash を実行し、指示された文言を出力した |
| `reason` は Claude にどう届くか | **`isMeta: true` の user メッセージ。**本文は `Stop hook feedback:\n` + reason の原文 |
| 2回目の Stop hook は発火するか | **発火した。**標準入力の保存が2件になった |

## 実測: subagent の識別子と background_tasks の id の関係

**言いたいこと。**subagent の `agent_id` と `background_tasks[].id` は**同じ文字列である**（15件すべて一致）。
だが **`background_tasks` が空配列であることを「turn が終わった」の判定に使ってはならない。**
4回の試行すべてで、**turn の途中に `background_tasks: []` の `Stop` が発火した**。

### 何を仕掛けたか

Claude Code 2.1.234 を herdr の pane で対話モード起動し（`--settings <下記> --permission-mode dontAsk`）、
`SubagentStart` / `SubagentStop` / `Stop` / `PostToolUse`（matcher `Agent|Task`）の4つに
**標準入力を原文のままファイルへ落とすだけ**のスクリプトを仕掛けた。判断は一切させていない。

- 記録スクリプト: `<probe>/rec.sh`（`cat > "$D/$1-<epoch.usec>-$$.json"` のみ）
- 設定: `<probe>/settings.json`
- 対話は「1メッセージ内で Agent ツールを N 個並列に呼べ」を4回（N = 3, 3, 5, 4）

### 識別子は一致する

**named subagent 15件について、次の4つの集合が完全に一致した。**

| どこの値か | フィールド |
| --- | --- |
| subagent 開始 | `SubagentStart.agent_id` |
| Agent ツールの戻り値 | `PostToolUse.tool_response.agentId` |
| 実行中一覧 | `Stop.background_tasks[].id` |
| subagent 終了 | `SubagentStop.agent_id` |

実物（1件）。`Read f1.txt` の subagent。

```json
{"hook_event_name":"SubagentStart","agent_id":"af1b2c1bba3856179","agent_type":"general-purpose"}
{"hook_event_name":"PostToolUse","tool_name":"Agent","tool_response":{"isAsync":true,"status":"async_launched","agentId":"af1b2c1bba3856179","description":"Read f1.txt"}}
{"hook_event_name":"Stop","background_tasks":[{"id":"af1b2c1bba3856179","type":"subagent","status":"running","description":"Read f1.txt","agent_type":"general-purpose"}]}
{"hook_event_name":"SubagentStop","agent_id":"af1b2c1bba3856179","agent_type":"general-purpose","last_assistant_message":"file 1"}
```

### Agent ツールは非同期に起動する

`PostToolUse.tool_response` が `{"isAsync":true,"status":"async_launched"}` を返す。
**subagent の結果を待たずに main の turn がいったん終わる。**だから subagent 実行中に `Stop` が発火する。
実測: 15回の `Stop` のうち **6回が `background_tasks` 非空**だった。

### 空配列を「turn の終わり」に使えない

**4回の試行すべてで、`background_tasks: []` の `Stop` が turn の途中に出た。**

| 試行 | 途中の Stop（bt 空）の `last_assistant_message` | 次の Stop までの間隔 |
| --- | --- | --- |
| 3並列 | `Bが完了しました（date の出力: …）` | 5.60 秒 |
| 3並列 | `D（f1.txt）が完了しました: file 1。E と F の完了を待ちます。` | 2.20 秒 |
| 5並列 | `f5.txt が完了しました: file 5。残り2つ（f6、f7）の完了を待ちます。` | 2.15 秒 |
| 4並列 | `f5.txt（file 5）と f6.txt（file 6）が完了しました。残り1つ（f7）の完了を待ちます。` | 2.02 秒 |

**なぜ空になるか。**subagent が終わると registry から即座に消える。だが結果は別の wake-up として
あとから main へ届く。**「registry が空」と「結果が届き終わった」の間に 2〜6 秒の隙間がある。**
その隙間に `Stop` が発火する。

**wake-up ごとに `prompt_id` が変わる。**利用者が1回入力した turn が、実測で `Stop` 3〜4回に分かれた。
`prompt_id` が利用者入力のものと一致するかで判定する案も成立しない。最終回答が出た `Stop` の
`prompt_id` は利用者入力のものと**別の値**だった（3並列の例: 入力 `d1b4da00…` → 最終 `46828471…`）。

### herdr の agent_status は途中で idle にならなかった

4並列の試行中、herdr の `agent_status` を 0.4 秒間隔で 45 回観測した。
途中の `Stop`（1787050690.026 / 692.225 / 695.241）のいずれでも `idle` は現れず、
最終 `Stop`（1787050697.263）の **0.38 秒後**に `idle` へ変わった。

```
1787050695.241 working   <- background_tasks: [] の Stop と同時刻
1787050696.851 working
1787050697.252 working
1787050697.646 idle      <- 最終 Stop の直後
```

**0.4 秒間隔の観測なので、それより短い idle があっても捉えられない。**「一度も idle にならない」とは言えない。

### continuo はどう作るか

**`Stop` の `background_tasks` が空であることだけで完了と判定しない。**次の2つを併用する。

1. **`background_tasks` 非空なら即「未完了」**（これは確実。誤検知しない方向にしか外れない）
2. **空だった場合は、一定時間（実測の最大 5.6 秒に余裕を見て 15 秒以上）新しい `Stop` /
   `SubagentStop` が来ないことを確かめてから完了とする**

**さらに herdr の `agent_status` を併用する。**実測では herdr は途中の `Stop` で idle にならず、
最終 `Stop` の直後だけ idle になった。hook 単独より外れにくい。

### 副次の観測

- **`agent_type` が空文字の `SubagentStop` が 14 回発火した。**`SubagentStart` が対応せず、
  `background_tasks` にも一度も現れない。`last_assistant_message` が
  `wait for E and F, then summarize` のような**次の入力候補の文面**である。
  Claude Code 内部の補助 subagent とみられる。**数を数える判定に使うと破綻する。**
- **`SubagentStop` の `background_tasks` は、停止しつつある自分自身を `running` として載せている**（15/15）。
  `SubagentStop` 側で空配列を待っても永久に空にならない。
- **この試行では subagent の Bash が拒否された。**実測の拒否文言:
  `Permission to use Bash has been denied because Claude Code is running in don't ask mode.`
  **原因は subagent ではなく、許可リストに `Bash` が無かったことである**（後述の9セッションの検証で切り分け済み）。

### 公式ドキュメント

- hook のスキーマ: https://code.claude.com/docs/en/hooks （生の markdown は同 URL に `.md`）

  **ただし「空なら turn が終わった」とは書いていない。**上の実測どおり、空でも turn は続く。

  ただし **`agent_id` と `background_tasks[].id` が同一だとは書かれていない。**上は実測による。

## 実測: `--permission-mode dontAsk` で subagent の Bash が拒否されるか

**言いたいこと。**拒否の原因は subagent ではない。**同じコマンドを main と subagent に与えた18対すべてで結果が一致した。**
**許可リストに載っていれば通る。載っていなくても通ることがあり、その条件は特定できていない**（`echo hello` は空の設定でも通った）。
`permissions.allow` に **`"Bash"`（引数の限定なし）を1つ書けば、main も subagent も Bash が通る。**
subagent を起動する経路そのものは、許可リストが空でも一度も拒否されなかった。

### 結論

| 決めたこと | 内容 |
| --- | --- |
| continuo のエージェントに subagent を使わせてよいか | **よい。** |
| 許可リストに書くもの | **`"Bash"`**（ツール名だけ。`Bash(echo:*)` のような引数限定では足りない） |
| `"Task"` を書く必要 | **無い。**Claude Code v2.1.234 に `Task` というツールは存在せず、subagent 起動ツールの名前は **`Agent`** である |

### 実測した設定と結果（3設定 × 3回 = 9セッション、各セッションで4観測）

`--settings <file> --permission-mode dontAsk` で起動。`<file>` の中身は次の3種類。

| 呼び名 | `permissions.allow` |
| --- | --- |
| 許可なし | キー自体を書かない（`{}`） |
| echo だけ許可 | `["Bash(echo:*)", "Task"]` |
| Bash 丸ごと許可 | `["Bash", "Task"]` |

結果（3回とも同じ。◯=実行された、×=拒否された）。

| 設定 | main の `echo hello` | subagent の `echo hello` | main の `touch probe.txt && rm -f probe.txt` | subagent の同コマンド |
| --- | --- | --- | --- | --- |
| 許可なし | ◯ | ◯ | × | × |
| echo だけ許可 | ◯ | ◯ | × | × |
| Bash 丸ごと許可 | ◯ | ◯ | ◯ | ◯ |

**main と subagent の結果は9セッション全てで一致した。**subagent だけが拒否された観測は無い。

### 拒否の文言（原文のまま）

```
Permission to use Bash has been denied because Claude Code is running in don't ask mode. IMPORTANT: You *may* attempt to accomplish this action using other tools that might naturally be used to accomplish this goal, e.g. using head instead of cat. But you *should not* attempt to work around this denial in malicious ways, e.g. do not use your ability to run tests to execute non-test actions. You should only try to work around this restriction in reasonable ways that do not attempt to bypass the intent behind this denial. Let the user decide how to proceed.
```

出典は Claude Code の記録ファイル（`~/.claude/projects/…/<session>.jsonl` および
その配下の `<session>/subagents/agent-*.jsonl`）の `tool_result` で、`is_error: true` が付く。

### 「許可なし」でも `echo hello` が通った理由

**dontAsk は、許可リストに無くても読み取り専用と判定したコマンドを通す。**
9セッション全てで `echo hello` は通り、`touch … && rm -f …` は「Bash 丸ごと許可」以外で拒否された。

**この判定は安定しない。**`ls -la probe.txt 2>&1; echo "---exit:$?---"` は
「許可なし」で拒否され、「echo だけ許可」では通った。**読み取り専用に見えるコマンドが通る保証は無い。**
だから **`"Bash"` を許可リストに書く以外の書き方は採れない。**

### subagent 起動そのものは拒否されない

**許可リストが空（`{}`）の設定でも、main は `Agent` ツールで subagent を起動できた。**3回とも成功。
`Agent` ツールが拒否された観測は9セッションで0件である。

### 確認できなかったこと

- **`"Bash"` を許可すれば任意のコマンドが通るのか。**確かめたのは `echo` と `touch && rm` の2種類だけである。
- **`permissions.deny` を併用したときの優先順位。**試していない。
- **同期実行の subagent。**v2.1.234 では `Agent` ツールが**バックグラウンド起動**になり、
  9セッション全てでそう動いた。同期実行の経路を通す方法は確かめていない。

## 実測: `Stop` hook の `last_assistant_message` に何が入るか

**言いたいこと。**`last_assistant_message` に入るのは、**その turn の「最後の assistant テキストブロック1つ」だけ**である。
長さでは切られない（44,823 バイトまで無切断を実測）。切られるのは**位置**で、
**印より後ろにツール実行があると印は消える。**だから表明は「最後の1行」に置くよう縛る必要がある。

### 出す結論: `last_assistant_message` だけに寄せてはいけない

**寄せられる条件つきなら成り立つ。**「印を最終応答の最後の行に置き、そのあとツールを呼ばない」を
エージェントが守れているあいだは、長さでも位置でも壊れない（44,823 バイトまで実測）。

| --- | --- |
| 印を書いたあとにツールを1回でも呼ぶ | 印はブロックごと捨てられ、`last_assistant_message` は締めの一言だけになる |
| ツール実行で終わり、印を書き忘れる | エージェントが選んだ短文（`Done.` など）が入り、印は無い |

**採る手。**`last_assistant_message` を先に見て印があれば採用し、無ければ `transcript_path` を遡る。
両方に無ければ「表明なし」として扱う。**Esc 中断はそもそも hook が来ないので、この経路では拾えない。**

## 実測: turn の終わりを確定するのに、どれだけ静止を待てばよいか

**言いたいこと。**静止時間で turn の終わりを決めるのは**成立しない。**
`background_tasks` が空の `Stop` から次の `Stop` までの隙間は、**重い作業では 63.972 秒**まで伸びた。
**この 63.972 秒は「何も起きていない時間」ではなく、メインが `./heavy.sh 45 30` を実行していた時間である。**
**したがって否定できたのは「`Stop` イベントだけを数えて静止を測る判定」であって、hook を使う判定全般ではない。**
**上限は測れていない**（100秒の作業を仕掛けた試行では、そもそも途中の空 `Stop` が出ていない）。

### 何を仕掛けたか

Claude Code 2.1.234 を herdr 0.8.0 の pane で対話モード起動し
（`--settings <下記> --permission-mode dontAsk`）、`Stop` / `SubagentStop` / `SubagentStart` /
`PostToolUse`（matcher `Agent|Task`）の4つに、**標準入力を原文のままファイルへ落とすだけ**の
スクリプトを仕掛けた。ファイル名に受信時刻をマイクロ秒まで入れる。

記録スクリプト（zsh の `$EPOCHREALTIME` を使う。外部プロセスを起動しないので遅延が乗らない）。

```zsh
#!/bin/zsh
zmodload zsh/datetime
T=$EPOCHREALTIME
D=<probe>/rec
cat > "$D/$1-$T-$$.json"
exit 0
```

重い作業を作るための道具。**このハーネスは foreground の `sleep` をブロックする**ので、
`sleep` を使わず python で待つスクリプトを置いた（`<probe>/work/heavy.sh`）。

```zsh
#!/bin/zsh
# usage: ./heavy.sh <seconds> <lines>
exec python3 -c '
import time, sys
d = float(sys.argv[1]); n = int(sys.argv[2])
end = time.time() + d
while True:
    r = end - time.time()
    if r <= 0: break
    time.sleep(min(0.25, r))
for i in range(1, n + 1):
    print("HEAVY line %04d of %04d payload=%s" % (i, n, "x" * 40))
' "$1" "$2"
```

**10回**の試行を行った。並列数 5〜10、各 subagent の所要 15〜70 秒、返す出力 300〜1500 行。
subagent には**バックグラウンド実行を禁止**した（`&` を使われると registry に background shell が
残り、`background_tasks` が空にならないため）。

### 隙間の実測

**「`background_tasks` が空の `Stop`」が turn の途中に出たのは 10試行中3試行。**その3件の
「次の `Stop` までの間隔」が下記である。**残り7試行では、空の `Stop` は最後の1回だけだった。**

| 試行 | 仕掛けた内容 | Stop の回数 | bt が空の Stop | 途中の空 Stop → 次 Stop |
| --- | --- | --- | --- | --- |
| 5並列・30秒・400行 | subagent のみ | 6 | 2 | **6.556 秒** |
| 8並列・25秒・1000行 | subagent のみ | 6 | 2 | **11.945 秒** |
| 5並列・20秒・800行 | **全部終わったあとメインが `./heavy.sh 45 30` を実行** | 6 | 2 | **63.972 秒** |
| 5並列・30/40/50/60/70秒・400行 | subagent のみ | 7 | 1 | 途中に出ず |
| 10並列・20秒・1500行 | subagent のみ | 9 | 1 | 途中に出ず |
| 6並列・30秒・600行 | subagent のみ | 6 | 1 | 途中に出ず |
| 6並列・20秒・600行 | 全部終わったあとメインが `./heavy.sh 100 30` | 6 | 1 | 途中に出ず |
| 5並列・15秒・300行 | 結果1つごとにメインが `./heavy.sh 30 10` | 2 | 1 | 途中に出ず |
| 5並列・20秒・800行 | 全部終わったあとメインが `./heavy.sh 45 30` | 6 | 1 | 途中に出ず |
| 8並列・25秒・1000行 | subagent のみ | 6 | 1 | 途中に出ず |

**実測した最大値は 63.972 秒。**

### 63.972 秒の中身（原文）

途中の空 `Stop`。**5つの subagent はこの時点で全部終わっている**が、メインはまだ4つ目までしか
結果を受け取っていない。

```json
{"session_id":"221ab532-5884-457d-bdd4-8e3b5823e081","cwd":"…/settle/work","prompt_id":"37e680b3-44b1-4fd5-afdc-d603d08fa828","permission_mode":"dontAsk","effort":{"level":"xhigh"},"hook_event_name":"Stop","stop_hook_active":false,"last_assistant_message":"subagent 4/5 が完了しました（800行）。最後の1つの完了を待ちます。","background_tasks":[],"session_crons":[]}
```

受信時刻 `1787055073.416192`。次の `Stop` は `1787055137.387734`（**+63.972 秒**）で、
`last_assistant_message` は最終回答（`ステップ3: 結果一覧です。…`）だった。
**その 63.972 秒の間、メインは 5つ目の結果を受け取り、`./heavy.sh 45 30` を foreground で実行していた。**

### だから静止時間で決めてはいけない

**隙間の長さ = 「残った結果の配送」＋「メインの次の1手が終わるまで」である。**
「メインの次の1手」は利用者のタスク次第で、`go test ./...` でも `npm run build` でも
`gh pr create` でもよい。**何分でもありうる。**63.972 秒は「45秒の作業をさせたから 63.972 秒だった」

```python
def human_turn_slice(rows, prompt_id):
    """promptSource=="typed" を起点に、人間から見た1 turn を切り出す。"""
    anchor = None
    for i, o in enumerate(rows):
        if o.get("type") == "user" and o.get("promptId") == prompt_id:
            anchor = i
            break
    if anchor is None:
        return None, None
    start = None
    for i in range(anchor, -1, -1):
        o = rows[i]
        if o.get("type") == "user" and o.get("promptSource") == "typed":
            start = i
            break
    if start is None:
        return None, None
    end = len(rows)
    for j in range(start + 1, len(rows)):
        o = rows[j]
        if o.get("type") == "user" and o.get("promptSource") == "typed":
            end = j
            break
    return start, end
```

**言いたいこと。**Bash の実行時間には上限をかけられた。`BASH_DEFAULT_TIMEOUT_MS` と

### 結論

| 設定する場所 | Claude Code に渡す settings ファイルの `env` |
| 設定する項目 | `BASH_DEFAULT_TIMEOUT_MS` と `BASH_MAX_TIMEOUT_MS` の**両方** |
| 効き方 | エージェントが自分で長い `timeout` を指定しても、上限が勝った（3/3） |
| 打ち切られた後 | プロセスは殺されず、バックグラウンドタスクに移された |

`continuo` が Claude Code を起動するときに渡す settings ファイルの実物。

```json
{
  "env": {
    "BASH_DEFAULT_TIMEOUT_MS": "20000",
    "BASH_MAX_TIMEOUT_MS": "20000"
  }
}
```

起動は `claude --settings <このファイルの絶対パス> --permission-mode dontAsk` である。

### なぜ両方を書くのか（片方だけでは効かない）

公式文書 https://code.claude.com/docs/en/env-vars.md の原文。

> `BASH_MAX_TIMEOUT_MS` | Maximum timeout the model can set for long-running bash commands
> (default: 600000, or 10 minutes). The effective ceiling is the larger of this and `BASH_DEFAULT_TIMEOUT_MS`

（訳：`BASH_MAX_TIMEOUT_MS` は、モデルが長時間動く bash コマンドに設定できる timeout の最大値
（既定 600000、すなわち10分）。**実効の上限は、この値と `BASH_DEFAULT_TIMEOUT_MS` のうち大きいほう**である）

> `BASH_DEFAULT_TIMEOUT_MS` | Default timeout for long-running bash commands (default: 120000, or 2 minutes)

（訳：`BASH_DEFAULT_TIMEOUT_MS` は、長時間動く bash コマンドの既定の timeout（既定 120000、すなわち2分））

同じことが https://code.claude.com/docs/en/tools-reference.md にも書かれている。

> Each command runs under a timeout, and Claude manages it: when it wants longer than the default
> for a command, it passes the `timeout` parameter with that call — you never set a per-command timeout.

（訳：どのコマンドも timeout のもとで動き、それを差配するのは Claude 自身である。あるコマンドに
既定より長い時間が欲しいとき、Claude はその呼び出しに `timeout` パラメータを添える。
コマンドごとの timeout を人間が設定することはない）

**この「大きいほう」の規則を実測で確かめた。**`BASH_DEFAULT_TIMEOUT_MS=35000` /
`BASH_MAX_TIMEOUT_MS=20000` にして、エージェントに `timeout: 180000` を指定させて60秒かかる
コマンドを実行させたところ、**打ち切りは 20 秒ではなく 35 秒**だった（3/3）。

## 実測: 権限の確認で止まった turn を、herdr の待ち受けで拾えるか

**言いたいこと。**`herdr agent prompt --wait --until idle --until done` は、権限の確認で止まった turn を
**拾えずに timeout で落ちる**（3/3）。`--until blocked` を足せば 2.7〜4.1 秒で拾える（6/6）。
ただし **blocked の agent に prompt を投げると、保留中の権限要求が承認されて実行されてしまう**（3/3）。

**実測日 2026-08-18。**`claude --version` = `2.1.234 (Claude Code)`、`herdr --version` = `herdr 0.8.0`。

```
When submission starts from a non-working state, --wait first requires an observed state change within 5000ms; otherwise it returns agent_prompt_stalled. A shorter --timeout returns timeout instead. It then matches idle, done, or blocked by default, or any exact --until state. It does not track turns: if the agent is already working, that active turn's completion may match. Without --timeout, the settled-state wait is indefinite.
```
