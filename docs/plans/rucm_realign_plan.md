# ユースケース記述（RUCM）を実装に合わせ直す計画

対象は issue #110（ユースケース記述（RUCM）6本から、テストが1本も生成されていない）と、
その sub issue の issue #57（ユースケース記述（RUCM）の ABORT と RESUME STEP の使い分けを、既存の12ファイルに当て直す）である。

## 1. 何をするか

**言いたいこと。**記述は実装から逆に起こしたものなので、終わり方も戻り先も実装に答えがある。
代替フローを1本ずつ実装と突き合わせて書き直し、そこから CFG とテストの印を作り直す。
テストは記述ごとのファイルへまとめ直す。テストを持たない記述には、持たない理由を記述の中へ書く。

| 順 | 何をするか | 出どころ |
| --- | --- | --- |
| 1 | 19本の記述の代替フローを、実装を読んで1本ずつ判定し直す | issue #57 の「やること」。人間の指示（[2026-09-07 00:16 (JST)](https://github.com/maimuzo/continuo/issues/57#issuecomment-5560167053)） |
| 2 | 判定の根拠を、判断ログへ実装のファイル名と関数名で書く | issue #57 の受け入れ条件 |
| 3 | `.cfg.json` を作り直す | issue #57 の「進め方」 |
| 4 | 印の付いたテストを、記述ごとのテストファイルへまとめ直し、関数名に記述名と経路の番号を入れる | 人間の指示（[2026-09-07 00:11 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5560140879) と [2026-10-02 10:15 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5943753162)） |
| 5 | テストが1本も無い5本を1本ずつ確かめ、無い理由を記述の中へ書く | issue #110 の「やること1」。人間の指示（[2026-09-06 23:07 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5559756155)） |
| 6 | `[W1]` は警告のままにする（7節） | issue #110 の「やること2」「やること3」 |
| 7 | CI から RUCM の検査を外し、手元の検査として残す | 人間の指示（[2026-09-05 17:35 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5550623226)。「CIではRUCMの更新チェック部分は実施不要」） |

新しいテストは足さない。人間の指示が「効果が薄いなら作らない。GitHub の操作を自動テストへ盛り込みたくない」であるため。

**記述のファイルの分け方。**止まらない段のあとに別の段が続く記述は、2本に分ける（人間の決定。2026-10-02）。
1本に書くと、前の段の結末と後ろの段の結末の掛け算で経路が増えるためである。分けた先は `INCLUDE USE CASE` で引く。
最初の例は `設定ファイルを作る` で、値を決める段を `設定に書く値を gh から引く` へ分けた（8節）。
それ以外は、いまの分け方（利用者が叩くコマンド1つか、常駐プロセスの処理のひとまとまり1つに、記述1本）を保つ。

**直す前に、記述の全部を実装と突き合わせる**（人間の指示。[2026-10-02 12:44 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5945211489)）。
実装を直したのに記述を直し忘れている箇所が在るので、終わり方だけでなく、段・順番・事後条件・根拠資料・図の全部を見る。
2026-10-02 に19本を突き合わせた結果は [impl/issue110_rucm_code_diff.md](impl/issue110_rucm_code_diff.md) に在る。

## 2. 判定のしかた

**言いたいこと。**問いは「実装がそこで何をするか」の1つだけである。記述の中だけで判定しない。
基準は issue #57 の本文のものである。下の表は、その基準を実装の動きの側から引けるように並べ直したものである。

| 実装が何をするか | 記述の書き方 |
| --- | --- |
| その場で処理を打ち切って返る（終了コードを返す、誤りを返して呼び出し元も止まる） | 代替フローにし、`ABORT` で終える |
| 人間の判断を待って止まる | 代替フローにし、`ABORT` で終える。`POSTCONDITION` に、人間が何を見るかを書く |
| やり直す（入力し直させる、待ってから同じ段をもう一度行う） | 代替フローにし、`RESUME STEP <実装がやり直す段>` で終える。CFG では `cycle` になる |
| その1件だけ諦めて先へ進む（値を埋めないまま次の処理を呼ぶ、その issue だけ飛ばす） | 代替フローにし、`RESUME STEP <実装が実際に次に行う段>` で終える |
| 同じ段の並びを、条件が満たされるまで繰り返す | 本線の `DO … UNTIL`。その中の代替フローは `UNTIL` の段へ戻る。CFG では `cycle` になる |
| 本線のどの段からでも割り込み、済んだら元の段へ戻る | 任意時点の代替フロー（`GLOBAL ALTERNATIVE FLOW`）にし、入った段へ `RESUME STEP` で戻る。CFG では `cycle` になる |

本線の `IF … THEN … ELSE … ENDIF` は、どちらの分岐も正常な場合にだけ使う（プラグインの規約 `rucm_structure.md`）。
本線に失敗の扱いが `IF` で書かれているのを見つけたら、代替フローへ出す。

**終わり方のほかに、実装との食い違いを見つけたとき。**

| 見つけたもの | どうするか |
| --- | --- |
| 記述に在る代替フローが実装に無い / 実装に在る失敗の分岐が記述に無い / `RFS` の段や中身が実装と違う | 記述を実装へ合わせて直し、判断ログへ書く |
| mermaid と rucm ブロックが食い違っている | 実装に合っているほうへ揃える |
| 記述が正しく、実装のほうが誤りに見える | 実装は直さない。記述を実装のとおりに書き、見つけたことを issue へ報告する |
| 設計文書の決定と実装が食い違っている | 実装は直さない。記述を実装のとおりに書く。設計文書を直したときは、どの節をどう直したかを issue へ報告する |
| 根拠資料や判断ログの出典が、実在しないファイルや関数を指している | 実在する場所へ直す（例: `設定ファイルを作る` の `runInit` は `cmd/continuo/main.go` ではなく `internal/cli/cli.go` に在る） |

**`cycle` の扱い。**`cycle` は CFG の経路の終わり方の1つで、同じ段をもう一度通ったところで打ち切った経路である。
上の表の「やり直す」「繰り返す」「割り込んで元の段へ戻る」の3つは、正しく書いても `cycle` になる。
直すのは、**実装がやり直しも繰り返しもしないのに、戻り先の番号のせいで `cycle` になっている経路**だけである。
いまの `cycle` 160本のうち、少なくとも74本は正しい（`前提が揃っているかを検査する` の35本は `DO … UNTIL`、
`指示書に沿って issue を1件仕上げる` の36本は任意時点の代替フロー「進捗報告を書く」、残り3本は代替フローを通らない本線だけの経路から出ている）。

`cycle` に出ない誤りもある。実装は先へ進むのに、記述が `ABORT` で止めている場合である。
`RESUME STEP` が1本も無い記述が3本あり、issue #57 の本文は「書き手の癖である可能性が高いので、先に見ること」としている。

**「実際に次に行う段」の決め方。**次の処理を呼んでも、その処理が何もせずに返るなら、そこは戻り先ではない。
`detectProject` は owner が空なら `gh` を叩かずに返り、`detectRepositories` は owner が空かボードの番号が0以下なら `gh` を叩かずに返る。
owner を決められなかったときの戻り先は、ボードを引く段でもリポジトリを引く段でもなく、その先の段である。
こう決めると、実装が通れない組み合わせ（ボードは決まらなかったのにリポジトリは引けた、など）が CFG の経路に出ない。

実例。`設定ファイルを作る` の代替フロー「ボード候補なし」は、段20 の検査から入って `RESUME STEP 20` で同じ検査へ戻る。
実装（`internal/scaffold/detect.go` の `Detect`）は `detectOwner` → `detectProject` → `detectRepositories` を一直線に呼び、
ボードを決められなくても同じ検査へは戻らない。戻り先は、上の決め方で実物を読んで決める。
同じ記述のフローチャート（mermaid）は、既に先の段へ戻る形で描いてある。古いのは rucm ブロックの番号である。

直したあとの見本（段の番号は直すときに実物で決める）。

```
SPECIFIC ALTERNATIVE FLOW ボード候補なし:
RFS BASIC FLOW 20
1. システムは tracker.provider.project_number の値をプレースホルダ 0 のまま残す。
…
6. RESUME STEP <実装が実際に次に行う段>
POSTCONDITION: （いまのまま）
```

**何を読んで判定するか。**根拠は記述ごとに決め、判断ログへ書く。

| 記述の種類 | 根拠にするもの |
| --- | --- |
| continuo の処理を書いた記述（13本） | Go の実装。ファイル名と関数名で書く |
| `continuo を入れる` | `install.sh`。関数名で書く |
| `指示書に沿って issue を1件仕上げる` | 主体はエージェント。動きを決めているのは組み込みの指示書 `internal/prompt/builtin.md` なので、その節番号で書く |
| `ボードを新規に用意する` | 人間が GitHub の画面で行う手順。`README.ja.md` と `docs/trying_it_out.md` の節で書く |
| シナリオ3本（`scenario/`） | 段ごとに、continuo の処理なら Go の実装、人間の操作なら文書 |

判断ログの行の見本。行番号は書かない（`check_reference_format.py` が禁じている）。

```
| 28 | 代替フロー ボード候補なし | ボードを1つ作る案内を記録して RESUME STEP <次の段> | `Detect` は `detectProject` が番号を決められなくても先へ進む。`detectRepositories` は番号が0以下なら何もせずに返る。同じ検査へは戻らない | `internal/scaffold/detect.go` の `Detect` | 95% |
```

**直さないもの。**過去に出た出力の引用（テストの `--- FAIL:` の行など）と、過去の作業の記録（`docs/plans/impl/` と `docs/plans/todo.md`）は、古い名前のまま残す。書き換えると記録が嘘になる。

**`internal/` のコメントを直すとき。**`internal/cli/cli.go` と `internal/daemon/daemon.go` は、hook の挙動を変える変更を検知する網のパスである。
直すのはコメントだけで、挙動は変えない。pull request の本文に、触ったことと挙動が変わらないことを1段落で書く。

`RUCM-PATH` は、作り直す前後の経路の対応表を作ってから貼り直す。sha だけを貼り直すと、検査は通るのに印が別の経路を指す。
対応表は印の付いた経路の分だけを作り、その記述の commit メッセージの本文へ書く。
テストが通っているのに、そのテストが指していた経路が作り直しで消えたときは、先に記述を疑う（実装の動きを記述から落としていないか）。
本当に消えたときだけ印を外し、そのテストは元のファイルに単体テストとして残す。1本が複数に割れた経路は、そのテストが実際に通す段の並びと一致するほうへ付ける。
外した印の数、経路の数と `cycle` の数の前後も、同じ commit メッセージへ書く。手元の絶対パスは書かない。

記述のほかに触るのは次の4つである。

| パス | 何を直すか |
| --- | --- |
| [.github/workflows/ci.yml](../../.github/workflows/ci.yml) | RUCM の検査の step と、それを説明する冒頭のコメントを消す。CI は検査スクリプトを取ってこないので、いまも毎回飛ばしている。消しても CI の挙動は変わらない |
| [scripts/check-rucm.sh](../../scripts/check-rucm.sh) | 「CI でも呼ぶ」「（CI 向け）」の文面を直す。`--strict` を付けない経路は、プラグインを持たない人が手元で叩いたときのために残す |
| [CONTRIBUTING.md](../../CONTRIBUTING.md) | 「外部からの PR では CI が飛ばします」を「CI では行いません」へ直す。あわせて、記述名の付いたテストファイルの決まりを数行足す（下の見本） |
| [docs/plans/continuo_design.md](continuo_design.md) | 節を1つ足し、この計画で決めたこと（テストのファイル名と関数名の形・`[W1]` を警告のままにすること・CI で RUCM を検査しないこと）を書く |

`CONTRIBUTING.md` へ足す文面の見本。

```
`<ユースケース記述の名前>_test.go` という名前のテストファイルは、その記述の経路に対応するテストだけを置く場所です。
関数名は `Test_<記述名>_<経路の番号>_<何を確かめるか>` です。
経路に対応しないテストは、このファイルではなく、同じディレクトリの別のファイルへ足してください。
```

CI が RUCM の検査を走らせると書いている場所は、上の3ファイルだけである。
`git grep -n -E 'check-rucm|CI が飛ばし'` はほかに8ファイル（`docs/releasing.md`・`docs/plans/continuo_design.md`・`docs/plans/` の作業記録3本・記述と判断ログ3本）に当たるが、
どれも手元で叩く話で、CI には触れていない。`go test` の中に sha の一致を見るテストは無い。

CI から外したあとの検査の呼び手は、[docs/releasing.md](../releasing.md) のリリース前の検査（`sh scripts/check-rucm.sh --strict`）と、
記述を直す人が commit の前に叩く分である。前者は既に在るので、足すものは無い。

## 4. 進める順番

**言いたいこと。**1本で形を作り、その1本をコードと突き合わせて出た差分を見てから、残りも同じ確かめをして直す。
形でよいかの人間への確認は、全部を直し終えたあとに1回だけ行う
（人間の指示。[2026-10-02 10:32 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5943915051) と
[2026-10-02 12:44 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5945211489)。後者が「この形で残りへ進めてよいか」は最後に訊くことだと決めた）。
どの1本かは任されている。`設定ファイルを作る` にする。`cycle` の経路がいちばん多く、判定のしかたの効き方がいちばんよく見えるためである。

| 順 | 何をするか |
| --- | --- |
| 1 | `設定ファイルを作る` を直す。記述・判断ログ・CFG・テストのまとめ直しまでを1つの commit にする |
| 2 | `rucm-judge-review` スキルで、この1本の判断ログを確かめる |
| 3 | push し、draft の pull request を作る（CI は pull request でしか走らない。日本語と空白を含むファイル名が ubuntu と macOS で通るかを、ここで確かめる） |
| 4 | この1本を実装と1段ずつ突き合わせ、終わり方のほかの食い違いも直す（8節）。残りの記述も、書いた役とは別の役に実装と突き合わせてもらってから直す |
| 5 | `RESUME STEP` が1本も無い3本を判定する（issue #57 の本文の「先に見ること」） |
| 6 | 戻り先の誤りが `cycle` に出ている残りの記述を直す |
| 7 | そのほかの記述を判定する。変えないものは、変えない理由を判断ログへ書く。テストのまとめ直しは行う |
| 8 | テストが1本も無い5本を確かめ、理由を記述へ書く（5節） |
| 9 | CI から RUCM の検査を外し、設計文書へ節を足し、`CONTRIBUTING.md` を直す |
| 10 | `rucm-judge-review` スキルで全部の判断ログを通して確かめる。経路の数の前後を issue #57 へ報告する |
| 11 | この形でよいかを、決めてほしいことと一緒に、1件のコメントで人間に確認する |

`設定ファイルを作る` で確かめられない形は、次の5つである。残りの記述で確かめた。

- 2つ以上のディレクトリにまたがる記述
- テストが0本の記述の理由の文
- 印が2つ付いた関数
- `DO … UNTIL` と任意時点の代替フローを持つ記述
- 空白を含むファイル名（`設定ファイルを作る_test.go` は空白を含まない。テストを持つ14本のうち7本は含む）。順5 では、空白を含む `再起動して実行中の issue を引き継ぐ` を最初に push して、その CI で確かめる

記述1本ごとに、次を通してから commit する。あわせて `rucm-checker` スキルで、記述と判断ログの両方を機械検証する。

```
mermaid-validate validate-md "docs/spec/usecases/<置き場>/<名前>.rucm.md"
sh scripts/check-rucm.sh --strict
gofmt -l ./cmd ./internal ./test
go vet ./...
go test ./...
```

経路の数と `cycle` の数の前後は、記述ごとに commit メッセージと進捗のコメントへ書く。
経路が掛け算で増えた記述は、止まらない段を別の記述へ分ける（1節。人間の決定）。分けても増えたものは、実装に在る分岐を足した分である。

## 5. テストが1本も無い5本の扱い

issue #110 の本文が挙げた6本のうち、`issue の担当を入札で決める` と `画面に出す文言の言語を決める` は、いまの `main` ではテストを持っている。

## 6. 記述とテストファイルを 1:1 に揃える

**言いたいこと。**別の issue へ分ける合理的な理由は無いので、この issue の中で揃える。
記述の直しで経路の番号が振り直され、どのみち印を全部貼り直す。同じ commit で置き場所と名前も直す。

別の issue へ分ける理由として検討し、成り立たなかったもの。

| 検討した理由 | なぜ成り立たないか |
| --- | --- |
| pull request が大きくなる | 大きさは先送りの理由にならない。記述1本ごとに commit を分ければ読める |
| テストの分け方を先に決める必要がある | 人間が形を決めている（記述と 1:1 のファイル、名前に記述名と経路の番号） |
| Go では1ファイルが1 package にしか入らない | 14本のうち11本は、いまも1つのディレクトリに収まっている（下の表） |

実測は 2026-10-02、commit `6191f31`。印を持つテストファイルは47本、その中の `Test` 関数は579本、`RUCM-PATH` の印は230個である。
印が付いた関数は229本（1つの関数に印が2つ付いた箇所が1つある）、印の無い関数は350本である。
同じ記述の同じ経路を指す印が2個以上ある組が30ある（うち14が `着手を取り消す`）。

| 記述 | いまのファイル数 | ディレクトリ |
| --- | --- | --- |
| issue を1件処理する | 12 | `test/internal/orchestrator` |
| 既存のボードの Status を割り当てる | 7 | `test/internal/cli`・`scaffold`・`setup` の3つ |
| 対象リポジトリを信頼登録する | 4 | `test/internal/trust` |
| 本家のリポジトリへ PR を出す | 3 | `test/internal/orchestrator`・`workspace` の2つ |
| レートリミットで待って再開する / 人間に判断を渡す | 3 / 3 | `test/internal/orchestrator` |
| 前提が揃っているかを検査する | 3 | `test/internal/doctor` |
| worktree と branch を片付ける | 3 | `test/internal/workspace` |
| 再起動して実行中の issue を引き継ぐ | 2 | `test/internal/daemon`・`orchestrator` の2つ |
| 設定ファイルを作る / issue の担当を入札で決める | 2 / 2 | `test/internal/scaffold` / `test/internal/orchestrator` |
| 着手を取り消す / 画面に出す文言の言語を決める / continuo を入れる | 1 / 1 / 1 | `test/internal/abandon` / `test/internal/cli` / `test/install` |

揃えたあとの形。

| 何 | 形 | 例 |
| --- | --- | --- |
| ファイル名 | `<記述のファイル名>_test.go`。その記述のテストがいま在るディレクトリへ、新しく作る | `test/install/continuo を入れる_test.go` |
| ファイルの冒頭 | 1行目に `RUCM-CFG-SHA256` と `SOURCE`。元のファイルが build tag（`//go:build unix` など）を持っていたら持ち越す | |
| 中身 | その記述の、印の付いたテストだけ。そのディレクトリの補助関数は、いまのファイルに残したまま使う | |
| 印 | 同じ経路に複数のテストが付いていることを理由には、減らさない。30組のうち `着手を取り消す` の14組は、設計文書 6-20 の決定（畳んだ条件の真偽の両側を通す）による。残りの16組は、重複を整理することを issue が求めていないので、数を変えない | |
| 関数名 | `Test_<記述名から空白を除いたもの>_<経路の番号>_<何を確かめるか>`。3つ目は、いまの関数名が言っている中身をそのまま使う | `Test_continuoを入れる_P003_releaseから実行ファイルを取って置く` |
| 1つの関数に印が2つ付いたもの（1件） | テストが実際に通している経路を読んで、1つに決める | |
| 印の無い `Test` 関数（350本） | 動かさない | |
| 元のファイル | 印の付いたテストが1本も残らないなら、1行目の印を消す。`Test` 関数も補助関数も残らないなら、ファイルを消す | |
| 2つ以上のディレクトリにまたがる記述（3本） | 寄せない。ディレクトリごとに、同じ名前のファイルを1本ずつ置く。テストは確かめる対象の package と同じ名前のディレクトリに置く決まり（`CONTRIBUTING.md`）と、その補助関数を保つため | `test/internal/daemon/再起動して実行中の issue を引き継ぐ_test.go` と `test/internal/orchestrator/再起動して実行中の issue を引き継ぐ_test.go` |

関数名の3つ目を付けるのは、同じ経路を指すテストが同名になってコンパイルできなくなるのを避けるためである。

日本語と空白を含むファイル名と関数名は、Go 1.26.7 で `go test`・`go test -race`・`go vet`・`gofmt -l` が通ることを 2026-10-02 に試した。
CI（ubuntu と macOS）で通るかは、4節の順3 と順5 で確かめる。

揃ったことの確かめ方。3つとも、動くことを 2026-10-02 に確かめた。並べ替えに `LC_ALL=C` を付けるのは、macOS の `sort` と `uniq` が日本語の違う文字列を同じ行に畳むことがあるためである。

| コマンド | 揃っているときの出力 |
| --- | --- |
| 1つ目。`SOURCE` ごとのファイル数 | 1。ディレクトリをまたぐ3本だけ、またぐディレクトリの数（2か3） |
| 2つ目。ファイル名と `SOURCE` の記述名の一致 | 何も出ない |
| 3つ目。関数名の番号と印の一致 | 何も出ない |

```
git grep -h '"SOURCE"' -- 'test/*.go' | LC_ALL=C sort | LC_ALL=C uniq -c
git -c core.quotepath=false grep -l '"SOURCE"' -- 'test/*.go' | while IFS= read -r f; do s=$(head -5 "$f" | grep -o '[^/]*\.cfg\.json' | head -1); [ "$(basename "$f")" = "${s%.cfg.json}_test.go" ] || echo "名前が違う: $f"; done
git -c core.quotepath=false grep -e '"RUCM-PATH"' -e '^func Test' -- 'test/*.go' | awk -F'\\.go:' '{if($1!=f){f=$1;p=""}} /RUCM-PATH/{match($0,/"P[0-9]+"/); p=substr($0,RSTART+1,RLENGTH-2); next} /:func Test/{if(p!=""){if(index($0,"_" p "_")==0) print "番号が違う: " p " " $0; p=""}}'
```

## 7. `[W1]` を警告のままにする理由

**言いたいこと。**issue #110 の「やること2」（`[W1]` を落とす理由にするか）と「やること3」（一部だけ未生成の記述をどう扱うか）への答えは、どちらも「警告のまま」である。

| 案 | 採るか | 理由 |
| --- | --- | --- |
| 落とす理由にする | 採らない | 経路688本のうち印が付いているのは165本である。落とすと、GitHub の操作を含む経路にもテストを書かないと検査が通らなくなる。人間の指示（GitHub の操作を自動テストへ盛り込みたくない）に反する |
| 数を上限にする | 採らない | `scripts/check-rucm.sh` の側で数える仕組みを足すことになる。issue も人間も、新しい仕組みを求めていない。上限の数を誰がいつ見直すかも決める必要が出る |
| 警告のままにする | 採る | テストは経路の全部に1本ずつは書かない方針で書かれている（`test/internal/scaffold/` のテストの冒頭に「終端フローごとに代表を1本ずつ対応づける」とある） |

**限界。**`[W1]` は、理由を書いてテストを持たない記述と、書き忘れた記述を見分けない。
見分けるのは人間で、記述の冒頭に 5節の形の理由が在るかを読む。issue #110 の題が言う「気づけない」は、この分だけ残る。
