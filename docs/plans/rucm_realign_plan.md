# ユースケース記述（RUCM）を実装に合わせ直す計画

対象は issue #110（ユースケース記述（RUCM）6本から、テストが1本も生成されていない）と、
その sub issue の issue #57（ユースケース記述（RUCM）の ABORT と RESUME STEP の使い分けを、既存の12ファイルに当て直す）である。

## 1. 何をするか

**言いたいこと。**記述は実装から逆に起こしたものなので、終わり方も戻り先も実装に答えがある。
代替フローを1本ずつ実装と突き合わせて書き直し、そこから CFG とテストの印を作り直す。
テストは記述1本につきテストファイル1本へまとめ直す。テストを持たない記述には、持たない理由を記述の中へ書く。

| 順 | 何をするか | どの issue の求めか |
| --- | --- | --- |
| 1 | 19本の記述の代替フローを、実装を読んで1本ずつ判定し直す | issue #57 の「やること」 |
| 2 | 判定の根拠を、判断ログへ実装のファイル名と関数名で書く | issue #57 の受け入れ条件 |
| 3 | `.cfg.json` を作り直し、既存テストの `RUCM-CFG-SHA256` と `RUCM-PATH` を貼り直す | issue #57 の「進め方」 |
| 4 | 印の付いたテストを、記述1本につきテストファイル1本へまとめ直し、関数名に経路の番号を入れる | 人間の指示（2026-09-07 と 2026-10-02） |
| 5 | テストが1本も無い5本に、無い理由を記述の中へ書く。書ける経路にはテストを書く | issue #110 の「やること1」と人間の指示 |
| 6 | `[W1]` は警告のままにする | issue #110 の「やること2」「やること3」 |
| 7 | CI から RUCM の検査を外し、手元の検査として残す | 人間の指示 |

## 2. 判定のしかた

**言いたいこと。**問いは「実装がそこで何をするか」の1つだけである。記述の中だけで判定しない。

| 実装が何をするか | 記述の書き方 |
| --- | --- |
| その場で処理を打ち切って返る（終了コードを返す、関数から誤りを返して呼び出し元も止まる） | 代替フローにし、`ABORT` で終える |
| やり直して本線の途中へ戻る（入力し直させる、待ってから同じ段をもう一度行う） | 代替フローにし、`RESUME STEP <実装が戻る段>` で終える |
| 止まりも戻りもせず、値が埋まらないまま次の処理へ進む | 代替フローにしない。本線の中に `IF … THEN … ELSE … ENDIF` で書く |

3行目が、これまで見落としていた形である。実例は [internal/scaffold/detect.go:168-182](../../internal/scaffold/detect.go#L168-L182) で、
`detectOwner` → `detectProject` → `detectRepositories` を一直線に呼び、どれが失敗しても次を呼ぶ。
記述はこれを `RESUME STEP 20` で戻る代替フローとして書いており、160経路のうち69経路が終端しない。

判断ログの根拠欄には、実装のファイル名と関数名を書く。行番号は書かない（`check_reference_format.py` が禁じている）。

## 3. どのファイルを触るか

**言いたいこと。**19本すべてを判定する。直す量が多いのは、終端しない経路を持つ10本である。

実測は 2026-10-02、commit `6191f31`（`main` と同じ内容）。

| 記述 | 代替フロー | ABORT | RESUME | 経路 | 終端しない経路 | 印の付いた経路 |
| --- | --- | --- | --- | --- | --- | --- |
| 設定ファイルを作る | 14 | 6 | 8 | 160 | 69 | 5 |
| 指示書に沿って issue を1件仕上げる | 10 | 2 | 8 | 74 | 36 | 0 |
| 前提が揃っているかを検査する | 10 | 5 | 5 | 177 | 35 | 13 |
| issue を1件処理する | 36 | 27 | 9 | 43 | 8 | 31 |
| 既存のボードの Status を割り当てる | 9 | 7 | 2 | 11 | 3 | 11 |
| issue を着手から片付けまで見届ける | 3 | 0 | 3 | 4 | 3 | 0 |
| レートリミットで待って再開する | 8 | 6 | 2 | 11 | 2 | 8 |
| はじめて continuo を動かせるようにする | 6 | 5 | 1 | 13 | 2 | 0 |
| ボードを新規に用意する | 6 | 5 | 1 | 11 | 1 | 0 |
| 対象リポジトリを信頼登録する | 5 | 4 | 1 | 6 | 1 | 6 |
| 残り9本 | 84 | 72 | 12 | 178 | 0 | 91 |
| 合計 | 191 | 139 | 52 | 688 | 160 | 165 |

記述1本につき、次の4種類のファイルを1つの commit で直す（issue #57 の「進め方」）。

| 種類 | パス | 何を直すか |
| --- | --- | --- |
| 記述 | `docs/spec/usecases/<置き場>/<名前>.rucm.md` | rucm ブロックの代替フローと、mermaid の2ブロック |
| 判断ログ | `docs/spec/usecases/<置き場>/<名前>.judge_log.md` | 終わり方の判断の行。根拠を実装の関数名で書く |
| CFG | `docs/spec/usecases/<置き場>/<名前>.cfg.json` | `rucm_to_cfg.py` で作り直す。手では書かない |
| テスト | その記述を `SOURCE` に持つ `test/` のファイル | 1行目の `RUCM-CFG-SHA256` と、各テストの `RUCM-PATH` |

`RUCM-PATH` は、作り直す前後の経路の対応表を作ってから貼り直す。sha だけを貼り直すと、検査は通るのに印が別の経路を指す。

記述のほかに触るのは次の4つである。

| パス | 何を直すか |
| --- | --- |
| [.github/workflows/ci.yml](../../.github/workflows/ci.yml) | RUCM の検査の step と、それを説明する冒頭のコメントを消す |
| [scripts/check-rucm.sh](../../scripts/check-rucm.sh) | 「CI でも呼ぶ」「（CI 向け）」の文面を直す |
| [CONTRIBUTING.md](../../CONTRIBUTING.md) | 「外部からの PR では CI が飛ばします」を「CI では行いません」へ直す |
| `test/` に新しく足すテスト | `はじめて continuo を動かせるようにする` の「Go の版が古い」経路。ほかに書ける経路が出たら足す |

## 4. 進める順番

**言いたいこと。**1本で形を作ってから残りへ広げる。最初の1本は `設定ファイルを作る` にする。

| 順 | 何をするか |
| --- | --- |
| 1 | `設定ファイルを作る` を直す。経路の数と終端しない経路の数を、直す前後で測って issue #57 へ報告する |
| 2 | 終端しない経路を持つ残り9本を、多い順に直す |
| 3 | 終端しない経路を持たない9本を判定する。変えないものは、変えない理由を判断ログへ書く |
| 4 | 記述ごとにテストファイルを1本へまとめ直す（6節）。記述の直しが全部終わり、経路の番号が動かなくなってから行う |
| 5 | テストが1本も無い5本に、無い理由を記述へ書く。書ける経路のテストを書く |
| 6 | CI から RUCM の検査を外す |

1本ごとに `sh scripts/check-rucm.sh --strict` と `go test ./...` を通してから commit する。

## 5. テストが1本も無い5本の扱い

**言いたいこと。**新しくテストを書く効果は薄い。理由は5本それぞれ違うので、1本ずつ別の文で書く。

| 記述 | 記述の中へ書く理由 |
| --- | --- |
| はじめて continuo を動かせるようにする | 段の大半は `test/e2e/walkthrough_test.go` が偽の `gh` で通している。この記述の印は付けていない |
| issue を着手から片付けまで見届ける | 同じ e2e が通している |
| 夜に機械を落として翌朝に担当を続ける | 担当を外すかどうかの判定は `test/internal/handoff/` が検査している |
| ボードを新規に用意する | continuo に機能が無い（記述が既にそう書いている） |
| 指示書に沿って issue を1件仕上げる | 主体がエージェントで、`claude -p` が禁止されている（判断ログに既にある） |

上の表の「どのテストが通しているか」は、2026-09-06 に敵対的レビュワーが挙げたものである。段4 で1本ずつ実物に当て直してから書く。

## 6. 記述とテストファイルを 1:1 に揃える

**言いたいこと。**別の issue へ分ける合理的な理由は無いので、この issue の中で揃える。
記述の直しで経路の番号が振り直され、どのみち印を全部貼り直す。そのときに置き場所と名前も直せば、貼り直しが1回で済む。

別の issue へ分ける理由として検討し、成り立たなかったもの。

| 検討した理由 | なぜ成り立たないか |
| --- | --- |
| pull request が大きくなる | 大きさは先送りの理由にならない。記述1本ごとに commit を分ければ読める |
| テストの分け方を先に決める必要がある | 人間が形を決めている（記述と 1:1 のファイル、名前に記述名と経路の番号） |
| Go では1ファイルが1 package にしか入らない | 14本のうち11本は、いまも1つのディレクトリに収まっている（下の表） |

実測は 2026-10-02、commit `6191f31`。印を持つテストファイルは47本、その中の `Test` 関数は579本、`RUCM-PATH` の印は230個である。

| 記述 | いまのファイル数 | ディレクトリ |
| --- | --- | --- |
| issue を1件処理する | 12 | `test/internal/orchestrator` |
| 既存のボードの Status を割り当てる | 7 | `test/internal/cli`・`scaffold`・`setup` の3つ |
| 対象リポジトリを信頼登録する | 4 | `test/internal/trust` |
| 本家のリポジトリへ PR を出す | 3 | `test/internal/orchestrator`・`workspace` の2つ |
| レートリミットで待って再開する / 人間に判断を渡す | 3 / 3 | `test/internal/orchestrator` |
| 前提が揃っているかを検査する | 3 | `test/internal/doctor` |
| worktree と branch を片付ける | 3 | `test/internal/workspace` |
| 再起動して実行中の issue を引き継ぐ | 2 | `test/internal/daemon`・`orchestrator` の2つ |
| 設定ファイルを作る / issue の担当を入札で決める | 2 / 2 | `test/internal/scaffold` / `test/internal/orchestrator` |
| 着手を取り消す / 画面に出す文言の言語を決める / continuo を入れる | 1 / 1 / 1 | `test/internal/abandon` / `test/internal/cli` / `test/install` |

揃えたあとの形。

| 何 | 形 | 例 |
| --- | --- | --- |
| ファイル名 | `<記述のファイル名>_test.go`。その記述のテストがいま在るディレクトリへ置く | `test/install/continuo を入れる_test.go` |
| 1行目 | いまと同じ `RUCM-CFG-SHA256` と `SOURCE` | 変えない |
| 関数名 | `Test_<記述名から空白を除いたもの>_<経路の番号>` | `Test_continuoを入れる_P003` |
| 関数の直前 | いまと同じ `RUCM-PATH` の印と、いまの関数名が言っていた中身を1行のコメントで残す | `// release から実行ファイルを取って置く` |
| 印の無い `Test` 関数（349本） | 動かさない。経路に対応しない単体テストなので、いまのファイルに残す | |

日本語と空白を含むファイル名と関数名は、Go 1.26.7 で `go test` と `go vet` が通ることを 2026-10-02 に試した。

2つ以上のディレクトリにまたがる3本は、印の付いたテストがいちばん多いディレクトリへ寄せる。
寄せるテストが元のディレクトリの `helpers_test.go` を使っているかは、段4 で1本ずつ読んで確かめる。

## 7. 決まっていないこと

| 何 | 何が分かれば決まるか |
| --- | --- |
| 直したあとの経路の数 | 1本ずつ作り直して測る。`設定ファイルを作る` は本線の `IF` に書き直すので、前に測った568本とは別の数になる |
| またがる3本のテストを1つのディレクトリへ寄せられるか | 段4 で、寄せるテストが使っている補助関数を読む。寄せられないものが出たら、その理由を記述へ書いて報告する |
