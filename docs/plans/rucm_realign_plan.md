# ユースケース記述（RUCM）を実装に合わせ直す計画

対象は issue #110（ユースケース記述（RUCM）6本から、テストが1本も生成されていない）と、
その sub issue の issue #57（ユースケース記述（RUCM）の ABORT と RESUME STEP の使い分けを、既存の12ファイルに当て直す）である。

## 1. 何をするか

**言いたいこと。**記述は実装から逆に起こしたものなので、終わり方も戻り先も実装に答えがある。
代替フローを1本ずつ実装と突き合わせて書き直し、そこから CFG とテストの印を作り直す。
テストは記述1本につきテストファイル1本へまとめ直す。テストを持たない記述には、持たない理由を記述の中へ書く。

| 順 | 何をするか | 出どころ |
| --- | --- | --- |
| 1 | 19本の記述の代替フローを、実装を読んで1本ずつ判定し直す | issue #57 の「やること」。人間の指示（[2026-09-07 00:16 (JST)](https://github.com/maimuzo/continuo/issues/57#issuecomment-5560167053)） |
| 2 | 判定の根拠を、判断ログへ実装のファイル名と関数名で書く | issue #57 の受け入れ条件 |
| 3 | `.cfg.json` を作り直す | issue #57 の「進め方」 |
| 4 | 印の付いたテストを、記述1本につきテストファイル1本へまとめ直し、関数名に経路の番号を入れる | 人間の指示（[2026-09-07 00:11 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5560140879) と [2026-10-02 10:17 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5943753162)） |
| 5 | テストが1本も無い5本を1本ずつ確かめ、無い理由を記述の中へ書く | issue #110 の「やること1」。人間の指示（[2026-09-06 23:07 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5559756155)） |
| 6 | `[W1]` は警告のままにする（7節） | issue #110 の「やること2」「やること3」 |
| 7 | CI から RUCM の検査を外し、手元の検査として残す | 人間の指示（[2026-09-05 17:35 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5550623226)。「CIではRUCMの更新チェック部分は実施不要」） |

新しいテストは足さない。人間の指示が「効果が薄いなら作らない。GitHub の操作を自動テストへ盛り込みたくない」であるため。

## 2. 判定のしかた

**言いたいこと。**問いは「実装がそこで何をするか」の1つだけである。記述の中だけで判定しない。
基準は issue #57 の本文のものをそのまま使う。新しい基準は足さない。

| 実装が何をするか | 記述の書き方 |
| --- | --- |
| その場で処理を打ち切って返る（終了コードを返す、誤りを返して呼び出し元も止まる、人間の判断を待って止まる） | 代替フローにし、`ABORT` で終える |
| やり直す（入力し直させる、待ってから同じ段をもう一度行う） | 代替フローにし、`RESUME STEP <実装がやり直す段>` で終える。CFG では `cycle` になる |
| その1件だけ諦めて先へ進む（値を埋めないまま次の処理を呼ぶ、その issue だけ飛ばす） | 代替フローにし、`RESUME STEP <実装が次に行う段>` で終える。CFG では `end` か `abort` になる |

本線の `IF … THEN … ELSE … ENDIF` は、どちらの分岐も正常な場合にだけ使う（プラグインの規約 `rucm_structure.md`）。失敗の扱いを本線へ入れない。

**`cycle` の扱い。**`cycle` は CFG の経路の終わり方の1つで、同じ段をもう一度通ったところで打ち切った経路である。
実装が本当にやり直すなら正しい。実装がやり直さないのに `cycle` になっているなら、戻り先の番号が誤っている。
目標は `cycle` を0本にすることではなく、**実装がやり直さないのに `cycle` になっている経路を0本にすること**である。

実例。`設定ファイルを作る` の代替フロー「ボード候補なし」は、段20 の検査から入って `RESUME STEP 20` で同じ検査へ戻る。
実装（`internal/scaffold/detect.go` の `Detect`）は `detectOwner` → `detectProject` → `detectRepositories` を一直線に呼び、
ボードを決められなくても `detectRepositories` へ進む。戻り先は、ボードを決める段のあとの段が正しい。

直したあとの見本（段の番号は直すときに実物で決める）。

```
SPECIFIC ALTERNATIVE FLOW ボード候補なし:
RFS BASIC FLOW 20
1. システムは tracker.provider.project_number の値をプレースホルダ 0 のまま残す。
…
6. RESUME STEP <対象リポジトリを引く段>
POSTCONDITION: （いまのまま）
```

**何を読んで判定するか。**根拠は記述ごとに決め、判断ログへ書く。

| 記述の種類 | 根拠にするもの |
| --- | --- |
| continuo の処理を書いた記述（15本） | Go の実装。ファイル名と関数名で書く |
| `指示書に沿って issue を1件仕上げる` | 主体はエージェント。動きを決めているのは組み込みの指示書 `internal/prompt/builtin.md` なので、その節番号で書く |
| `ボードを新規に用意する` | 人間が GitHub の画面で行う手順。`README.ja.md` と `docs/trying_it_out.md` の節で書く |
| シナリオ3本（`scenario/`） | 段ごとに、continuo の処理なら Go の実装、人間の操作なら文書 |

判断ログの行の見本。行番号は書かない（`check_reference_format.py` が禁じている）。

```
| 28 | 代替フロー ボード候補なし | ボードを1つ作る案内を記録して RESUME STEP <次の段> | `Detect` は `detectProject` が番号を決められなくても `detectRepositories` を呼ぶ。同じ検査へは戻らない | `internal/scaffold/detect.go` の `Detect` | 95% |
```

| 設計文書 | `docs/plans/continuo_design.md` の 6-17・6-18・6-19 | 代替フローの本数が変わったら、本数を直す |

`RUCM-PATH` は、作り直す前後の経路の対応表を作ってから貼り直す。sha だけを貼り直すと、検査は通るのに印が別の経路を指す。
対応表は、その記述の commit メッセージの本文へ書く（実装レビューが、印の指す先を確かめられるようにするため）。
作り直しで消えた経路を指していた印は外す。1本が複数に割れた経路は、テストが通っているほうへ付ける。

記述のほかに触るのは次の3つである。

| パス | 何を直すか |
| --- | --- |
| [.github/workflows/ci.yml](../../.github/workflows/ci.yml) | RUCM の検査の step と、それを説明する冒頭のコメントを消す。CI は検査スクリプトを取ってこないので、いまも毎回飛ばしている。消しても CI の挙動は変わらない |
| [scripts/check-rucm.sh](../../scripts/check-rucm.sh) | 「CI でも呼ぶ」「（CI 向け）」の文面を直す。`--strict` を付けない経路は、プラグインを持たない人が手元で叩いたときのために残す |
| [CONTRIBUTING.md](../../CONTRIBUTING.md) | 「外部からの PR では CI が飛ばします」を「CI では行いません」へ直す |

## 4. 進める順番

**言いたいこと。**1本で形を全部作り、人間の確認を受けてから残りへ広げる。最初の1本は `設定ファイルを作る` にする
（人間の指示。[2026-10-02 10:32 (JST)](https://github.com/maimuzo/continuo/issues/110#issuecomment-5943915051)）。

| 順 | 何をするか |
| --- | --- |
| 1 | `設定ファイルを作る` を直す。記述・判断ログ・CFG・テストのまとめ直しまでを1つの commit にする |
| 2 | 経路の数と `cycle` の数を直す前後で測り、issue #57 へ報告する。push して、この形で残りへ進めてよいかを人間に確認する |
| 3 | 了承のあと、`cycle` の経路を持つ残り9本を、多い順に直す |
| 4 | `cycle` の経路を持たない9本を判定する。変えないものは、変えない理由を判断ログへ書く。テストのまとめ直しは行う |
| 5 | テストが1本も無い5本を確かめ、理由を記述へ書く（5節） |
| 6 | CI から RUCM の検査を外す |
| 7 | `rucm-judge-review` スキルで19本の判断ログを通して確かめる。19本の経路の数の前後を issue #57 へ報告する |

記述1本ごとに、次の4つを通してから commit する。

```
mermaid-validate validate-md "docs/spec/usecases/<置き場>/<名前>.rucm.md"
sh scripts/check-rucm.sh --strict
gofmt -l ./cmd ./internal ./test
go test ./...
```

記述を直すと、テストのまとめ直しも同じ commit に入るので、印の貼り直しは記述1本につき1回で済む。

## 5. テストが1本も無い5本の扱い

**言いたいこと。**新しいテストは書かない。1本ずつ実物で確かめ、結果で2つに分ける。

issue #110 の本文が挙げた6本のうち、`issue の担当を入札で決める` と `画面に出す文言の言語を決める` は、いまの `main` ではテストを持っている。
いまテストが0本なのは、下の5本である。

| 確かめた結果 | どうするか |
| --- | --- |
| その記述の経路を、最初から最後まで通しているテストが既に在る | そのテストを 6節の形のファイルへ移し、印を付ける。「テストが無い」のではなく「印が無い」だったことになる |
| 在らない | 無い理由を記述の冒頭へ書く。テストは足さない |

| 記述 | 確かめる相手（2026-09-06 に敵対的レビュワーが挙げたもの。当て直す前） |
| --- | --- |
| はじめて continuo を動かせるようにする | `test/e2e/walkthrough_test.go`（偽の `gh` で通している） |
| issue を着手から片付けまで見届ける | 同じ e2e |
| 夜に機械を落として翌朝に担当を続ける | `test/internal/handoff/` |
| ボードを新規に用意する | continuo に機能が無い。記述の冒頭に、既に理由が書いてある |
| 指示書に沿って issue を1件仕上げる | 主体がエージェントで、`claude -p` が禁止されている。記述に既に理由が書いてある |

理由の文の見本（`ボードを新規に用意する.rucm.md` の冒頭に在る先例と同じ形にする）。

```
> **この記述からテストコードは作らない。**
> <なぜ作らないか。1〜2文>
> `check_update_tests.py` が出す `[W1]`（テスト未生成パス）は、ここでは想定どおりである。
```

rucm ブロックの外へ書くので、CFG と sha は動かない。

## 6. 記述とテストファイルを 1:1 に揃える

**言いたいこと。**別の issue へ分ける合理的な理由は無いので、この issue の中で揃える。
記述の直しで経路の番号が振り直され、どのみち印を全部貼り直す。同じ commit で置き場所と名前も直す。

別の issue へ分ける理由として検討し、成り立たなかったもの。

| 検討した理由 | なぜ成り立たないか |
| --- | --- |
| pull request が大きくなる | 大きさは先送りの理由にならない。記述1本ごとに commit を分ければ読める |
| テストの分け方を先に決める必要がある | 人間が形を決めている（記述と 1:1 のファイル、名前に記述名と経路の番号） |
| Go では1ファイルが1 package にしか入らない | 14本のうち11本は、いまも1つのディレクトリに収まっている（下の表） |

実測は 2026-10-02、commit `6191f31`。印を持つテストファイルは47本、その中の `Test` 関数は579本、`RUCM-PATH` の印は230個である。
印が付いた関数は229本（1つの関数に印が2つ付いた箇所が1つある）、印の無い関数は350本である。
同じ記述の同じ経路を指す印が2個以上ある組が34ある。

| 記述 | いまのファイル数 | ディレクトリ |
| --- | --- | --- |
| issue を1件処理する | 12 | `test/internal/orchestrator` |
| 既存のボードの Status を割り当てる | 7 | `test/internal/cli`・`scaffold`・`setup` の3つ |
| 対象リポジトリを信頼登録する | 4 | `test/internal/trust` |
| 本家のリポジトリへ PR を出す | 3 | `test/internal/orchestrator`・`workspace` の2つ |
| レートリミットで待って再開する / 人間に判断を渡す | 3 / 3 | `test/internal/orchestrator` |
| 前提が揃っているかを検査する | 3 | `test/internal/doctor` |
| worktree と branch を片付ける | 3 | `test/internal/workspace` |
| 再起動して実行中の issue を引き継ぐ | 2 | `test/internal/daemon`・`orchestrator` の2つ |
| 設定ファイルを作る / issue の担当を入札で決める | 2 / 2 | `test/internal/scaffold` / `test/internal/orchestrator` |
| 着手を取り消す / 画面に出す文言の言語を決める / continuo を入れる | 1 / 1 / 1 | `test/internal/abandon` / `test/internal/cli` / `test/install` |

揃えたあとの形。

| 何 | 形 | 例 |
| --- | --- | --- |
| ファイル名 | `<記述のファイル名>_test.go`。その記述のテストがいま在るディレクトリへ置く | `test/install/continuo を入れる_test.go` |
| 1行目 | `RUCM-CFG-SHA256` と `SOURCE`。その記述を `SOURCE` に持つファイルは、この1本だけにする | |
| 印 | 1つの経路につき1本のテストにだけ付ける（設計文書 6-18e の決定を19本へ当てる）。付けるのは、その経路の `POSTCONDITION` を確かめているテスト | |
| 関数名 | `Test_<記述名から空白を除いたもの>_<経路の番号>` | `Test_continuoを入れる_P003` |
| 関数の直前 | `RUCM-PATH` の印と、いまの関数名が言っていた中身を1行のコメントで残す | `// release から実行ファイルを取って置く` |
| 同じ経路を指していた残りのテスト | 印を外し、名前を変えず、いまのファイルに単体テストとして残す | |
| 1つの関数に印が2つ付いたもの（1件） | テストが実際に通している経路を読んで、1つに決める | |
| 印の無い `Test` 関数（350本） | 動かさない | |
| 印の付いたテストが無くなった元のファイル | 1行目の印を消す。`Test` 関数が1本も残らないなら、ファイルごと `git mv` で新しい名前にする | |

日本語と空白を含むファイル名と関数名は、Go 1.26.7 で `go test`・`go test -race`・`go vet`・`gofmt -l` が通ることを 2026-10-02 に試した。
CI（ubuntu と macOS）で通るかは、最初の1本を push したときの CI で確かめる。

2つ以上のディレクトリにまたがる3本は、印を付ける1本ずつを読み、印の付いたテストがいちばん多いディレクトリへ寄せる。
寄せるテストが、元のディレクトリにしか無い補助関数を使っていて寄せられないときは、
ディレクトリごとに同じ名前のファイルを1本ずつ置き、そうなった記述と理由を issue へ報告する。

揃ったことの確かめ方。`SOURCE` ごとのファイル数を数え、1を超える記述が上の受け皿の分だけであることを見る。

```
git grep -h '"SOURCE"' -- 'test/*.go' | sort | uniq -c
```

## 7. `[W1]` を警告のままにする理由

**言いたいこと。**issue #110 の「やること2」（`[W1]` を落とす理由にするか）と「やること3」（一部だけ未生成の記述をどう扱うか）への答えは、どちらも「警告のまま」である。

| 案 | 採るか | 理由 |
| --- | --- | --- |
| 落とす理由にする | 採らない | 経路688本のうち印が付いているのは165本である。落とすと、GitHub の操作を含む経路にもテストを書かないと検査が通らなくなる。人間の指示（GitHub の操作を自動テストへ盛り込みたくない）に反する |
| 数を上限にする | 採らない | 上限の数を誰がいつ見直すかの仕組みが要る。検査スクリプトはプラグインの側に在り、このリポジトリからは変えられない |
| 警告のままにする | 採る | テストは「終端フローごとに代表を1本」で書かれており（`test/internal/scaffold/scaffold_test.go` の冒頭のコメント）、経路の全部に1本ずつは書かない |

**限界。**`[W1]` は、理由を書いてテストを持たない記述と、書き忘れた記述を見分けない。
見分けるのは人間で、記述の冒頭に 5節の形の理由が在るかを読む。

## 8. 決まっていないこと

| 何 | 何が分かれば決まるか |
| --- | --- |
| 直したあとの経路の数 | 1本ずつ作り直して測る。最初の1本の結果を人間へ報告する |
| またがる3本のテストを1つのディレクトリへ寄せられるか | 順3・順4 で、寄せるテストが使っている補助関数を読む |
| テストが0本の5本のうち、通しているテストが既に在るもの | 順5 で実物を読む |
