### 1-1. 見出しの数え方と、issue 本文の「91件」との関係

**言いたいこと。**`^###` は `^####` も、コードブロックの中のシェルのコメントも拾う。
**目次を作る側は、それを見出しと数えてはならない。**

**issue 本文は `### は91件` と書いている。これは `^###` が `^####` も拾った数である**（86 + 5 = 91）。
**矛盾していない。**あわせて `^#` は**コードブロックの中のシェルのコメントも拾う**（7行）。

```

### 1-2. anchor（リンクの飛び先の id）は、GitHub の描画から取る

**言いたいこと。**slug の規則を推測すると必ず外れる。`?ref={branch}` を落とすと既定 branch を測る。

**自分で slug の規則を実装しない。**日本語・全角の括弧・`✗`・`…`・バッククォートが混ざるので、
**規則を推測すると必ず外れる。**

```bash
gh api "repos/{owner}/{repo}/contents/docs/FAQ.md?ref={branch}" \
  -H 'Accept: application/vnd.github.html' \
  | grep -o 'id="user-content-[^"]*"'
```

**これは GitHub の画面と同じ描画器の出力である。**98件返り、`user-content-` を外したものが
markdown から `#…` で飛べる id である。

**`{owner}` `{repo}` `{branch}` は gh が手元のリポジトリの値へ置き換える。**実測した。

```
$ gh api "repos/{owner}/{repo}/contents/docs/FAQ.md?ref={branch}" -H 'Accept: application/vnd.github.html'
{"message":"No commit found for the ref continuo/maimuzo/continuo/213", …}
```

**返っているのは「その branch がまだ push されていない」というエラーであり、3つとも置換が効いた証拠である。**

**`?ref={branch}` を落としてはならない。**落とすと、この API は**既定 branch を描画する。**
すると、**見出しを足した人が push して叩いたときに、新しい見出しはまだ既定 branch に無いので偽の失敗が出る。**
逆に**見出しを消したときは、既定 branch にまだ在るので偽の合格になる。**

例（実物）。

| 見出し | GitHub が付けた id |
| --- | --- |
| `### 版を上げたら「progress_interval_ms の値 3600000 が不正です」で起動しなくなった` | `版を上げたらprogress_interval_ms-の値-3600000-が不正ですで起動しなくなった` |
| `### \`✗ clone  ghq が PATH にありません\`` | `-clone--ghq-が-path-にありません` |

## 2. GitHub の自動目次が、実際にどうなっているか

**言いたいこと。**GitHub が返す HTML に目次の中身は1文字も入っておらず、ボタンは押されていない状態で届く。
**「押すまで気づけない」は、これで実測になった。**

**issue が「実際の GitHub の画面で両方を見てから決めること」と書いている。**
**Claude in Chrome はこのセッションで権限を拒否されたので、画面は開いていない。**
**代わりに、GitHub が返す HTML そのものを取って測った。**

```bash
curl -sL https://github.com/<owner>/<repo>/blob/main/docs/FAQ.md
```

| 何 | 実測 |
| --- | --- |
| Outline の実体 | **`<button data-component="IconButton" … TableOfContents-module__IconButton …>`。**ラベルは tooltip の `Outline` だけ |
| その class が HTML に出てくる回数 | **1回。**パネル本体の markup は1つも無い |
| ボタンの初期状態 | **`aria-pressed="false"`** |
| 目次の中身（見出しへの `href="#…"`）が描かれているか | **0件** |
| 本文の見出しの id | **196回**（98個 × 2。`id=` と anchor の `href=`） |
| 中身（押したときに出るもの） | **h1〜h4 の98項目を、階層のまま全部**（blob ページに埋まっている `"toc"` から） |
| 維持の手間 | **ゼロ。**見出しを足せば勝手に追随する |

**GitHub が返す HTML の中に、目次の中身は1文字も入っていない。ボタンは押されていない状態で届く。**
**これが「押すまで気づけない」の実測である。**

**issue が「長すぎて読めない」と心配した91項目は、GitHub の自動目次では既に98項目として起きている。**
**書く側は97項目**（6 + 86 + 5）**で、98との差は h1（`# よくある質問`。文書の題名であって節ではない）だけである。**
**つまり、短さで勝負にはならない。書く価値があるのは、置き場所が違うからである。**ページを開いた瞬間に目に入る。

## 3. 決めたこと

**言いたいこと。**先頭に入れ子の箇条書きの目次を書く。節の並べ替えは要らない。
目次の中に見出しを作らない。検算のコマンドは出荷しない。

### 3-1. 自動目次に任せるのではなく、ファイルの先頭に書く。両方が並び立つ

**言いたいこと。**自動目次は消せないので、決めるのは「書くか / 書かないか」だけである。書く。

**自動目次は消せないので、「両方」になる。**決めるのは「書くか / 書かないか」だけである。

| どうするか | 選ぶと利用者に起きること | 選ばないと続くこと |
| --- | --- | --- |
| **ファイルの先頭に目次を書く（採る）** | **ページを開いた瞬間に、6つの症状の区分と91個の見出しが目に入る** | **`aria-pressed="false"` のボタンを押すことを知らない人は、2522行をめくって探し続ける** |
| 自動目次だけに任せる（採らない） | 何もしなくてよい | 同上。**issue が「メニューを開くまで気づけない」と名指しした状態がそのまま残る** |

### 3-2. 節の並べ替えは要らない。既に6つに分かれている

**言いたいこと。**issue が条件付きで挙げた作業だが、条件が成り立たない。数えて確かめた。

**issue の「あわせて考えること」は「`##` の大見出しでグループ分けされているかを確かめ、
分かれていなければ先に節の並べ替えが要る」と条件付きで書いている。****確かめた。分かれている。**

| `##` の大見出し | その下の `###` の数 |
| --- | --- |
| 起動できないとき | 10 |
| doctor が通らないとき | 18 |
| issue が動かないとき | 34 |
| 片付けたいとき | 13 |
| 気にしなくてよいもの | 4 |
| 使い方が分からないとき | 7 |

**したがって、この issue の範囲は「目次を付ける」のままでよい。**
**節の並べ替えも、別の issue への切り出しも行わない。**

### 3-3. `####` の5個も目次に載せる

**言いたいこと。**issue が例に挙げた節が `####` だからである。`###` だけに絞ると、その節が漏れる。

**載せる理由は、issue 本文が自分で挙げた例がそれだからである。**

> この文書には「担当している PC が壊れたとき」「チームで、issue ごとに担当の PC を決めたい」のような、
> 他のどこにも書いていない手順が入っている。

**「担当している PC が壊れたとき」は `####` である**（`### 同じ GitHub アカウントで、複数の PC を動かしたい` の1つ前、
`### チームで、issue ごとに担当の PC を決めたい` の下）。
**`###` だけに絞ると、issue が「辿り着けなくて困る」と名指しした節が、目次に載らない。**

**行番号では指さない。**この変更が目次を先頭へ足すので、**その行番号は書いた直後にずれる。**

### 3-4. 目次の中に見出しを作らない。入れ子の箇条書き1つにする

**言いたいこと。**同じ文言の見出しが2つになると、GitHub が後のほうの id に `-1` を付け、
**本文側の id が変わる。**外から貼られたリンクの飛び先が目次へ移る。

**これは壊れ方の話である。**目次の区分けを `### 起動できないとき` のように見出しで書くと、
**本文の `## 起動できないとき` と同じ文字列の見出しが2つになる。**
**GitHub は後から出たほうの id に `-1` を付けて重複を避けるので、本文側の id が変わる。**
**外から `#起動できないとき` で貼られたリンクの飛び先が、目次のほうへ移る。**

**だから、目次は箇条書きだけで組む。**新しく作る見出しは `## 目次` の1つだけである
（`目次` という見出しは既に無いので、重複しない）。

```markdown
## 目次

- [起動できないとき](#起動できないとき)
  - [版を上げたら「progress_interval_ms の値 3600000 が不正です」で起動しなくなった](#版を上げたらprogress_interval_ms-の値-3600000-が不正ですで起動しなくなった)
  - …
- [issue が動かないとき](#issue-が動かないとき)
  - …
  - [チームで、issue ごとに担当の PC を決めたい](#チームでissue-ごとに担当の-pc-を決めたい)
    - [担当している PC が壊れたとき](#担当している-pc-が壊れたとき)
```

### 3-5. リンクの文は、見出しの原文をそのまま使う

**言いたいこと。**利用者は自分の画面に出た文字列を目で照合する。バッククォートを外すと照合しにくくなる。

**バッククォートも全角の括弧も落とさない。**この FAQ の `###` は、ほぼ画面に出るメッセージそのものである。
**利用者は自分の画面に出た文字列を目で照合するので、`` `✗ clone  ghq が PATH にありません` `` の
バッククォートを外すと、コードの体裁が消えて照合しにくくなる。**

**そのうえで、これが 3-8 の (c) を成り立たせる。**リンクの文と見出しの原文が同じ文字列なので、
**手元で `diff` を取るだけで1対1を両方向とも確かめられる。**

### 3-7. 直し忘れへの備えは、注意書きの3行だけ

**言いたいこと。**受け入れ条件が求めているのは注意書きである。
**検算のコマンドは [docs/FAQ.md](../../FAQ.md) へ出荷しない。**この設計文書に記録として置く。

**issue 本文の表も、代償をはっきり引き受けている。**

> ファイルの先頭に目次を書く … 見出しを足すたびに目次も直す必要があり、直し忘れると目次が嘘をつく

**したがって [docs/FAQ.md](../../FAQ.md) に置くのは、注意書きの3行だけである。**

> **見出しを足す・文言を変える・並べ替えるときは、この目次も直してください。**
> 直し忘れると、目次だけが古い見出しを指し続けます。
> リンクの飛び先（`#…`）は GitHub が見出しの文言から作る id なので、
> **文言を変えると飛び先も変わります。**目次の側だけが古い id を指したままになります。

**あわせて、HTML コメントを1行だけ置く。**この設計文書を指す。
**GitHub の描画に HTML コメントは1文字も出ない**ので、利用者の目には触れない。

### 3-8. この pull request をどう検算したか

**言いたいこと。**下の3つを叩いて確かめた。**これは「この変更が正しいことの記録」であって、
標準の手順として出荷するものではない。**捕まえないものは 3-9 に並べる。

**リポジトリの根で、bash か zsh で叩く**（`<(…)` を使っている）。

```bash
( export LC_ALL=C
  cd "$(git rev-parse --show-toplevel)" || exit 1
  awk '/^```/{f=!f;next} !f && /^#{1,6} /' docs/FAQ.md \
    | sed -E 's/^#+ +//' | sort | uniq -d
  awk '/^## 目次$/{t=1;next} t&&/^---$/{exit} t&&/^ *- \[/' docs/FAQ.md | wc -l
  diff \
    <(awk '/^## 目次$/{t=1;next} t&&/^---$/{exit}
           t&&/^ *- \[/{ n=match($0,/[^ ]/); d=(n-1)/2+2; s=$0
                         sub(/^ *- \[/,"",s); sub(/\]\(#[^)]*\)$/,"",s)
                         printf "%s %s\n", substr("######",1,d), s }' docs/FAQ.md) \
    <(awk '/^```/{f=!f;next} !f && /^#{2,4} /' docs/FAQ.md \
      | sed -E 's/^(#+) +/\1 /' | grep -vx '## 目次') )
```

**push したあと、GitHub が実際に付けた id とも突き合わせた。**

```bash
( export LC_ALL=C
  cd "$(git rev-parse --show-toplevel)" || exit 1
  comm -23 \
    <(awk '/^## 目次$/{t=1;next} t&&/^---$/{exit} t&&/^ *- \[/' docs/FAQ.md \
      | grep -o '](#[^)]*)' | sed 's/^](#//; s/)$//' | sort -u) \
    <(gh api "repos/{owner}/{repo}/contents/docs/FAQ.md?ref={branch}" -H 'Accept: application/vnd.github.html' \
      | grep -o 'id="user-content-[^"]*"' | sed 's/id="user-content-//; s/"$//' | sort -u) )
```

| 何を測ったか | 結果 |
| --- | --- |
| 同じ文言の見出し | **0件** |
| 読めた目次の項目 | **97**（空振りしていない） |
| 目次と見出しの、深さと文言の1対1 | **差分0** |
| 飛び先が無いリンク（push 済みの版） | **0件** |
| GitHub が付けた id | **99個**（98 + `## 目次`）。**`-1` で終わるものは0件** |

**この検算そのものも、3通りの入力で試した。**

| 入力 | 同じ文言の見出し | 読めた目次の行数 | 深さと文言の1対1 |
| --- | --- | --- | --- |
| **いまの [docs/FAQ.md](../../FAQ.md)** | **0行** | **97** | **0行** |
| 同じ文言の見出しを1つ足した写し | **1行**（捕まえた） | 98 | 0行 |
| 目次の字下げを1段ずらした写し | 0行 | 97 | **食い違いを出した**（捕まえた） |

### 3-9. この検算が捕まえないもの

**言いたいこと。**7つある。**出荷しない理由でもある。**
標準の手順にするなら、下を全部塞いだうえで、機械が走らせる場所へ置く必要がある。

| 捕まえないもの | どう壊れるか |
| --- | --- |
| **slug が衝突する重複** | 見出しの原文で重複を見ているので、`### 進捗報告の間隔を変えたい。` と `### 進捗報告の間隔を変えたい` は素通りする。**GitHub は句読点を落とすので id は衝突し、2本目のリンクが1本目の節へ飛ぶ** |
| **anchor と文の貼り違え** | 深さと文言を比べる側は anchor を捨て、id を比べる側は集合として比べる。**97項目を手で書くときにいちばん起きやすい誤りが、両方とも通る** |
| **`gh` の失敗** | 認証切れ・オフライン・push 忘れのとき id が0件になり、**97本全部が「飛び先が無い」と出る。**道具の失敗と見分けられない |
| **終了コード** | 部分式の終了コードは最後の `diff` のものになる。**重複が出ても 0 で終わる** |
| **h5 と h6** | 深さを比べる側は `#{2,4}` しか見ない。**`#####` を足すと見えない** |
| **字下げの幅** | `d=(n-1)/2+2` は空白2つを前提にする。**3つだと `d=3.5` になり、`substr` の扱いが awk の実装で割れる**（macOS は切り捨て、gawk は丸め） |
| **awk の版** | `/^#{1,6} /` は区間表現である。**macOS 12 以前の awk（20070501）はこれを literal として扱い、いつも「重複なし」を返す** |

## 5. FAQ.md を行番号で指している既存のリンク2本は、直さない

**言いたいこと。**2本ともこの変更の前から別の場所を指している。範囲外である。
**そのうえで、この設計文書は FAQ.md を行番号で1本も指さない。**

**この変更は FAQ.md の先頭へ109行足すので、FAQ.md を行番号で指しているリンクが全部ずれる。**

```
検索パターン: FAQ\.md#L
対象パス:     リポジトリの追跡ファイル全部（git grep）
対象コミット: afa4de0（この設計文書を入れる前）
結果:         2件
```

| どこ | 何を指しているつもりか | `afa4de0` の時点で指していた中身 |
| --- | --- | --- |
| [docs/plans/impl/issue142_144_branch_mismatch.md](issue142_144_branch_mismatch.md) の46行目 → `FAQ.md#L413` | 「ディレクトリだけが残っている」の節 | **`continuo doctor --missing-keys-patch` を patch へ渡すコマンド**（別物） |
| 同 146行目 → `FAQ.md#L431` | `**上の節（ディレクトリだけが残っている）とは違います。**` の行 | **`! 対応表のキー` の節の表の中**（別物） |

**2本とも、この変更を入れる前から既に別の場所を指している。**

**直さない。理由は5つ。**

| 何 | 中身 |
| --- | --- |
| **受け入れ条件が対象にしていない** | 受け入れ条件の3つとも [docs/FAQ.md](../../FAQ.md) の中の話で、`docs/plans/impl/` の下を1つも対象にしていない |
| **この変更が壊したものではない** | 2本とも `afa4de0` の時点で既に別の場所を指している |
| **1行の書き換えでは直らない** | 2本が欲しい場所は別々である。1本目は節そのもの、2本目はその次の節の中の1文。**正しく直すには2本それぞれの意図を読み直す必要がある** |
| **読み手が違う** | `docs/plans/impl/` は AI が過去の実装判断を辿るための記録で、利用者は読まない。**利用者向けの FAQ に目次を足す diff に、AI 向け記録の行番号修正が混ざると、pull request が「目次を足した」として読めなくなる** |
| **正しい直し方は別の範囲を持つ** | [.claude/rules/plan-file.md](../../../.claude/rules/plan-file.md) が求めているのは、行番号リンクを1本ずつ手で当てることではなく**全部を機械で検算し直すこと**である。`docs/plans/impl/` の9ファイル全体に対して1度やるべき作業で、この pull request の中に埋めるものではない |

**そのうえで、この設計文書は FAQ.md を行番号で1本も指さない。**
**「既に壊れている2本は範囲外だから直さない」は「自分で3本目と4本目を作ってよい」を含まない。**
**指すときはファイルとして指し、場所は見出しの名前で書く**（3-3 がそうしている）。
