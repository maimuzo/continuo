**言いたいこと。**GitHub の自動目次は既にあるが、**その中身は GitHub が返す HTML に1文字も入っておらず、
ボタンを押すまで存在しない。****ファイルの先頭に、6つの大見出しでグループ分けした入れ子の箇条書きの目次を書く。**
リンクの飛び先は GitHub が実際に付けた id を、GitHub が返す HTML から取って使う。

### 1-1. anchor（リンクの飛び先の id）は、GitHub が返す HTML から取る

**言いたいこと。**slug の規則を推測すると必ず外れる。**GitHub が返す HTML から取る。**

**日本語・全角の括弧・`✗`・`…`・バッククォートが混ざるので、規則を自分で実装しない。**

```bash
# continuo リポジトリの root で、push したあとに実行する
gh api "repos/{owner}/{repo}/contents/docs/FAQ.md?ref={branch}" \
  -H 'Accept: application/vnd.github.html' \
  | grep -o 'id="user-content-[^"]*"' | sed 's/id="user-content-//; s/"$//'
```

**`{owner}` `{repo}` `{branch}` は gh が、いる場所のリポジトリの値へ置き換える。**
**別のリポジトリの中で叩くと、別のファイルの HTML が返り、それらしい嘘の一覧になる。**
**このコマンドを [docs/FAQ.md](../../FAQ.md) へ置いてはならない。**
`grep` の型が、そのコマンド自身の文字列を拾う（実測で100件返り、3行目が `id="user-content-[^"` だった）。

**これは GitHub の画面と同じ仕組みが返す HTML である。**`user-content-` を外したものが、
markdown から `#…` で飛べる id である。

| 見出し | GitHub が付けた id |
| --- | --- |
| `### 版を上げたら「progress_interval_ms の値 3600000 が不正です」で起動しなくなった` | `版を上げたらprogress_interval_ms-の値-3600000-が不正ですで起動しなくなった` |
| `### \`✗ clone  ghq が PATH にありません\`` | `-clone--ghq-が-path-にありません` |

## 2. GitHub の自動目次が、実際にどうなっているか

**言いたいこと。**GitHub が返す HTML に目次の中身は1文字も入っておらず、ボタンは押されていない状態で届く。
**「押すまで気づけない」は、これで実測になった。**

**issue が「実際の GitHub の画面で両方を見てから決めること」と書いている。**
**Claude in Chrome はこのセッションで権限を拒否されたので、画面は開いていない。**
**代わりに、GitHub が返す HTML そのものを取って測った**（`curl -sL https://github.com/<owner>/<repo>/blob/main/docs/FAQ.md`）。

| 何 | 実測 |
| --- | --- |
| 目次の中身（見出しへの `href="#…"`）が HTML に描かれているか | **0件** |
| Outline のボタンの初期状態 | **`aria-pressed="false"`。**パネル本体の markup は1つも無い |
| 押したときに出る中身 | **h1〜h4 の98項目を、階層のまま全部** |
| 維持の手間 | **ゼロ。**見出しを足せば勝手に追随する |

**issue が「長すぎて読めない」と心配した91項目は、自動目次では既に98項目として起きている。**
**書く側は97項目**（6 + 86 + 5）**で、98との差は h1（文書の題名）だけである。**
**短さで勝負にはならない。書く価値があるのは、置き場所が違うからである。**

## 3. 決めたこと

**言いたいこと。**先頭に入れ子の箇条書きの目次を書く。節の並べ替えは要らない。
目次の中に見出しを作らない。検算のコマンドは出荷しない。

### 3-1. 自動目次に任せるのではなく、ファイルの先頭に書く。両方が並び立つ

**言いたいこと。**自動目次は消せないので、決めるのは「書くか / 書かないか」だけである。書く。

| どうするか | 選ぶと利用者に起きること | 選ばないと続くこと |
| --- | --- | --- |
| **ファイルの先頭に目次を書く（採る）** | **ページを開いた瞬間に、6つの症状の区分と91個の見出しが目に入る** | **`aria-pressed="false"` のボタンを押すことを知らない人は、2522行をめくって探し続ける** |
| 自動目次だけに任せる（採らない） | 何もしなくてよい | 同上。**issue が「メニューを開くまで気づけない」と名指しした状態がそのまま残る** |

### 3-2. 節の並べ替えは要らない。既に6つに分かれている

**言いたいこと。**issue が条件付きで挙げた作業だが、条件が成り立たない。数えて確かめた。

| `##` の大見出し | その下の `###` の数 |
| --- | --- |
| 起動できないとき | 10 |
| doctor が通らないとき | 18 |
| issue が動かないとき | 34 |
| 片付けたいとき | 13 |
| 気にしなくてよいもの | 4 |
| 使い方が分からないとき | 7 |

**この issue の範囲は「目次を付ける」のままでよい。**別の issue への切り出しも行わない。

### 3-3. `####` の5個も目次に載せる

**言いたいこと。**issue が例に挙げた節が `####` だからである。`###` だけに絞ると、その節が漏れる。

> この文書には「担当している PC が壊れたとき」「チームで、issue ごとに担当の PC を決めたい」のような、
> 他のどこにも書いていない手順が入っている。

**「担当している PC が壊れたとき」は `####` である**
（`### チームで、issue ごとに担当の PC を決めたい` の下）。
**行番号では指さない。**この変更が目次を先頭へ足すので、その行番号は書いた直後にずれる。

### 3-4. 目次の中に見出しを作らない。入れ子の箇条書き1つにする

**言いたいこと。**同じ文言の見出しが2つになると、GitHub が後のほうの id に `-1` を付け、
**本文側の id が変わる。**外から貼られたリンクの飛び先が目次へ移る。

**だから目次は箇条書きだけで組む。**新しく作る見出しは `## 目次` の1つだけである
（`目次` という見出しは既に無いので、重複しない）。

```markdown
- [起動できないとき](#起動できないとき)
  - [版を上げたら「progress_interval_ms の値 3600000 が不正です」で起動しなくなった](#版を上げたらprogress_interval_ms-の値-3600000-が不正ですで起動しなくなった)
- [issue が動かないとき](#issue-が動かないとき)
  - [チームで、issue ごとに担当の PC を決めたい](#チームでissue-ごとに担当の-pc-を決めたい)
    - [担当している PC が壊れたとき](#担当している-pc-が壊れたとき)
```

### 3-5. リンクの文は、見出しの原文をそのまま使う

**言いたいこと。**利用者は自分の画面に出た文字列を目で照合する。バッククォートを外すと照合しにくくなる。

**この FAQ の `###` は、ほぼ画面に出るメッセージそのものである。**
`` `✗ clone  ghq が PATH にありません` `` のバッククォートを外すと、コードの体裁が消える。

### 3-6. 置く場所と、中の並び

**言いたいこと。**[docs/FAQ.md](../../FAQ.md) は `##` の前に必ず `---` と空行を置いている。その並びに合わせる。

```
（前書きと continuo doctor のコマンド）
（空行）
---
（空行）
## 目次          ← ここから足す
（空行）
（注意書き。5行）
（空行）
（目次の本体 97行）
（空行）
---
（空行）
## 起動できないとき
```

**注意書きは目次の本体より前に置く。**
**受け入れ条件が求めているのは「その場に書いてある」ことであり、97行の後ろへ回すと
`## 目次` を見た人の視界から外れるためである。**

### 3-7. 直し忘れへの備えは、注意書きだけ

**言いたいこと。**受け入れ条件が求めているのは注意書きである。
**検算のコマンドは [docs/FAQ.md](../../FAQ.md) へ出荷しない。**

> - [ ] 目次を書いた場合は、見出しを足したときに目次を直す必要があることが、その場に書いてある

**issue 本文の表も、代償をはっきり引き受けている。**

> ファイルの先頭に目次を書く … 見出しを足すたびに目次も直す必要があり、直し忘れると目次が嘘をつく

**したがって [docs/FAQ.md](../../FAQ.md) に置くのは、注意書きだけである。**

| 何を書くか | なぜ |
| --- | --- |
| 足す・**消す**・書き換える・**別の `##` の下へ移す**ときは目次も直す | **「消す」を落とせない。**節を消して目次の行を残すと、飛び先の無いリンクが残り、[docs/releasing.md](../../releasing.md) の門も通ってしまう（下の 4.）。**「移す」も落とせない。**節を別の区分へ移すと**anchor も文言も変わらないのでリンクは全部通り、目次の入れ子だけが誤りになる** |
| **見出しに1文字でも触ったら**（空白の数や `#` の数も含む）**、項目の文と飛び先の両方を見直す** | **動詞を並べると漏れる。**空白2つを1つへ詰めるのは11個の見出しに効き、25本の anchor が `--` を含む。`####` を `###` へ変えると**id は変わらないまま入れ子だけがずれる。**どちらも「文言を変える」とは読まれない |
| **正しい id の取り方は、この設計文書にあると書く**（コマンドそのものは置かない） | **これが無いと、手で slug を推測して外す**（1-1）。**コマンドを [docs/FAQ.md](../../FAQ.md) へ置いてはならない。**GitHub は要素のテキストの `"` を実体参照にしないので、コードブロックの中の `grep` の型がそのまま HTML に出て、**自分で自分を拾う**（実測で99個の見出しに100件返った） |

**強調は行の全体に掛ける。**このファイルは `**…。**文字` の形を315行で使っているが、
**閉じる `**` の直前が句点で直後が文字だと、CommonMark が強調の終わりと認めない。**
**GitHub が返す HTML に、文字としての `**` が636個残っている**（実測）。
**315行には触らない。**足す行だけ、同じファイルの中で強調として効く形を選ぶ。

**検算のコマンドを出荷しない理由。**

| 何 | 中身 |
| --- | --- |
| **issue が求めていない** | 受け入れ条件は注意書きまでである |
| **誰も走らせない** | CI にも [docs/releasing.md](../../releasing.md) の門にも入っていない。**走らないコマンドは、間違っていても誰も気づかない** |

| 何 | なぜやらないか |
| --- | --- |

| **目次を検査するスクリプトと CI の追加** | **issue が求めていない。**受け入れ条件は注意書きまでである。**手元で試した検算は7つを捕まえなかった**（slug の衝突・anchor の貼り違え・`gh` の失敗・終了コード・h5 と h6・字下げの幅・awk の版）。**機械の門にするなら全部塞ぐ必要がある。**中身は issue #213 のコメントに残した |

| **[docs/FAQ.md](../../FAQ.md) 以外の文書への目次** | **issue の対象は FAQ 1本である。**他の6本（[docs/upgrading.md](../../upgrading.md) 1690行ほか）にも目次は無いが、範囲を広げない |

## 5. FAQ.md を行番号で指していたリンク2本を、見出しの名前で指し直す

**言いたいこと。**2本ともこの変更の前から別の場所を指していた。
**この変更が97本の飛び先を実測で揃えた直後なので、そのうち2本を借りて指し直すのがいちばん安い。**

```
検索パターン: FAQ\.md#L
対象パス:     リポジトリの追跡ファイル全部（git grep）
対象コミット: afa4de0（この設計文書を入れる前）
結果:         2件。どちらも docs/plans/impl/issue142_144_branch_mismatch.md の中
```

**行番号で指すと、指した直後にずれる。**
[.claude/rules/plan-file.md](../../../.claude/rules/plan-file.md) が実測で記録している。
3行足しただけで13本がずれ、**うち3本は主張の逆を書いた行に着地した。**
この変更は [docs/FAQ.md](../../FAQ.md) の先頭へ108行足すので、2本はさらに108行ずれる。

**だから行番号を当て直さない。見出しの名前で指す。**

| どこ | 何を指したいか | 指し直した先 |
| --- | --- | --- |
| [docs/plans/impl/issue142_144_branch_mismatch.md](issue142_144_branch_mismatch.md) の1つ目 | 「ディレクトリだけが残っている」の症状の節 | `#着手が目的のパスに実体があるのに-git-の-worktree-として登録されていませんで止まる` |
| 同 2つ目 | `**上の節（…）とは違います。**` の1文がある節 | `#着手がworktree-がどの-branch-にも載っていませんdetached-headで止まる` |

**2本とも、この変更が目次へ書いた飛び先である。**新しく作ったものは1つも無い。
**指し直したあと、リポジトリに `FAQ.md#L` は0件になる。**

**残りの `docs/plans/impl/` の行番号リンクは、この pull request では触らない。**
**この2本を直せたのは、この変更が同じファイルの飛び先を全部持っているからである。**
他のファイルを指しているものは、その飛び先を測るところから始まる。

## 6. 人間にしかできないこと

**言いたいこと。**受け入れ条件の1つ目は目で見るしかない。ブラウザ操作の権限が無いので代替できない。

> - [ ] GitHub の画面で `docs/FAQ.md` を開き、目次から任意の節へ飛べる

**pull request の branch の blob の画面**（`https://github.com/<owner>/<repo>/blob/<branch>/docs/FAQ.md`）
**で開き、目次の項目をいくつか押して確かめてもらう。**
**Files changed の diff の画面ではない。**この変更の id は全部 blob の HTML に対して確かめたもので、
diff の画面では anchor が働かず、「押しても何も起きない」が本物の欠陥と見分けられない。
