## 1. 人間が決めた方針

**言いたいこと。**目次の行はファイルに書かない。**GitHub の outline に任せる。**人間がそう決めた。

**原文**（issue #213 のコメント。OWNER）。

> FAQ.mdの中に目次として表示する行を自分で用意せず、githubの目次ボタン(outlineボタン)を押すことで目次を表示するようにしたい。
> 理由として、FAQの中に目次として表示する行を用意すると、この先FAQの内容を変更するたびに目次も更新しなければならず、メンテナンスコストがかかる。
> 一方outlineを使うならば、適切なセクション深度(#や##や###など)で表現すれば、自動的に目次が表現できるため、必ず整合性が確保される。

**outline はボタンを押すまで存在しない。**GitHub が返す HTML に目次の中身は1文字も入っておらず、
ボタンは `aria-pressed="false"` で届く（実測）。**だから在りかを見せる節を作る。**

**「現在のFAQの内容を全部書き換えて」の読み方。**
**構成と見出しの全面変更と読み、本文の中身は書き換えない。**
根拠は、同じ指示の中に「**この下にサブセクションをAI判断で作り、その中に各FAQ本文を移して**」があることである。
**返事は待たずに進める。**本文の書き直しまで求めているなら止めてほしい、と issue のコメントで伝えてある。

## 3. FAQ を3つの区分へ組み直す

**言いたいこと。**トップレベルを3つにし、その下に「どんな時に困るか」で名付けたサブセクションを作る。
**いまの `###` は `####` へ1段下げて移す。**

### 3-1. 読み手を新人エンジニアに固定する

**言いたいこと。**人間が読み手を名指しした。**そこからサブセクションの言葉が決まる。**

> 対象読者は、新人エンジニアを想定しろ。continuoを使いたいが、linuxを使ったこともなく、
> どう使えばいいかわからない状態の人を想定し、continuoを手順書通りに動かしてみたが、
> 困ったことが起きた時にFAQを読んで、具体的な操作方法や、機能を知るためにFAQを使う想定。

**サブセクションの名前に、設定のキー名とコードの識別子を出さない。**
`tracker.active_states` も `automated_state_rewrite` も、この人は設定ファイルの中でしか見たことがない。

**`worktree` `hook` `branch` `issue` は英語のまま使う。**
[.claude/rules/reporting.md](../../../.claude/rules/reporting.md) が、これらを日本語へ直訳することを禁じている。
**画面と手順書に出る語なので、訳すと同じものに名前が2つできる。**

**「ボード」と書かない。「カンバン」と書く。**
[docs/spec/translation-glossary.md](../../spec/translation-glossary.md) がそう決めている。

### 3-2. 階層の作り方

**言いたいこと。**深さを1段ずつ下げるだけにする。**個々の FAQ の見出しは1文字も変えない。**

| 深さ | 何を置くか | いくつ |
| --- | --- | --- |
| `#` | `よくある質問` | 1 |
| `##` | `目次を表示するには` と、区分3つ | 4 |
| `###` | **サブセクション。**「どんな時に困るか」で名付ける | 24 |
| `####` | **いまの `###` をそのまま下げたもの** | 93 |
| `#####` | **いまの `####` をそのまま下げたもの** | 13 |

**個々の FAQ の見出し（`####`）は、エラーメッセージのまま残す。**
**新人が画面の文字列で探せる唯一の手掛かりだからである。**
他の文書とテストが、この文言を名前で引いているためでもある。

**`## continuoで何ができるか` は、`continuo` と `で` のあいだを空けない。**
**人間が原文でこの文字列を指定したためである。**

> - セクションタイトルは、トップレベルを以下の内容にして。
>   - **continuoで何ができるか**（機能別に、機能説明しているFAQを配置）

**FAQ の他の見出しは、欧文と日本語のあいだを空けている**（`continuo 自体を直したいとき` /
`continuo doctor が赤くなるとき` / `hook の置き場所でつまずくとき`）。
**この1つだけが例外である。**リポジトリの中でこの書き方をしているのはここだけで、
**割れているリンクは0件である。****typo に見えるが、直さない。**
揃えるかどうかは人間が決める（下の 6.）。

### 3-4. 位置で他の節を指している本文を、名前で指す形へ直す

**言いたいこと。**本文が「上の節」「下の『…』」で他の節を指している。**並べ替えると逆を向く。**
**位置の語を落として、名前だけで指す。**

**残してよいのは、指し先が同じ節の中にあるものだけである。**
**節やサブセクションをまたぐものは、位置の語を落とし、区分とサブセクションの名前を括弧で添える。**

**いま14箇所残っている。内訳と、触らない理由は次のとおり。**

| 何を指しているか | 件数 | なぜ触らないか |
| --- | --- | --- |
| **節の中の表**（「下の表」「上の表」） | 7 | 同じ節の中にある表なので、並べ替えても離れない |
| **節の中の小見出し**（「上の『確かめ方』」「下の『他に見るところ』」） | 2 | 同上 |
| **同じサブセクションの中の、前後の `#####`** | 2 | 振り分けで隣り合わせを保っている |
| **ほぼ同じ名前の直前の節**（括弧の有無だけが違う2つ） | 2 | 名前で指すと、読者がどちらか判別できない |
| **ダッシュボードの画面の、いちばん上の表** | 1 | FAQ の節ではない |

**数え方。****改行をまたぐものがあるので、行単位の grep では数えられない。**
**「下の」で行が終わり、次の行が引用で始まる形が2件あり、5周のあいだ見えていなかった。**
原文全体へ正規表現を当て、コードフェンスの中を除き、**1件ずつ「いる節」と「指し先の節」を突き合わせる。**

```python
import re, io
src = io.open('docs/FAQ.md', encoding='utf-8').read()
lines = src.split('\n')
pat = re.compile(r'(上の「|下の「|上の節|下の節|上の表|下の表|いちばん上の|1つ上の|上の JSON|上の\n「|下の\n「)')
for m in pat.finditer(src):
    ln = src[:m.start()].count('\n') + 1
    f = False
    for l in lines[:ln]:
        if l.startswith('```'):
            f = not f
    if f:            # コードフェンスの中は数えない
        continue
    print(ln, m.group(1).replace('\n', '⏎'), lines[ln-1].strip()[:60])
```

**区分をまたぐ4件は、直さないと確実に壊れる。**

| どこ | 何を指しているか | 割れる先 |
| --- | --- | --- |
| 「判定の中身は、**下の**…」 | 複数の機械で見張っているのに、どの機械も issue を取らない | トラブルシューティング → 目的別使用例 |
| 『（**上の**「版を上げたら…」）』 | 版を上げたら progress_interval_ms が不正 | 担当が外れる → 入れたばかり、または版を上げたあと |
| 『**下の**「持ち回りを使わずに…」』 | 持ち回りを使わずに、1台だけで動かしたい | 担当が外れる → 何台かの PC |
| 『その使い方は**下の**「チームで…」』 | チームで、issue ごとに担当の PC を決めたい | 担当が外れる → 何台かの PC |

## 4. スクリーンショット

**言いたいこと。**outline はボタンを押すまで存在しないので、在りかを見せる。
**古くなる情報を1つも写さない。**ツールバーのボタンの並びだけを切り出す。

### 4-1. 撮り方

**言いたいこと。**`playwright-cli` で撮る。**注釈は、ページの中へ枠と説明を差し込んでから撮る。**

| 順 | 何をするか |
| --- | --- |
| 1 | **組み直した [docs/FAQ.md](../../FAQ.md) を push してから**、その branch のページを開く |
| 2 | outline のボタンの位置を、`TableOfContents-module__IconButton` を含む class から取る |
| 3 | そのボタンに赤い枠と吹き出しを、ページの中へ差し込む |
| 4 | **ツールバーのボタンの並びと吹き出しだけを切り出して**、[docs/images/faq_outline.png](../../images/faq_outline.png) へ置く（310x94） |

**組み直したあとに撮る。**先に撮ると、**写り込む見出しが、その画像を載せた文書に存在しないものになる。**

**画像編集の道具を足さない。**注釈をページの中で作るので、撮った時点で完成している。

### 4-2. FAQ へ書く節の文面

**言いたいこと。**参照は [images/faq_outline.png](../../images/faq_outline.png) と書く。**`docs/` を先頭に付けない。**

**[README.ja.md](../../../README.ja.md) は [docs/images/board.png](../../images/board.png) を `docs/` から始まる形で書いているが、あれはリポジトリの直下にあるからである。**
**[docs/FAQ.md](../../FAQ.md) は `docs/` の中にあるので、同じ形を写すと `docs/docs/images/…` を指して画像が出ない。**
**`docs/` の中から画像を参照した前例は0件で、倣える前例が無い。**

```markdown

**この文書は長いので、GitHub の目次から探すのが速いです。**

## 5. 受け入れ条件を書き直す

**言いたいこと。**方針変更で、3つとも意味が変わった。**測れる形にする。**

**いまの原文。**

> - [ ] GitHub の画面で `docs/FAQ.md` を開き、目次から任意の節へ飛べる
> - [ ] 目次に載っている項目が、実在する見出しと1対1で対応している（飛び先が無いリンクが0件）
> - [ ] 目次を書いた場合は、見出しを足したときに目次を直す必要があることが、その場に書いてある

**書き直す案。**

| 条件 | どう測るか |
| --- | --- |
| **目次として書いた行が、FAQ に1行も残っていない** | **見出しへのリンクの箇条書き**（`- [` で始まり `](#` を含む行）**が0件。**`## 目次を表示するには` は目次そのものではなく、outline の在りかを説明する節なので、見出しの名前では数えない |
| **見出しの深さが飛んでいない**（`##` の次が `####` にならない） | 見出しを順に読み、深さの差が2以上になる箇所が0件 |
| **本文が失われていない** | 組み替えの前後で、**見出しと区切り線以外の行**を数え、**意図した書き換えの対応表を織り込んだうえで、説明の付かない増減が0。**3-4 が本文の書き換えを命じているので、**差分そのものは0にならない** |
| **3つの区分と24のサブセクションがある** | `##` が4つ（目次を表示するには＋3区分）、`###` が24 |
| **他の文書から FAQ への案内が浮いていない** | **FAQ を指している外部の参照を全部読み、節の名前・行番号・FAQ の性格の3つが合っているかを1件ずつ確かめる。**対象は [docs/upgrading.md](../../upgrading.md)、[docs/plans/continuo_design.md](../continuo_design.md)、[docs/plans/impl/issue142_144_branch_mismatch.md](issue142_144_branch_mismatch.md)、[README.ja.md](../../../README.ja.md)、[README.md](../../../README.md) |
| GitHub の画面で outline から任意の節へ飛べる | **人間が見る**（下の 6.） |
| スクリーンショットが outline の在りかを示している | **人間が見る**（同上） |

## 6. 人間にしかできないこと

**言いたいこと。**スクリーンショットが分かりやすいかは、人間にしか判定できない。

**あわせて、「現在のFAQの内容を全部書き換えて」の読み方を確かめてほしい。**
**私は「構成の全面変更。本文は移すだけ」と読み、返事を待たずに進めた。**
**本文の書き直しまで求めているなら、範囲が大きく変わるので止めてほしい。**
