# リポジトリ自身の運用の仕掛け（hook・スクリプト）

**言いたいこと。**このリポジトリは、「PR を出すときは `/code-review` を通す」という
CLAUDE.md の規則を、[.claude/hooks/block-merge-without-review.py:1](../../.claude/hooks/block-merge-without-review.py#L1)（PreToolUse hook）と
[scripts/check-release-ready.sh:1](../../scripts/check-release-ready.sh#L1)（リリース前の検査）の2つの機械で支えている。
**この節は、その2つの「いまの仕様」だけを置く。修正の履歴は置かない。**

**2つは役目が違う。**hook は**実行の前に一律で止めるだけ**で、レビューの有無を判定しない。
リリース前の検査は、**マージ済みの PR にレビュー結果が貼ってあるかを数える。**

---

## 1-1. block-merge-without-review.py は一律で止める

**言いたいこと。**`Bash` へ渡す `command` を語に切り、**`gh` `pr` `merge`（または `ready`）が
この順で語として並んでいたら止める。それだけである。**
**PR 番号は取り出さない。レビューの有無も見ない。外部コマンドを呼ばない。**

**実装。**[.claude/hooks/block-merge-without-review.py](../../.claude/hooks/block-merge-without-review.py)。
`Bash` ツールの `PreToolUse` として [.claude/settings.json:87-96](../../.claude/settings.json#L87-L96) に登録されている。

**止めるもの。**

- **マージと ready の呼び出しのすべて。**番号・引用符で囲んだ番号・PR の URL・`--repo` /
  `-R`・branch 名・引数を1つも書かない形の、どれでも同じように止める
- `;` `&&` `&` `|` 改行 括弧 バッククォート `$( )` で区切った先にあるものも止める

**止めないもの。**

- **`--undo` が同じ断片にあるもの**（`gh pr ready <番号> --undo`）。draft へ戻す手順そのものである
- **`--help` / `-h` が同じ断片にあるもの。**使い方を表示するだけで、PR は動かない
- **heredoc の中身**（`<<EOF` `<<'EOF'` `<<"EOF"` `<<-EOF` の4形）。実行される文ではなく、
  ファイルへ書く文章である。**文書にマージの手順を書くだけで止まっては困る**
- **語に切れなかった行**（引用符が閉じていないなど）。**解析に失敗したら通す**

**通したいときは逃がし口を使う。**環境変数 `CONTINUO_ALLOW_UNREVIEWED_MERGE=1`。
**判定より先に見るので、置いてあれば何も解析しない。**人間が `claude` を起動する前のシェルで置く。
**AI が自分で置いてはならない**（[CLAUDE.md](../../CLAUDE.md) 参照）。

## 1-2. なぜ番号を取り出すのをやめたか

**言いたいこと。**番号を取り出す形は、字句解析の穴を塞ぎ切れなかった。
**止めるだけなら番号は要らない。**レビューが貼ってあるかは、逃がし口の前で人間が確かめる。

**収束しなかった。**引用符の中の `<<` で以降の行を全部落とす、コメントに書いた例で誤爆する、
`--repo` を2回書くとでたらめなほうが勝つ、番号と branch 名が混ざると branch 名を見ない、
リポジトリ名の判定と問い合わせ先が食い違う——**PR #109 の3回のレビューで45件の指摘が出て、
3回目でも実際に踏むものが5件残っていた。**取り出す情報を増やすほど、判定の場合分けが増える。

**そもそも完璧にはできない。**`eval "…"` / `bash -c "…"` / 変数越しの呼び出しのように
文字列の中に隠す形は、語に切った段階ではただの文字列にしか見えない。この hook は
`Bash` ツールへ渡す文字列を実行の前に読むだけで、シェルへ渡して実行するわけではない。
**狙いは「規則を忘れた・読み替えた場合の素の呼び出し」を止めることだけである。**

**誤爆と見逃しなら、見逃しを採る。**何もしていない作業を止めると、そのぶん作業が進まない
実害が出る。だから **解析に失敗したら通す**（崩れた引用符・閉じていない heredoc）。

**残っている見逃しの例。**`echo 'a << b'` のように引用符の中に `<<` があると、heredoc の
開始と読まれて以降の行が中身として飛ばされる。**その行より後ろのマージは止まらない。**
**これは意図した倒し方である**（止める側へ倒すと、文書を書くだけで誤爆する）。

## 1-3. scripts/check-release-ready.sh が数える条件

**言いたいこと。**「レビュー済みとみなす条件」を持つのは、**リリース前の検査だけになった。**
hook 側には無い。**同じ条件を2箇所に書く問題は、hook から消えたことで無くなった。**

**リリース前の検査が数えるもの。**
[scripts/check-release-ready.sh](../../scripts/check-release-ready.sh) の `review_of()` が、
`gh pr view <番号> --json comments` の結果を jq で絞る。

| 条件 | どう書いてあるか |
| --- | --- |
| 目印が**コメントの先頭**にあること | `test("^\\s*<!-- code-review-result -->")` |
| 信頼できる投稿者が貼ったものだけ | `["OWNER", "MEMBER", "COLLABORATOR"] \| index($a)` |

**投稿者を絞る理由。**このリポジトリは PUBLIC である。通りがかりの人が目印を貼れば、
その PR は恒久的にレビュー済み扱いになってしまう。

**先頭に限る理由。**本文の途中で目印を引用しただけの説明コメント
（例:「◯◯のコメントに目印が無い」という指摘そのもの）まで数えると、同じことが起きる。
