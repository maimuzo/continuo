# ユースケース: 夜に機械を落として翌朝に担当を続ける

## 根拠資料

- `docs/plans/continuo_design.md#3-77c`（就業時間を過ぎて PC を落としたとき。夜・朝・最初の巡回・着手の4段と、18時間を超えたときに起きること）

## この記述が追うのは、朝に pane が残っていない場合である

**言いたいこと。**continuo は止まるときに pane を閉じないが、**電源を落とせば herdr のプロセスごと終わる。**
朝に起動し直した continuo から見ると、身元ファイルを持つ worktree は在るのに、その worktree を cwd に持つ pane が無い。
この記述はその場合を追う（朝に pane が残っている機械では、`再起動して実行中の issue を引き継ぐ` の基本フローが pane ごと引き継ぐ）。

| 順 | 誰が | 何をするか | 記述のどこか |
| --- | --- | --- | --- |
| 1 | 復元 | pane が無く Status が active_states なので、`restart.orphan_running_action` を読む。既定の `redispatch` では何もせず、印にも入れずに次の巡回へ委ねる | ステップ6（取り込んだ記述の `paneの不在`） |
| 2 | 最初の巡回 | active_states の候補を取る。この issue は Status が running_state のままなので候補に出る | ステップ7 |
| 3 | 最初の巡回 | 担当者を読む。この機械の投稿者1人なので、入札せずに着手へ進む。hold も書き直さない | ステップ7 |
| 4 | 着手 | Status は既に running_state なので書かない。Status を動かした記録も書かない | ステップ8 |
| 5 | 着手 | 置き場所に在る前の日の worktree を作り直さずに使う | ステップ9 |
| 6 | 着手 | 身元ファイルのセッション UUID に会話の記録が在れば、`--resume` で復帰する | ステップ10 と11 |
| 7 | 着手 | 1回目の本文を送る。継続の指示ではない | ステップ12 |

**送るのが1回目の本文である理由。**継続の指示には「issue を読むこと」「紐づく PR も読むこと」が入っていない。
それだけを送ると、差し戻された issue で新しく付いたレビューを読まないまま進む（`internal/orchestrator/dispatch.go` の `startRunFromWorktree`）。
**会話は残っているので、エージェントは前の日にどこまで進めたかを分かったうえで読み直す。**

**着手の段で起きる次の2つは、この記述の経路に出していない。**どちらも `issue を1件処理する` の代替フローが受ける。

| 何が起きるか | どう進むか | 受ける代替フロー |
| --- | --- | --- |
| 会話の記録は在るのに、復帰つきの起動が完了しない | 新しいセッション UUID を採番し、新しいセッションで起動し直す。前の日の会話は引き継がれない | `issue を1件処理する` の `復帰の失敗` |
| herdr が agent を登録していないまま、作業中の hook が届いている | 1回目の本文をその場では送らず、走っている turn の終わりを待つ | `issue を1件処理する` の `未登録のまま作業中` |

**`restart.orphan_running_action` が既定でないとき、この記述のとおりにはならない。**
`to_dispatch_state` なら Status が着手待ちへ戻り、Status を動かした記録が1件増える。
`to_failure_state` なら Status が failure_state へ落ち、人間が戻すまで着手されない。だから事前条件に `redispatch` を書いた。

## 夜のあいだ、担当は動かない

**言いたいこと。**電源が落ちているあいだ、GitHub 側では何も動かない。
**Status も担当者も hold のコメントもそのままである。**

| 段 | 何が起きるか |
| --- | --- |
| 夜、電源が落ちる | GitHub 側は何も動かない |
| 夜のあいだ | ほかの機械は、担当者が自分でなく期限内なので**触らない。入札もしない** |
| 朝、同じ機械が起動する | 復元は pane の無い run を次の巡回へ委ねる |
| 最初の巡回 | 担当者は自分なので**入札は起きない。**hold のコメントも書き直さない |
| 着手 | **前の日の worktree をそのまま使う。**前の日の会話へ復帰する |

**continuo が書くコメントは1件も増えない。**これが「担当も worktree もそのまま続く」の中身である。
進捗のコメントを書くのは、1回目の本文を受け取った Claude Code である（`指示書に沿って issue を1件仕上げる` の範囲）。

## 期限を18時間にした理由

**言いたいこと。**期限は、**1日の業務が終わって翌朝に戻るまでを跨げる長さにする。**

| 期限の長さ | 何が起きるか |
| --- | --- |
| 8時間 | **終業して帰るだけで担当を奪われる。**翌朝に別の機械が最初からやり直している |
| **18時間（既定）** | 翌朝に戻れば続きから進む。**週末や休暇で止まったら、別の機械が拾い直す** |
| 1週間 | 落ちたまま戻らない機械の担当が、丸1週間ほかの機械を止める |

**期限が切れて担当が移るのは、`期限をまたぐ` である。**そのとき何が残り、何が失われるかは
下の表が正である。**担当を外した側は `<!-- continuo:released -->` の印を付けたコメントを1件書く**
（設計 3-77c）。

## 担当が移ったときに残るものと失われるもの

| 何が | どうなるか | なぜか |
| --- | --- | --- |
| branch の名前 | **変わらない** | issue から一意に決まる（`herdr.worktree.branch_template`） |
| push した commit | **残る** | 新しい機械は同じ名前の branch を fetch して続きから始める |
| push していない commit | **新しい機械からは見えない** | 前の機械のディスクの中にあり、前の機械の worktree に残っている |
| worktree | **前の機械の中に残る** | 新しい機械は自分の置き場所に worktree を作り直す |
| 会話の文脈 | **引き継げない** | セッション UUID は身元ファイルにあり、前の機械のディスクの中にある |

**だから、生きている機械は進捗のコメントと一緒に push する。**
**進捗のコメントは期限も延ばす**ので、書き続けている機械は担当を外されない。

## 担当が移っていた朝に、前の機械が何をするか

**言いたいこと。**担当者を見るのは復元ではなく、巡回の着手の手前（`handoffGate`）である。
復元は worktree と pane とボードの Status しか見ない。

| 順 | 何が起きるか |
| --- | --- |
| 1 | 復元は pane の無い run を次の巡回へ委ねる。新しい担当の機械が Status を running_state にしているので、この issue は候補に出る |
| 2 | 巡回は担当者を読む。ほかの機械の投稿者1人で、その担当者を名指しする hold が在り、期限内である |
| 3 | 巡回はこの issue を着手の対象から外す。入札もしない。issue にコメントも書かない。ログは DEBUG の1行だけである |
| 4 | worktree は消さない。Claude Code を起動しないので、branch へ push するものも居ない |

**released のコメントを読んでログへ残すのは、印を持つ run の担当を確かめ直す経路（`verifyHandoff`）だけである。**
pane が無い朝の経路は印を持たないので、released のコメントをログへ残さない。直す前の記述はここを「記録に残す」と書いていた。

**降ろすときも worktree は1バイトも消さない。**push していない commit が残っていることがあり、
**利用者はそれを取り出せる唯一の場所にいる。**片付けるかどうかは `continuo abandon` で人間が決める。

**朝までに新しい担当の機械も止まって期限が切れていたとき**は、この機械がその担当を外して入札をやり直す
（取り込んだ記述 `issue の担当を入札で決める` の `他人の担当`）。この記述の経路には出していない。

        Note over S: ABORT コメントを書かない。push しない
    else 担当者がこの機械の投稿者1人のままである
        S->>S: 入札のコメントも hold のコメントも書かない
        S->>S: 前の日の worktree をそのまま使う
        alt 身元ファイルのセッション UUID の会話の記録がある
            S->>H: 前の日のセッション UUID への復帰での Claude Code の起動を要求する
        else 会話の記録が無い
            S->>H: 新しいセッションでの Claude Code の起動を要求する
            Note over S: 前の日の会話は引き継がれない
        end
        S->>CC: 1回目の本文を送る
    end
