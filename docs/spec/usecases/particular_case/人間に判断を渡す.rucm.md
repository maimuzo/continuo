# ユースケース: 人間に判断を渡す

> **turn の終わりの処理のうち、後半（取り直した Status で run の行き先を決める。`refreshIssue` → `decideAfterTurn` → `finishRun`）を書いた記述である。**
> 前半（表明を読んでStatusを動かす）は `表明を読んでStatusを動かす` に分け、段1 で `INCLUDE USE CASE` で引く。
> 成果の報告を確かめてから worker を止めて印を外す段は、`issueを1件処理する` と共通の `runを終えてworkerを止める` を引く（人間の決定。2026-10-02）。
>
> **実装は、表明で書いた値を信じない。**取り直した Status だけで行き先を決める。
> だから、表明が無くても Status が引き渡しの選択肢なら（エージェントが `gh` で自分で動かした・利用者が動かした）、基本フローを通る。
>
> **run を終える処理（`finishRun`）は、`issueを1件処理する` と同じ実装を通る。**

## この記述で使う言葉

**エージェント**とは、worker の中で動いている Claude Code のセッションである（設計 3-1 の worker の定義）。
Status をどう動かすかの判断を持つのはエージェントであり、ボードへ書くのはシステムである（設計 3-25）。

| 語 | 何を指すか |
| --- | --- |
| **引き渡しの選択肢** | 設定に名前が出てくるが、`active_states` にも `terminal_states` にも `tracker.direct_chat_state` にも入っていない Status（既定では `In Review` と `Blocked`） |
| **書き戻しの対象** | 設定に名前の無い Status で、次の4つが揃うもの。書いたのがボードの自動化である・`tracker.automated_state_rewrite` に戻す先がある・書き戻した回数が上限（3回）に達していない・戻せなかった回数が上限（3回）に達していない（`claimAutomatedRewrite`） |
| **印** | 走行中の run の登録（`o.runs`）。外れるとスロットが空く |

## 引き渡しが起きる5つの契機

**引き渡しとは「worker を止めて worktree を残し、人間の操作を待つこと」である**（設計 3-5）。

| 契機 | Status の遷移先 | 引き渡しの通知のコメント |
| --- | --- | --- |
| 表明が review である | review の遷移先（In Review） | 書かない。エージェントのコメントが記録である |
| 表明が blocked である | `status_signal_map` の `blocked` の値（既定は Blocked） | 書かない。エージェントのコメントが記録である |
| max_dispatch_turns に達した | failure_state（Blocked） | continuo が1件書く |
| 進んだ形跡が無いまま打ち切られ、リトライを使い切った | failure_state（Blocked） | continuo が1件書く |
| 設定に名前の無い Status へ動かされた | **動かさない**（利用者の操作を巻き戻さない） | continuo が1件書く |

**ボードの自動化が名前の無い Status へ動かした場合は、引き渡しにならない**（設計 3-54）。
対応表に戻す先があれば書き戻し、**worker は止めない。**

**表明で動かす先は、`review` も `blocked` も `tracker.status_signal_map` の値である**（`表明を読んでStatusを動かす`）。
`tracker.failure_state` を書くのは、continuo が自分で打ち切ったとき（表の3行目と4行目）と、`runを終えてworkerを止める` の `取り戻しの復帰の失敗` と `コメントの取り戻しの失敗` である。

## 取り直した Status と行き先

**turn の終わりの行き先は、取り直した Status だけで決まる**（`internal/orchestrator/lifecycle.go` の `decideAfterTurn`）。見る順は次のとおりである。

| 順 | 取り直した Status | 何が起きるか | この記述のどこか |
| --- | --- | --- | --- |
| 1 | `tracker.direct_chat_state` | 後始末をせずに戻り、次の巡回が direct chat へ入れる | 前提で外した（設計 3-83） |
| 2 | `terminal_states` | run を終える。`cleanup.on_states` なら worktree も片付ける | `完了済みのissue` |
| 3 | `active_states` | 次の turn を送る | `作業中のまま` |
| 4 | 設定に名前が無く、書き戻しの対象である | 戻す先を書いて、次の turn を送る | `turnの終わりの書き戻し` |
| 5 | 設定に名前が無く、書き戻しの対象でない | 理由を issue に書いて run を終える | `turnの終わりの知らないStatus` |
| 6 | それ以外（引き渡しの選択肢） | 成果の報告を確かめて worker を止め、worktree を残す | 基本フロー |

**順6 は、表明で動かした場合に限らない。**エージェントが `gh` で自分で `Blocked` へ動かした場合も、利用者が turn の途中で動かして turn の終わりが先に来た場合も、同じ段を通る。

## 巡回が turn の途中で先に見つけたとき

**turn が動いているあいだも、巡回は30秒ごとに issue を取り直す**（`internal/orchestrator/reconcile.go` の `reconcileRunning`）。
**巡回が先に止めた run は、成果の報告を確かめない。**turn の終わりの処理（基本フロー）とは通る段が違う。

| 巡回が見た Status | 条件 | 何が起きるか | この記述のどこか |
| --- | --- | --- | --- |
| 引き渡しの選択肢 | continuo が最後に書いた値と同じで、turn ループが走っていて、猶予（`tracker.unknown_state_grace_ms`）の内側 | 手を出さない。turn の終わりの処理に任せる（`holdForOwnMove`） | 基本フロー（turn の終わりが先に来る） |
| 引き渡しの選択肢 | 書いたのがボードの自動化で、turn ループが走っていて、猶予の内側 | 手を出さない（`holdForAutomatedMove`） | 基本フロー |
| 引き渡しの選択肢 | 上の2つのどちらでもない（利用者が動かした・エージェントが `gh` で動かした・猶予を過ぎた） | **after_run → pane を閉じる → 印を外す、だけを行う**（`stopAndReleaseAsync`）。バックグラウンド処理の申告を待たず、成果の報告も確かめない | `巡回が先に見つけた引き渡し` |
| 設定に名前が無い | 書き戻しの対象である | 書き戻す。worker は止めない | `自動化の書き戻し` |
| 設定に名前が無い | 書き戻しの対象でなく、猶予が残っている | 止めない。次の巡回で同じ判定をやり直す | `turnの猶予` |
| 設定に名前が無い | 書き戻しの対象でなく、猶予が残っていない | 理由を issue に書いて止める | `知らないStatus` |
| `terminal_states` | 書いたのが自動化でない、または猶予を過ぎた | run を終える（成果の報告は確かめる。`finishRunAsync`） | `issueを1件処理する` |

## 段にしていない分岐

**終わり方も、そのあと通る段も変わらない分岐は、段にせずここへ置く。**

| どこで | 何が起きるか | どうなるか |
| --- | --- | --- |
| 段1 より前（表明を読む前） | 担当者が自分でなくなっている（`tracker.provider.handoff.recheck_interval_ms` に1回だけ確かめる） | after_run を走らせずに pane を閉じる。`issueを1件処理する` の `担当が移った` が受け持つ（前提で外した） |
| 段3 | 取り直した issue がボードから見えない | リトライを積んで pane を閉じる（使い切っていれば `failure_state`）。`issueを1件処理する` の `ボードから消えたissue` が受け持つ |
| `取り直しの失敗` の段2 | 控えてある写しの Status が `active_states` でない | 段4 以降と同じ判定を、その値で通る。**控えは、最後の巡回か、前の turn の終わりが取り直した値である。**表明で引き渡しの選択肢へ書けた直後でも、控えが `running_state` のままなら次の turn を送る（ボードは引き渡しの選択肢、run は走り続ける。次の巡回が `巡回が先に見つけた引き渡し` か基本フローで拾う） |
| `作業中のまま`・`取り直しの失敗`・`turnの終わりの書き戻し` の「継続の指示を送る」 | turn 数が `agent.max_dispatch_turns` に達している | 送らずに `failure_state` へ落とす。`issueを1件処理する` の `上限での打ち切り` が受け持つ |
| `作業中のまま` の「継続の指示を送る」 | 前の turn に表明の行が1行も無かった | 継続の指示に、表明を促す1文が足される（`表明を読んでStatusを動かす` の `表明なし`） |
| `turnの終わりの書き戻し` の段1 | 書き込みが失敗する、既にその値である、item が見えない | どれも run を続け、次の turn を送る。記録のコメントは、ボードが実際に動いたときだけ書く |
| `turnの終わりの書き戻し` の段1 | 利用者が `terminal_states` か `tracker.direct_chat_state` へ動かしていて、書き込みを断られる | その Status で、段4 以降と同じ判定を通る（次の turn は送らない） |
| `turnの終わりの書き戻し` の入口 | 巡回からの書き戻しが既に飛んでいる | 書かずに次の turn を送る。終わらせる処理が走っているなら、turn ループを止めるだけである |
| `自動化の書き戻し` の入口 | 書き戻しの印を取れない（終わらせる処理が走っている・別の書き戻しが飛んでいる） | **書き込みを要求しない。**確保した回数を返して戻る |
| `自動化の書き戻し` の段2 | 既に戻す先の値である／利用者が `terminal_states` か `tracker.direct_chat_state` へ動かしていて断られる | 記録を書かない。**戻せなかった回数にも数えない**（段4 の側ではない）。次の巡回が取り直して判定する |
| `自動化の書き戻し` の段5 | 「戻す先の選択肢がボードに無い」という誤りである | 回数を1つではなく上限ぶん足す（1回で人間へ渡す） |
| `自動化の書き戻し` のあと | 戻せなかった回数が上限に達している | 次の巡回では書き戻しの対象でなくなり、`知らないStatus` へ進む。**5分おきに1度だけ、もう一度試す** |
| `知らないStatus`・`巡回が先に見つけた引き渡し` の「pane を閉じる」 | herdr が pane を閉じ損ねる | **閉じた記録を書かない。**保留も捨てる（`settleClosedRecord`）。あとの段はそのまま続く |
| 段9・`完了済みのissue`・`turnの終わりの知らないStatus` の INCLUDE の中、印を外す前 | 取り直した Status が `cleanup.on_states` に入っている | worktree と branch を片付ける（`finishRunClaimed` だけが行う。`runを終えてworkerを止める` は片付けを段に持たないので、ここに書く）。基本フローでは**前提で外した**（引き渡しの選択肢は `cleanup.on_states` に入っていない） |
| 段9・`turnの終わりの知らないStatus`・`完了済みのissue` の INCLUDE | `runを終えてworkerを止める` が `確かめないrun` で終わる（draft issue、direct chat から直接終端へ抜けた run など） | 成果の報告を確かめずに、after_run → pane を閉じる → 印を外す、まで済ませて終わる。そのあとの段（利用者の段・ABORT）は変わらない |
| 段9・`turnの終わりの知らないStatus`・`完了済みのissue` の INCLUDE | 段9・`turnの終わりの知らないStatus`・`完了済みのissue` の INCLUDE | `runを終えてworkerを止める` が `復元の断念`・`取り戻しの復帰の失敗`・`コメントの取り戻しの失敗` のどれかで終わる | **Status が `failure_state` へ書き換わる**（`terminal_states` のときは書かない）。`turnの終わりの知らないStatus` では、止めた理由の通知を先に投稿しているので、失敗の通知は投稿されない |
| `知らないStatus` のあと | 動いた先の Status が `cleanup.on_states` に入っている | 止めた巡回では片付けない。印が外れたあとの巡回が片付ける（`reconcileWorktrees`） |

## Status を動かしたら、何から何へ動かしたかを残す（設計 3-29）

**言いたいこと。**continuo がボードへ書き込んだときは、**何から何へ動かしたのかを issue に残す。**
**書き込みが起きなかったときは残さない。**

**引き渡しの通知を出す経路では、独立したコメントを作らない。**通知の本文に1行入れる。
**同じことを言うコメントが2件並ぶのを避けるためである。**

| 契機 | 遷移をどこに書くか |
| --- | --- |
| 表明が review / blocked である | **独立したコメントを1件書く**（引き渡しの通知は出ない経路である） |
| max_dispatch_turns に達した | 引き渡しの通知の本文に1行入れる |
| 進んだ形跡が無いまま打ち切られ、リトライを使い切った | 引き渡しの通知の本文に1行入れる |
| 設定に名前の無い Status へ動かされた | **どこにも書かない。**動かしたのは利用者であって continuo ではない |
| ボードの自動化が動かしたので書き戻した | **独立したコメントを1件書く**（書いたのは continuo である。設計 3-54） |

**独立したコメントの本文はこの形である。**`tracker.comments.self_marker` は投稿する側が付ける。

```text
<!-- continuo:self -->
Status を **In Progress → In Review** へ動かしました。

- なぜ: 担当している Claude Code が `CONTINUO-STATUS: review` と表明したためです
- いつ: 2026-08-26 14:03 (JST)
- 書いたのは continuo です（人間の操作ではありません）
```

**引き渡しの通知に入る1行はこれである。**

```text
Status を **In Progress → Blocked** へ動かしました。
```

**「何から」は、書き込む直前に ID 指定で取り直した Status である。**巡回で読んだ時点の値ではない。
**古い値を書くと、この記録そのものが嘘をつく。**

## 設定に名前の無い Status を見つけたとき（設計 3-50）

**設定に名前の無い Status とは、`active_states` / `terminal_states` / `running_state` /
`dispatch_state` / `failure_state` / `status_signal_map` の遷移先のどれにも出てこない Status である。**
`In Review` と `Blocked` は名前が出てくるので、この扱いにはならない。

**「猶予が残っている」とは、次の3つがすべて成り立つことである。**

| 何 | 猶予が残る条件 |
| --- | --- |
| `unknown_state_grace_ms` | 0 より大きい |
| 経過 | 名前の無い Status を最初に見てから、その長さが経っていない |
| turn ループ | 走っている（走っていなければ、待っても表明は出てこない） |

**猶予が残っているあいだは止めない。**次の巡回が同じ判定を頭からやり直す（`turnの猶予`）。
**turn が終わっても名前の無い Status のままなら、その場で止める**（`finishRunUnknownState`。`turnの終わりの知らないStatus`）。

**巡回が止めた run の worktree は、止めた巡回では片付けない。**動いた先の Status が `cleanup.on_states` に入っていれば、
印が外れたあとの巡回が片付ける（`reconcileWorktrees`）。**turn の終わりに止めた run は、その場で片付ける**（`finishRunClaimed`）。

**待つと、利用者が本気で止めたいときに止まるのが turn 1回ぶん遅れる。**
だから待っているあいだ、そのことを記録に残す。

## 書いたのがボードの自動化なら、止めずに戻す（設計 3-54）

**エージェントが PR を作ると、ボードの組み込みの自動化が Status を動かす。**
それを利用者の引き渡しと読むと、**システムが自分のエージェントを turn の途中で殺す**（issue #33）。
**猶予の判定より前に、書いたのが誰かを見る。**

**判定は次の式である。**`Bot` はボードの自動化、`User` は利用者かシステム自身である。

```
自動化が動かした = (actor.__typename == "Bot") || wasAutomated
```

**`wasAutomated` だけでは見分けられない。**組み込みの自動化が動かしたときも偽が返る（設計 2-6 の実測）。

**書き戻すのは、次の4つがすべて成り立つときだけである。**

| 何 | 書き戻す条件 |
| --- | --- |
| 書いた主体 | ボードの自動化である（利用者が動かしたものは戻さない） |
| `automated_state_rewrite` | 動いた先の Status からの戻す先が書いてある |
| 書き戻した回数 | その Status について上限（3回）に達していない |
| 戻せなかった回数 | その Status について上限（3回）に達していない |

**1つでも欠ければ、いままでどおり猶予を置いて止める。**
**書き戻しに失敗しても、その場では止めない。**戻せなかった回数を数え、次の巡回が同じ判定を頭からやり直す（`自動化の書き戻し` の ELSE の側）。
**turn の終わりに書き戻すときは、書き込みが失敗しても run を続け、次の turn を送る**（`rewriteAndDecide`。`turnの終わりの書き戻し`）。

**書き戻した回数を数えるのは、ボードが実際に動いたときだけである。**
通信が失敗した・item がもう見えない・既にその値だった、のいずれでも回数は戻す。
**戻さないと、書き込みが3回失敗しただけで上限に達し、押し合いが1度も起きていない run が止まる。**

**そのかわり、「戻せなかった」は別に数える。**回数を戻すだけだと、
**毎回失敗する書き込みを巡回のたびに永久に打ち続けることになる**
（猶予の時計はその手前で戻ってしまうので始まらない）。
**上限に達したら書き戻しをやめ、猶予を置いて利用者へ渡す。**
これが起きるのは、**利用者がボードから戻す先の選択肢を消したとき**である。

**戻す先は `active_states` に入っていなければならない**（設定の検査が起動前に要求する）。
`terminal_states` や `cleanup.on_states` を戻す先にすると、
**書き戻した瞬間に run が終わるか worktree が消える。**
**したがって、書き戻せたときの行き先はいつも「次の turn へ」である。**

**書き戻せなかったときは、書き込みが取り直した Status で判定し直す。**
利用者が `terminal_states` へ動かしていると書き戻しは断られるので、
**その値で判定しないと、終わった issue へ次の指示を送る。**

## 人間が戻したあとに何が起きるか

| 人間の操作 | 次の巡回でシステムが行うこと |
| --- | --- |
| Status を dispatch_state（Ready）へ戻す | 候補に上がる。worktree を再利用して再 dispatch する |
| Status を `cleanup.on_states`（既定は Done）へ動かす | worktree と branch を片付ける（`レビューの完了`。判定は `terminal_states` ではなく `cleanup.on_states` で行う） |
| Status を動かさない | 何もしない。**pane は既に閉じている。**残るのは worktree と branch である |
