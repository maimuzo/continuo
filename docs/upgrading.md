# 版を上げるとき

**この文書が答えること。**

- **continuo を新しい版に入れ替えたら、`WORKFLOW.md` に何を足せばよいのか**
- **足さないと何が起きるのか**
- **足したかどうかを、どうやって確かめるのか**

**読む前に知っておくこと。**`WORKFLOW.md` は `continuo init` が置いたきり、
continuo が勝手に書き足すことはありません。**あなたが手で足さない限り、新しい版の中身は入りません。**

**`WORKFLOW.md` には2つの部分があり、足さなかったときに起きることが違います。**

| どこ | 何が書いてあるか | 足さないとどうなるか |
| --- | --- | --- |
| **front matter**（先頭の `---` に挟まれた YAML） | continuo の設定 | **壊れません。**既定の値で動きます。**新しい機能が使えないだけです** |
| **本文**（front matter より下） | **その project でだけ効く指示。**エージェントへ送る指示書の真ん中へ挟まります | **あなたが書いた流儀が古いままです。**continuo は本文を書き換えないので、**書いていない指示は届きません** |

**エージェントへ送る指示書のうち、仕組みの部分は continuo の実行ファイルの中にあります。**
**そちらは版を上げれば自動で新しくなるので、手で当てるものはありません。**
**送られる全文は `continuo prompt --show` で読めます。**

## v0.1.13 より前の「本文へこう足してください」は、もう当てないこと

**この文書の v0.1.12 以前の節には、「`WORKFLOW.md` の本文へこの節を足してください」という
差し替えの手順がいくつも書いてあります**（`## worktree と branch は切り替えないこと` /
`## 書いた人によって扱いを変えること` / `## この issue に紐づく PR も読むこと` など）。

**v0.1.13 では、それらは全部、組み込みのプロンプト（continuo の実行ファイルの中）に入っています。**
**版を上げるだけで届くので、本文へ足すものは1つもありません。**
**足すと、同じ指示が組み込みと本文の両方から届きます。**

**古い版から一気に上げる人は、v0.1.12 以前の節の差し替えを飛ばして、
下の「v0.1.13 から v0.1.14 へ」と「v0.1.12 から v0.1.13 へ」だけを読んでください。**
**設定（front matter）の増減は、版ごとの節のとおりに当ててください。**そちらは組み込みには入りません。

**症状から引きたいときは [FAQ.md](FAQ.md) を見てください。**この文書は版から引くものです。

## `continuo init --force` で作り直さないこと

**`--force` は `WORKFLOW.md` を丸ごと雛形で上書きします。**front matter も本文も一緒です。
**片方だけを作り直す形はありません。**

| 消えるもの | どこに書いたものか |
| --- | --- |
| **`continuo setup` で決めた Status の割り当て** | front matter |
| **手で足した設定の行** | front matter |
| **あなたがエージェントへ渡していた指示** | **本文の全文** |

**本文は、あなたが手で書く部分です。**
雛形にも「チームで共有するもの」と書いてあるとおり、**中身はあなたのものであって、
`--force` はそれを1行も残しません。**

**増えた設定は、`--force` ではなく、その行だけを手で足してください**（次の節）。
**どうしても `--force` を打つなら、先に控えを取ってください。**

```bash
cd ~/continuo-work && cp WORKFLOW.md WORKFLOW.md.bak
```

**v0.1.12 から上げる人も、この節のとおりです。**本文の意味は変わりましたが、
**書き直すのは本文だけで、front matter を作り直す理由はありません**
（下の「v0.1.12 から v0.1.13 へ」の「どう直すか」）。

## 何が足りないかは `continuo doctor` が出す

**手で見比べる必要はありません。**`continuo doctor` の `未記入の項目` の行に、
**足りない設定項目の名前**が出ます。

**それを足す差分は、次のコマンドで出します。**

```bash
cd ~/continuo-work && continuo doctor --missing-keys-patch WORKFLOW.md
```

**そのまま当てるなら、`patch` へ渡します。**当てる前に、上のコマンドで差分を読んでください。

```bash
cd ~/continuo-work && continuo doctor --missing-keys-patch WORKFLOW.md | patch -p0 WORKFLOW.md
```

**最後の `WORKFLOW.md` を落とさないでください。**Linux の `patch`（GNU patch）は、
差分の `---` の行が絶対パスだと**「いまいるディレクトリの外を書き換えようとしている」と見なして
差分を捨てます**（`Ignoring potentially dangerous file name` が出て、1行も変わりません）。
**当てる相手をこうして名指しすれば、Linux でも macOS でも当たります。**

**足すだけの差分です。**あなたが書いた行は1つも消えません。
**並び順を変えていても当たります**（差分は雛形ではなく、あなたの `WORKFLOW.md` から組み立てます）。

**当てたあとに何が増えたのかは、下の版ごとの節を読んでください。**
差分には雛形の説明のコメントもそのまま入っていますが、**書かなかったときに何が起きるかは
そちらにしか書いてありません。**

**`--missing-keys-patch` を持たない古い版から上げるときは、雛形を別の場所へ書き出して
見比べてください**（`continuo init` はディレクトリを作らないので、先に作ります）。

```bash
mkdir -p /tmp/continuo-template
continuo init /tmp/continuo-template
diff /tmp/continuo-template/WORKFLOW.md ~/continuo-work/WORKFLOW.md
```

### 同じカンバンを複数の機械で見張っている場合 — 全部同時に入れ替えてください

**何が変わったか。**v0.1.14 まで、continuo は「どの機械が担当しているか」を
issue のコメントに書いた機械の名前（`os.Hostname()` の値）で見分けていました。
**v0.1.15 からは、その機械の `gh` がログインしている GitHub アカウントで見分けます。**

**機械の名前は重複します。**WSL のディストリは既定が Windows のホスト名なので、
`/etc/wsl.conf` に書かないかぎり2つとも同じ名前になります。社内で命名規則に沿って
配られた PC も衝突します。**重複すると、2台とも「自分が勝った」と読みます。**

**そのため、issue に書かれるコメントの中身が変わります。**

```
（v0.1.14 まで）
<!-- continuo:bid -->
{"host": "mac-studio", "five_hour": 87, "weekly": 16, "score": 190, "at": "2026-08-29T16:45:00+09:00"}

（v0.1.15 から）
<!-- continuo:bid -->
{"five_hour": 87, "weekly": 16, "score": 190, "at": "2026-08-29T16:45:00+09:00"}
```

**誰が書いたかは、GitHub がそのコメントに付ける投稿者で分かります。**JSON には入りません。
**hold のコメントからも `host` が消えます**（`assignee` は残ります）。

#### 古いコメントは、そのまま読めます

**v0.1.15 の continuo は、v0.1.14 が書いたコメントを読めます。**
JSON は知らないキーを無視するので、`host` があっても無視されるだけです。
**走っている issue の担当も、そのまま引き継がれます。**

#### 混ざっていると何が起きるか

**v0.1.14 の continuo は、v0.1.15 が書いた入札を1件も数えません。**
古いほうは「機械の名前の無い入札は数えない」という決まりを持っているためです。

| 段 | 何が起きるか |
| --- | --- |
| 1 | **古い機械は自分の入札だけを見て「自分が勝った」と読みます** |
| 2 | 新しい機械は両方の入札を見ます。判定スコアが上なら「自分が勝った」と読みます |
| 3 | **古い機械が先に担当者と hold を書き終えていれば、新しい機械は次の巡回でそれを読んで止まります**（「他人が担当していて、期限内である」と読むためです）。**逆向き（古い機械が新しい機械の hold をどう読むか）は、古い版の判定に依ります** |
| 3の別の道 | **新しい機械の判定スコアが上で、かつ2台が同じ巡回で締め切りを跨いだときは、両方が担当者を書きます。アカウントが別なので、担当者が2人になります**（段4へ続きます）。**新しい機械の判定スコアが下なら、新しい機械は担当者を書かないので、担当者は1人のままです** |
| 4 | **担当者が2人になったときは、両方が hold を書き、両方が着手します。**branch 名は issue から決まるので同じ名前になり、**片方の push が通りません** |
| 5 | **走り出した新しい機械の作業は、そのまま続きます。**担当者に自分が混じっているあいだ、continuo は「担当は自分のまま」と読むためです（**古い機械が止まるかどうかは、古い版の判定に依ります**）。**ダッシュボードの「関門で止めた一覧」には出ませんが、実行中の一覧には出ます** |
| 6 | **両方の作業が終わったあとは、その issue に新しく着手されなくなります。**担当者が2人のままだからです。**あなたが担当者を外すまで戻りません。**issue には何も書かれません。**その issue がもう一度 `Ready` などの着手待ちへ戻ったときに、ログとダッシュボードに出ます** |

**やること。****同じカンバンを見張る機械を、全部 v0.1.15 へ入れ替えてください。**
**走っている issue がある機械は、その run が終わってから入れ替えてください**（v0.1.14 のときと同じです）。

**入れ替え終わったかの確かめ方。**それぞれの機械で叩いてください。

```bash
continuo version
```

**全部が `v0.1.15` 以降になっていれば、混ざっていません。**

**その版で実際に出ていた文面のまま残してあります。**

| どこで見えるか | v0.1.14 まで | v0.1.15 から |

### ロックの置き場所が固定され、`runtime` の節が無くなりました — **2行消してください**

> **上げる前に、動いている continuo を止めてください。**
> **v0.1.14 で、二重起動を止めるロックの置き場所が変わります**（hook の socket と同じディレクトリ →
> `~/.continuo/continuo.lock`）。**止めずに入れ替えると、古い continuo が握っているのは古い場所のロックで、
> 新しい `continuo abandon` が見るのは新しい場所です。**そこは空いているので、
> **`abandon` は「continuo は動いていません」と判定し、走っている worktree を消しにいきます。**
>
> ```bash
> pgrep -fl continuo     # 動いているものを確かめる
> ```
>
> **最後の砦は残っています。**その worktree に herdr の pane が生きていれば `abandon` は止まります。
> **ただし `--force` はそれを越えます。**上げている最中に `--force` を付けないでください。

**v0.1.13 まで。**二重起動を止めるロックは、hook の socket と同じディレクトリに置かれていました。
socket の場所は `CONTINUO_RUNTIME_DIR` / `XDG_RUNTIME_DIR` / `TMPDIR` で動くので、
**launchd から起動した continuo と、端末で叩いた `continuo abandon` が別の場所を見ることがありました。**
食い違うと、`abandon` は動いている continuo を「動いていません」と判定し、
**生きている worktree を消しにいきます。**

**v0.1.14 から。**ロックは `~/.continuo/continuo.lock` の1本に固定されます。
**環境変数でも設定でも動きません。**

**`runtime` の節は消しました。**設定で動かせない以上、置いておく意味がありません。
**読まない項目を残すと、次に読む人が「効いている」と思って設定します。**

#### 何もしないとどうなるか

**起動しません。**front matter は未知のキーを弾くので、次のエラーで止まります。

```
front matter が不正です: [167:1] unknown field "runtime"
（`[167:1]` は、あなたの WORKFLOW.md の何行目かです。数字は人によって違います）
```

#### どう直すか

**`WORKFLOW.md` から `runtime:` の2行を消すだけです。**`continuo init --force` は使わないでください
（front matter も本文も雛形へ戻ります）。

```bash
grep -n -A1 '^runtime:' ~/continuo-work/WORKFLOW.md   # 消す行を確かめる
```

```yaml
runtime:
  lock_file: null    # ← この2行を消す
```

**消したら起動します。**ロックは `~/.continuo/continuo.lock` になります。

#### 1台で2本以上動かしたいとき

**`--id <名前>` を付けてください。**開発中に、本番を止めずにテスト版を動かすためのものです。

```bash
continuo --id e2e ~/continuo-e2e-work
continuo abandon --id e2e <issue の URL> ~/continuo-e2e-work
```

**`--id` が分けるのはロック1本だけです。**worktree の置き場所（`workspace.root`）と
socket（`claude.hook_bridge.listen`）は分かれないので、
**テスト用の `WORKFLOW.md` を別のディレクトリに置いて、そちらで書き換えてください。**

**名前に書けるのは、小文字の英数字とハイフンだけです。**先頭は英数字、32文字まで。

### 同じカンバンを複数の機械で見張っている場合 — 走っている issue があるなら、終わってから入れ替えてください

**1台だけで動かしているなら、この節は読み飛ばしてかまいません。**

**何が起きるか。**v0.1.13 までの機械は、進捗のコメントに `<!-- continuo:progress -->` の印を付けません。
**v0.1.14 の機械から見ると、その issue は「進捗報告が1件も無い」ように見えます。**
そのとき18時間の時計は、担当を取った時刻（`<!-- continuo:hold -->` のコメント）から数えます。

**18時間より長く走っている issue があると、入れ替えた機械が最初の巡回（既定30秒以内）で
その担当を外し、入札をやり直します。**走っていた機械は
`tracker.provider.handoff.recheck_interval_ms`（既定1時間）で気づいて止まるので、
**push していない変更が失われます。**

**先に走っている側を入れ替えても防げません。**引き継ぎでは1回目の指示書を送り直さないので、
**走っている run のエージェントは、その run が終わるまで新しい印を教わりません。**

**やること。****走っている issue がある機械は、その run が終わってから入れ替えてください。**
走っている issue が無ければ、順番は問いません。

### 進捗のコメントが1件にまとまります — 設定に足すものはありません

**複数の機械で同じカンバンを見張っているときだけ関わる話です。**1台で動かしているなら、
issue の見た目が変わるだけです。

**v0.1.13 まで。**エージェントは1時間ごとに**新しいコメントを1件投稿していました**
（`## 長くかかるときは、途中でも状況を書くこと`。持ち回りの18時間の時計を進めるためです）。
**18時間の作業で18件並び、issue を開いても本題が読めませんでした。**

**v0.1.14 から。****いちばん下のコメントが自分の進捗報告なら、その1件に行を書き足します。**

```
<!-- continuo:agent -->
<!-- continuo:progress -->
まだ作業中です。

- 2026-09-03T05:40:34Z いま テストを直しています
- 2026-09-03T06:41:02Z いま PR の指摘に答えています
```

**間に別のコメントが入ったときは、書き足さずに新しく1件投稿します。**
**あなたが書いたコメントを、エージェントが書き潰さないためです。**前の進捗報告はそのまま残ります。

**持ち回りの期限は、書き足しでも進みます。**
GitHub はコメントを編集しても作成時刻を動かしませんが、更新時刻は進みます。
**continuo は v0.1.14 から、コメントの更新時刻も見るようになりました。**

**同時に、18時間の時計を進めるコメントが絞られました。**
**進めるのは `<!-- continuo:progress -->` が入っているコメントだけです。**

**v0.1.13 まで。**時計は「担当者のアカウントが投稿したコメント」で数えていました。
**エージェントも continuo もあなたも、同じ GitHub アカウントで投稿します。**
**だから、あなたが無関係なコメントを1件書くたびに、時計が振り出しに戻っていました。**
**落ちて黙り込んだ機械の担当が、それだけで18時間延びます。**別の機械が拾い直せません。

**v0.1.14 から。****あなたが書いたコメントでは、時計は進みません。**
落ちた機械の担当は、進捗報告が18時間現れなければ予定どおり外れます。
**あなたがこの印をコメントへ書いても構いません。**そのぶん時計が延びるだけで、書く理由はありません。

**当たっているかは、送られる文面で確かめます。****このコマンドは `WORKFLOW.md` を読みません。**

```bash
continuo prompt --show --builtin | grep -c '<!-- continuo:progress -->'
```

**`0` より大きければ入っています。**`0` なら、v0.1.14 より前の continuo が動いています。

**知っておくこと。**担当者が古い進捗報告を1文字直しただけでも、18時間の時計は振り出しに戻ります。
**進捗報告を新しく1件書いたときも同じことが起きます**ので、同じ種類の遅れです。
**進捗報告以外のコメントは、編集しても新しく書いても、時計を1秒も進めません。**

**症状から引きたいときは [FAQ.md](FAQ.md) の
「進捗のコメントが1件にまとまり、増えなくなりました」を見てください。**

### エージェントが PR を作るようになりました — 止められません

**v0.1.13 まで。**`continuo init` が置く本文に、次の節が入っていました。

```markdown
## PR を作るか

**PR は作らないでください。**push まで行い、そこで人間へ渡してください。
```

**この既定は、誰も頼んでいないものでした。**エージェントは push で止まるので、
**branch を自分で見つけて PR を作るのは人間の仕事**になっていました。

**v0.1.14 から。**組み込みのプロンプトに `## 3-5. pull request を出す` が入りました。
**`CONTINUO-STATUS: review` を出す前に、エージェントが自分で PR を作ります。**

**止める口はありません。**本文に「PR を作らない」と書いてあっても、組み込みは「作れ」と指示します。

| エージェントがすること | 中身 |
| --- | --- |
| **既にある PR を先に探す** | いま居る branch（`git branch --show-current`）で引きます。あれば作り直さず、その branch へ push します |
| **無ければ作る** | `gh pr create` を叩きます。**draft にはしません** |
| **本文へ `Closes #<番号>` を入れる** | この1行が PR と issue を結びつけます。**次の turn がレビューの指摘を読む先になります** |
| **作れなかったら `blocked`** | 理由をコメントに書いて、人間へ渡します |

#### 調査だけ・レビューだけを頼んでいる場合

**commit する成果が無い run は PR を作れないので、`Blocked` で止まります。**

**その issue は、continuo に渡さないでください。**
`WORKFLOW.md` の本文に「PR を作らない」と書いても、この版からは効きません。

**確かめ方。**

```bash
cd ~/continuo-work && continuo prompt --show | grep -c 'この issue の pull request を作ります'
```

**`1` なら、組み込みの側に「作れ」という指示が届いています。**
**本文に「PR を作らない」と書いてあると、エージェントは反対の指示を2つ受け取ります。**
**どちらに従うかは決まりません。**確実に作らせたいなら、その行を消してください。

#### 何を変えられるか

**組み込みの決めごとを上書きできるのは、この3つだけです。**`WORKFLOW.md` の本文に書くと、組み込みより優先されます。
**付けるラベルのような、組み込みが何も言っていない決まりは、そのまま本文に書けます。**

| 変えられるもの | 本文へ書く例 |
| --- | --- |
| **draft にするか** | `pull request は draft で作ってください。` |
| **base にする branch** | `base は develop にしてください。` |
| **成果がこの worktree の外にあるときの出し方** | project ごとの手順 |

**「作るかどうか」は、この3つに入っていません。**組み込みの決めごとなので、本文では上書きできません。

### 送られる文面が作り直されました — 本文の見出しを `###` へ下げることを勧めます

**エージェントへ送る指示書を、7つのセクションへ並べ直しました。**

    1. 概要（処理の流れを図で）   5. 共通ルール
    2. 目的                       6. セキュリティ
    3. 手順                       7. その他
    4. 処理に必要なコンテキスト

**あなたが書いた本文は、4-4「このプロジェクトの決まり」の下へ挟まります。**

**やってほしいことが1つあります。****本文の見出しを `##` から `###` へ下げてください。**

**なぜか。**本文が挟まる `## 4-4. このプロジェクトの決まり` は `##` です。
**あなたの本文も `##` で始まっていると、エージェントから見て「4-4 の中身」ではなく

**下げなくても届きます。**内容が消えることはありません。**読み取りやすさの話です。**

### `idle_timeout_ms` を1時間以下にしている人は、起動しません — 一緒に下げてください

**`tracker.provider.handoff.idle_timeout_ms`（担当者の最後の進捗報告からこれだけ経つと担当を外して入札をやり直す間隔。ミリ秒。既定 64800000 = 18時間）を、
1時間（3600000）以下へ下げている人だけが当たります**（**`0` を書いている人は当たりません。**0 は「既定の18時間を使う」という意味です）。
**下げていなければ、この節は読み飛ばしてかまいません。**

**何が起きるか。**v0.1.14 で増えた
`tracker.provider.handoff.progress_interval_ms`（エージェントに進捗報告を書かせる間隔。ミリ秒）の既定が
**3600000（1時間）** で、**`idle_timeout_ms` より短いことを求めます。**
**あなたが1文字も書いていない新しいキーの既定値が、あなたが書いた値とぶつかります。**

```
front matter が不正です: 設定キー tracker.provider.handoff.progress_interval_ms の値 3600000 が不正です: tracker.provider.handoff.idle_timeout_ms（1800000 ミリ秒）より短くすること。長いと、エージェントが指示どおりに書いていても書く前に担当が外れる
```

**なぜ求めるか。**間隔のほうが長いと、**エージェントが指示どおりに書いていても、書く前に担当が外れます。**
そのとき別の機械が入札をやり直し、**push していない変更が失われます。**

**どう直すか。**`progress_interval_ms` を、`idle_timeout_ms` より短い値にしてください。
**60000（1分）以上にすること。**59999 までは、また起動が止まります。

```yaml
tracker:
  provider:
    handoff:
      idle_timeout_ms: 1800000        # 30分（あなたが書いていた値）
      progress_interval_ms: 600000    # 10分（これを足す）
```

**直したかどうかは、次で確かめます。**

```bash
continuo doctor ~/continuo-work
```

**`設定ファイル` の行が `✓` になれば直っています**（画面の言語が英語なら `config`）。

### 進捗報告の間隔を、設定から変えられるようになりました — 既定は1時間ですが、書かなくても起動が止まる人がいます

**v0.1.13 まで。**「1時間以上コメントを書かないまま作業を続けないでください」が、送る文面へ直に書かれていました。
**変えられませんでした。**

**v0.1.14 から。**`tracker.provider.handoff.progress_interval_ms`（エージェントに進捗報告を書かせる間隔。ミリ秒）で変えられます。

```yaml
tracker:
  provider:
    handoff:
      progress_interval_ms: 3600000   # 1時間。既定値
```

**何もしなければ、既定の1時間が使われます。**v0.1.13 と同じ振る舞いです。
**ただし `idle_timeout_ms` を1時間以下にしている人は、書かないままだと起動しません**（上の節）。

**2つの決まりがあります。**

| 決まり | 破ると |
| --- | --- |
| **60000（1分）以上にすること** | 起動しません。**送る文面へは分に直して埋めるので、59999 までは全部「0分以上黙らない」になります** |
| **`idle_timeout_ms`（既定18時間）より短くすること** | 起動しません。**長いと、エージェントが指示どおりに書いていても、書く前に担当が外れます。**`idle_timeout_ms: 0` と書いた場合も、実行時に効く18時間と比べます |

**continuo はこの値を測りません。**送る文面へ分に直して埋めるだけです。
**測っているのは `idle_timeout_ms` のほうだけです。**

**確かめ方。**`continuo prompt --show <ディレクトリ>` を叩くと、実際に送られる全文が出ます。
**標準エラーに出る内訳の `WORKFLOW.md の本文` の行数**（画面の言語が英語なら `WORKFLOW.md body`）**が、
あなたの期待と合っているかを見てください。**

### 応答を差し戻す `Stop` hook との噛み合わせ — 設定は要りません

**用語です。**Claude Code の `Stop` hook は、`{"decision":"block","reason":"…"}` を返すと
**エージェントを止めずに、`reason` を指示として渡して応答を書き直させます。**これを**差し戻し**と呼びます。

**v0.1.12 まで。**差し戻しは hook の**戻り値**なので continuo には届かず、
continuo は「エージェントが止まってよいか尋ねた」という `Stop` を「turn が終わった」と読んでいました。
**書き直しの中央値は 21 秒で、continuo は 2 秒で締め切ります。**結果、
**書き直している最中の pane を閉じる／書き直した応答を読まない／遅れて届いた `Stop` を
次の turn の終わりとして数える**の3つが起きます。

**v0.1.13 から。**締め切りが来た瞬間に herdr へ「このエージェントはまだ動いているか」を1回聞き、
**動いていれば turn の終わりとせずに待ち直します。**

**あなたがすることは何もありません。****`WORKFLOW.md` は1文字も変えません。**
`Stop` hook を1本も入れていない場合も、これまでと同じ速さで turn が終わります
（締め切りの時点でエージェントは止まっているので、聞いた答えは「止まっている」になります）。

### 長くかかるときは途中でも状況を書けという指示 — 設定に足すものはありません

### 入札と担当決定のコメントが、人間にも読める形になりました

**前の版まで、issue に書かれる入札と hold のコメントは JSON 1行だけでした。**
issue を開いた人には `five_hour` が何の値なのかも、次に何が起きるのかも読めませんでした。
**この版から、JSON の下に人間が読む2行が付きます**（担当を外したときのコメントと同じ形です）。

```
<!-- continuo:bid -->
{"host": "mac-studio", "five_hour": 87, "weekly": 16, "score": 190, "at": "2026-08-29T16:45:00+09:00"}

**mac-studio がこの issue の担当に立候補しています。**上の JSON は、その機械にレートリミットの枠がどれだけ残っているかです。
**担当は約3分後に自動で決まります。**締め切りまでに届いた入札のうち、枠の余裕がいちばん大きい機械が担当になります。
```

**「約何分後」は `tracker.provider.handoff.bid_window_ms` から出します。**分に切り上げるので、
既定の 180000 ミリ秒は「約3分後」になります。**0 にしてあるときは「締め切りを待たずに決まります」と出ます。**

**このコメントはエージェントへは渡しません。**今までどおり、issue を GitHub の画面で開いたときだけ見えます。

### issue にリンクした branch が、作業の起点になりました

**GitHub の issue の Development に branch をリンクしておくと、continuo はその branch を起点に
worktree を作ります**（今までは、いつでもリポジトリの既定 branch が起点でした）。
**手元の clone にその branch がまだ無ければ、その1本だけを取ってきます。**

**起点に使うのは「リンクがちょうど1本で、それが issue と同じリポジトリの branch」のときだけです。**
次のどれかに当たるときは、今までどおり既定 branch が起点になります。
**リンクを付けていないカンバンでは、何も変わりません。**

| どういうとき | 例 |
| --- | --- |
| **リンクが無い** | — |
| **リンクが2本以上ある** | どれを起点にするか決められません |
| **別のリポジトリの branch を指している** | fork の branch をリンクした |
| **branch 名に英数字・`_`・`-`・`.`・`/` 以外が入っている** | `作業/issue-42`・`feature/a+b` |

**どれに当たったかはログに WARN で1行出ます。**着手は止めないので、
**気づく手掛かりはこの1行だけです。**

```bash
grep 'リンクされた branch' <ログの出力先>
```

**リンクした branch を手元へ取ってこられなかったときは、着手そのものをやり直します。**
既定 branch へ黙って倒すことはしません（別の起点で作業が始まってしまうためです）。
**`agent.max_retries`（既定3回）まで待って試し直し、それでも取ってこられなければ
`failure_state` へ落として issue に理由を書きます。**回線が一時的に切れただけなら、
次の巡回で通ります。

**プロンプトのテンプレートで `{{.push_branch}}` が使えるようになりました。**リンクされた
branch の名前がそのまま入ります（`origin/` は付きません）。リンクが1本でないときは空文字なので、
`{{if .push_branch}}` で書き分けられます。**足さなくても今までどおり動きます。**

**上の表に当たったものが、全部空になるわけではありません。**空になるのは
**リンクが無いとき・2本以上あるとき・別のリポジトリの branch を指すとき**の3つです。
**branch 名に使えない文字が入っているとき（`作業/issue-42`）は、起点には使いませんが、
`{{.push_branch}}` にはその名前がそのまま入ります。**起点と push 先が別々に決まるためです。

### push 先を分けた worktree が片付くようになりました

**当てなくても壊れません。**片付けの判定は continuo の側にあるので、この版に上げた時点で効きます。
**本文を当てるかどうかは、エージェントに `-u` を付けさせるかどうかの話です。**

**前の版で何が起きていたか。**エージェントが2本目の PR を出すときなどに、
別の名前へ push することがあります。

```bash
git push origin HEAD:pr-2nd
```

**この形は upstream を張り替えません。**upstream は worktree を作ったときのままなので、
片付けは失うものが残っていると判定し、**その worktree は永久に片付きませんでした。**
**出るメッセージは2通りあります。**1本目の push で upstream が張られていれば
「push されていない commit が N 件残っている」、一度も張られていなければ
「upstream が無いまま base … との差分が残っている」です。

**この版から、判定の最初の段が「HEAD が `refs/remotes/` のどれかに載っているか」を見ます。**
載っていれば、upstream が古くても消してよいと判定します。
**通信はしません。**`refs/remotes/` は手元にある ref です。

**base との差分で判定する段は残してあります。**remote を1つも持たない clone では
`refs/remotes/` が空になり、最初の段が常に偽になるためです。

| `recheck_interval_ms` | `3600000`（1時間） | 走っている最中に担当を確かめ直す間隔。担当が移っていたら、その turn の終わりで止めて push しない |
| `five_hour_margin_percent` | `10`（%） | 5時間の枠のうち、continuo のために残しておきたい割合 |
| `weekly_margin_percent` | `10`（%） | 1週間の枠のうち、continuo のために残しておきたい割合 |

**`tracker.provider.handoff` セクションを丸ごと書かなくても、この5つの既定値がそのまま使われます。**
壊れません。**書いていないことに気づく手段は、`continuo doctor` の `未記入の項目` の行だけです**
（下の「足したかどうかの確かめ方」）。

**何が変わって見えるか。**

- **担当者のいない issue に、`<!-- continuo:bid -->` と `<!-- continuo:hold -->` のコメントが付くようになります。**
  1台構成でも付きます。**このコメントはエージェントへは渡りません**（issue を GitHub の画面で開いたときだけ見えます）
- **複数の機械で見張っている場合、枠の使用率がいちばん低い1台に処理が集まります**
  （判定の中身は [docs/FAQ.md](FAQ.md) の「複数の機械で見張っているのに…」を見てください）
- **担当している機械が `idle_timeout_ms`（既定18時間）のあいだ進捗報告を書かないと、ほかの機械が担当を外して入札をやり直します**
- **既に人間が担当者になっている issue は、上げた時点で着手されなくなります。**
  continuo は、その PC の `gh` の持ち主とは違うアカウントが担当者になっている issue には触りません。
  **着手させるには、GitHub の画面でその担当者を外してください。**
  逆に、その PC の `gh` の持ち主を担当者にしておくと、その PC が着手します

  （v0.1.11 からは、**着手されなくなったこと**を WARN で知らせます。それより前の版では**ログに INFO が1行出るだけ**です。
  詳しくは [docs/FAQ.md](FAQ.md) の「人間が担当者になっている issue が、いつまでも着手されない」を見てください）

### `tracker.automated_state_rewrite` — 自動化に動かされた Status を戻す

**何のためのものか。**GitHub Projects の**組み込みの自動化**（`Pull request linked to issue` /
`Pull request merged` など）が Status を書き換えたときに、**continuo が意図した Status へ戻す**ための対応表です。
新しく作ったボードでは、これらの自動化が有効な状態で作られます。

**書かないとどうなるか。**

| | 書かない場合 | 書いた場合 |
| --- | --- | --- |
| **自動化に Status を動かされたら** | **猶予（`tracker.unknown_state_grace_ms`、既定10分）を置いて worker を止める** | **本来の Status へ戻して、止めずに続ける**（戻すのは3回まで） |
| **人間が Status を動かしたら** | 猶予を置いて止める | **猶予を置いて止める**（変わりません） |
| **起動** | 通ります | 通ります |

**壊れません。**書かないと、いままでどおり止まるだけです。**新しい機能が使えないだけです。**

**書き戻しは無制限ではありません。****同じ issue の同じ Status を戻せるのは3回まで**です。
continuo が戻すたびに自動化が書き直す押し合いになったら、**3回でその issue の書き戻しをやめ、
いままでどおり猶予を置いて worker を止めます**（そこから先は人間が決めます）。
そのとき issue のコメントに、押し合いが起きたことと、`Workflows` を切る手が案内されます。

### 足す場所と中身

**`tracker:` の下に足します。**`continuo init` が置いた雛形の Status 名のままなら、
次の2行をそのまま貼れば起動します。

```yaml
tracker:
  automated_state_rewrite:
    "Todo": "In Progress"   # 自動化が書く Status: 戻す先の Status
```

**Status の名前は、あなたのボードと `WORKFLOW.md` に合わせて置き換えてください。**上の例は
「自動化が `Todo` を書いたら、`In Progress` へ戻す」という意味です。
**`Todo` は GitHub が既定で作る選択肢です。**ボードから消してあるなら
`! 対応表のキー` が出ますが、**起動は止まりません**（下の「足したあとの確かめ方」を見てください）。

**左に、`tracker` の他のキーで使っている Status 名を書くと起動しません。**
雛形のままなら `Ready` / `In Progress` / `Done` / `Blocked` / `In Review` の5つが該当します。
たとえば `"In Progress": "AI In Progress"` を足すと、`continuo doctor` がこう言います。

```text
✗ 設定ファイル    … 設定キー tracker.automated_state_rewrite のキー の値 In Progress が不正です:
  tracker の他のキー（active_states / terminal_states / running_state / dispatch_state /
  failure_state / status_signal_map の遷移先）に無い Status 名にすること
```

**自動化が書く Status が `tracker` の他のキーに既に書いてあるなら、対応表は要りません。**
continuo が知っている Status なので、そもそも止まらないからです。

| --- | --- | --- |
| **左（キー）** | **`tracker` の他のキーに名前が出てこない Status。**自動化が書く Status 名です | **continuo が起動しません** |
| **右（値）** | **`tracker.active_states` に入っている Status** | **continuo が起動しません** |

`dispatch_state` / `failure_state` / `status_signal_map` の遷移先。
**`tracker` の外（`cleanup` など）は見ません。**

**どちらも起動時に弾かれます。**貼ってから気づけるので、当てずっぽうで書いても手元は壊れません。

**左が `active_states` などに書いてあると、その行は1度も効きません。**
書き戻しを引くのは「continuo が知らない Status になったとき」だけだからです。
**右が `terminal_states` だと、戻した瞬間に片付けが走ります。**だから両方とも弾きます。

**`continuo doctor` の `対応表のキー` の行を読みます。****記号だけで判断しないでください。**

```bash

| 記号のうしろに出る文 | どう読むか |
| --- | --- |
| `tracker.automated_state_rewrite は空です（書き戻しを行わない設定です）` | **足せていません。**別のファイルを編集したか、`tracker:` の下に置けていません |
| `tracker.automated_state_rewrite のキーはすべてカンバンの Status の選択肢にあります（1件）` | **足せています。**括弧の中の件数が、書いた行数と合っているかも見てください |
| `tracker.automated_state_rewrite のキーに、カンバンの Status の選択肢に無いものがあります（1件）` | 足せてはいますが、**綴りがカンバンと違うか、その Status をカンバンで使わなくなっています** |

**上の2つは `✓`、いちばん下は `!` です。**
**`!` のままでも continuo は起動します**（終了コードも 0 です）。
直し方は [FAQ.md](FAQ.md) の「doctor が通らないとき」にあります。

**`✗ 設定ファイル` が出たときは、対応表そのものが弾かれています。**
左右の決め方をもう一度読んでください。**この場合 continuo は起動しません。**

**書き換えたら continuo を再起動してください。**動いている最中は設定を読み直しません。

### 足したくない場合

**ボードの側で自動化そのものを止める手もあります。**
ボードの `Workflows` の設定から、動いてほしくない自動化を無効にしてください。
**そうすれば Status は横取りされないので、対応表も要りません。**

**どちらか一方でかまいません。**両方やっても構いませんが、片方で足ります。

**ただし、そのボードを人間も使っているなら、対応表のほうを勧めます。**
`Workflows` を切ると、continuo と関係なくボードを見ている人の使い勝手も変わります。
**continuo を入れたことが、人間の設定を変える理由になってはなりません。**
