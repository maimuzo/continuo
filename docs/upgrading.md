# 版を上げるとき

**この文書が答えること。**

- **continuo を新しい版に入れ替えたら、`WORKFLOW.md` に何を足せばよいのか**
- **足さないと何が起きるのか**
- **足したかどうかを、どうやって確かめるのか**

**読む前に知っておくこと。**`WORKFLOW.md` は `continuo init` が置いたきり、
continuo が勝手に書き足すことはありません。**あなたが手で足さない限り、新しい版の中身は入りません。**

**`WORKFLOW.md` には2つの部分があり、足さなかったときに起きることが違います。**

| どこ | 何が書いてあるか | 足さないとどうなるか |
| --- | --- | --- |
| **front matter**（先頭の `---` に挟まれた YAML） | continuo の設定 | **壊れません。**既定の値で動きます。**新しい機能が使えないだけです** |
| **本文**（front matter より下） | **その project でだけ効く指示。**エージェントへ送る指示書の真ん中へ挟まります | **あなたが書いた流儀が古いままです。**continuo は本文を書き換えないので、**書いていない指示は届きません** |

**エージェントへ送る指示書のうち、仕組みの部分は continuo の実行ファイルの中にあります。**
**そちらは版を上げれば自動で新しくなるので、手で当てるものはありません。**
**送られる全文は `continuo prompt --show` で読めます。**（前の回のあとに人間が書いたコメントを付ける節は、送る直前に issue のコメントから組み立てるので、ここには出ません）

## v0.1.13 より前の「本文へこう足してください」は、もう当てないこと

**この文書の v0.1.12 以前の節には、「`WORKFLOW.md` の本文へこの節を足してください」という
差し替えの手順がいくつも書いてあります**（`## worktree と branch は切り替えないこと` /
`## 書いた人によって扱いを変えること` / `## この issue に紐づく PR も読むこと` など）。

**v0.1.13 では、それらは全部、組み込みのプロンプト（continuo の実行ファイルの中）に入っています。**
**版を上げるだけで届くので、本文へ足すものは1つもありません。**
**足すと、同じ指示が組み込みと本文の両方から届きます。**

**古い版から一気に上げる人は、v0.1.12 以前の節の差し替えを飛ばして、
下の「v0.1.13 から v0.1.14 へ」と「v0.1.12 から v0.1.13 へ」だけを読んでください。**
**設定（front matter）の増減は、版ごとの節のとおりに当ててください。**そちらは組み込みには入りません。

**症状から引きたいときは [FAQ.md](FAQ.md) を見てください。**この文書は版から引くものです。

## `continuo init --force` で作り直さないこと

**`--force` は `WORKFLOW.md` を丸ごと雛形で上書きします。**front matter も本文も一緒です。
**片方だけを作り直す形はありません。**

| 消えるもの | どこに書いたものか |
| --- | --- |
| **`continuo setup` で決めた Status の割り当て** | front matter |
| **手で足した設定の行** | front matter |
| **あなたがエージェントへ渡していた指示** | **本文の全文** |

**本文は、あなたが手で書く部分です。**
雛形にも「チームで共有するもの」と書いてあるとおり、**中身はあなたのものであって、
`--force` はそれを1行も残しません。**

**増えた設定は、`--force` ではなく、その行だけを手で足してください**（次の節）。
**どうしても `--force` を打つなら、先に控えを取ってください。**

```bash
cd ~/continuo-work && cp WORKFLOW.md WORKFLOW.md.bak
```

**v0.1.12 から上げる人も、この節のとおりです。**本文の意味は変わりましたが、
**書き直すのは本文だけで、front matter を作り直す理由はありません**
（下の「v0.1.12 から v0.1.13 へ」の「どう直すか」）。

## 何が足りないかは `continuo doctor` が出す

**手で見比べる必要はありません。**`continuo doctor` の `未記入の項目` の行に、
**足りない設定項目の名前**が出ます。

**それを足す差分は、次のコマンドで出します。**

```bash
cd ~/continuo-work && continuo doctor --missing-keys-patch WORKFLOW.md
```

**そのまま当てるなら、`patch` へ渡します。**当てる前に、上のコマンドで差分を読んでください。

```bash
cd ~/continuo-work && continuo doctor --missing-keys-patch WORKFLOW.md | patch -p0 WORKFLOW.md
```

**最後の `WORKFLOW.md` を落とさないでください。**Linux の `patch`（GNU patch）は、
差分の `---` の行が絶対パスだと**「いまいるディレクトリの外を書き換えようとしている」と見なして
差分を捨てます**（`Ignoring potentially dangerous file name` が出て、1行も変わりません）。
**当てる相手をこうして名指しすれば、Linux でも macOS でも当たります。**

**足すだけの差分です。**あなたが書いた行は1つも消えません。
**並び順を変えていても当たります**（差分は雛形ではなく、あなたの `WORKFLOW.md` から組み立てます）。

**当てたあとに何が増えたのかは、下の版ごとの節を読んでください。**
差分には雛形の説明のコメントもそのまま入っていますが、**書かなかったときに何が起きるかは
そちらにしか書いてありません。**

**`--missing-keys-patch` を持たない古い版から上げるときは、雛形を別の場所へ書き出して
見比べてください**（`continuo init` はディレクトリを作らないので、先に作ります）。

```bash
mkdir -p /tmp/continuo-template
continuo init /tmp/continuo-template
diff /tmp/continuo-template/WORKFLOW.md ~/continuo-work/WORKFLOW.md
```

## v0.2.1 から v0.2.2 へ

**要点だけを読みたいときは、[FAQ.md](FAQ.md) の「v0.2.1 から v0.2.2 へ上げるとき」を先に読んでください。**

**`WORKFLOW.md` に足すものも、消すものもありません**（カンバンの自動化を有効にしていて、`tracker.automated_state_rewrite` が空の人を除きます。下の「pull request が、最初の push のときに draft で作られます」を読んでください）。下の表の6つで変わるのは、組み込みの指示書（continuo が Claude Code へ送る指示）だけです。**表の6つの節のあとに、`tracker.automated_state_rewrite` の変更が1つと、表明（`CONTINUO-STATUS:`）まわりの変更が2つ続きます。**そちらは continuo 本体と `continuo hook` の動きも変わるので、それぞれの節を読んでください。

| 何が変わったか | 設定の書き換え |
| --- | --- |
| **分岐元の取り込みで衝突しても、両方の変更を残せるなら、エージェントが解いて進みます** | 要りません |
| **エージェントが書く時刻が、機械のタイムゾーンになりました** | 要りません |
| **終わりの報告の前に、エージェントが受けた指示を読み直して分けます** | 要りません |
| **レビュワーと、直しを任せる subagent が、issue と pull request のコメントを全部読みます** | 要りません。**レートリミットの減りが増えます** |
| **pull request が、最初の push のときに draft で作られます** | 要りません。**本文に「draft で作らない」と書いていても、作業中は draft になります** |
| **エージェントが、push の前に issue の担当を確かめます** | 要りません。**`gh` とカンバンのトークンが別のアカウントの人は、揃えてください** |

### 取り込みで衝突しても、解ける衝突なら止まりません

**v0.2.1 まで。**分岐元の取り込みで衝突すると、エージェントは中身を見ずに戻し、Status を `Blocked` にして人間に訊いていました。
両方の branch が `.gitignore` の末尾へ別の行を足しただけの衝突でも、1往復かかっていました。

**v0.2.2 から。**衝突した箇所の全部で両方の変更をそのまま残せるなら、解いて commit し、作業を続けます。
1箇所でも判断が要るなら（同じ行を別の内容へ変えている・片方が消して片方が変えている・両方残すと壊れる・生成されたファイルやロックファイル）、いままでどおり戻して止まります。
**どのファイルをどう解いたかは、報告のコメントと merge commit に残ります。**

### エージェントが書く時刻が、機械のタイムゾーンになりました

**v0.2.1 まで。**途中経過のコメントの時刻だけが UTC（`2026-09-07T02:10:57Z`）で、continuo 自身のコメント（`2026-09-04 14:22 (JST)`）と混ざっていました。

**v0.2.2 から。**エージェントも `2026-10-05 02:23 (JST)` の形で、機械のタイムゾーンで書きます。
**時間帯を選ぶ設定は足していません。**continuo は、時刻をその機械のタイムゾーンで書くと決めています。別の時間帯で書かせたいときは、機械のタイムゾーンを変えてください。
ずれる場合は [FAQ.md](FAQ.md) の「エージェントが書く時刻と、continuo が書く時刻がずれている」にあります。

### 終わりの報告に、まだ実行していない指示が並びます

エージェントは、報告のコメントを書く前に issue と pull request のコメントを読み直し、受けた指示を1件ずつ
「実行した」「まだ実行していない」「後の指示で取り消された」に分けます。
**「実行した」以外は、報告に理由と一緒に書かれます。**1件も無ければ「実行していない指示はありません」と書かれます。
**拾うのは、OWNER / MEMBER / COLLABORATOR が AI の印を付けずに書いた指示だけです。**

### レビューのたびに、subagent がコメントを全部読みます。**レートリミットの減りが増えます**

**v0.2.1 まで。**レビュワーへ渡す経緯は、前の周で「直さない」と決めた指摘とその理由だけでした。
過去の周で否定した方向と、その理由がレビュワーにも直す側にも届かず、同じ方向の指摘がまた出ることがありました。

**v0.2.2 から。**レビュワーの全部の役と、直しを任せる subagent へ、issue と pull request の URL を渡して、本文とコメントを1件残らず読ませます。
**コメントの多い issue ほど、1周あたりの消費が増えます。**
Bash を持たない subagent（`WORKFLOW.md` の本文の「レビューを頼む subagent」に、道具が `Read` / `Grep` / `Glob` だけのものを書いている場合）には、
エージェントがコメントをファイルへ書き出して渡します。

### pull request が、最初の push のときに draft で作られます

**v0.2.1 まで。**pull request は、実装が終わってから作っていました。途中で担当が別の機械へ移ると、次の機械に見えるのは branch の commit だけでした。

**v0.2.2 から。**エージェントは、最初に commit を push した直後に、pull request を draft で作ります。実装が終わると、題名と本文を書き直します。

| あなたの `WORKFLOW.md` の本文 | どうなるか |
| --- | --- |
| **draft について何も書いていない** | 作業中は draft。実装レビューが収まると外れます |
| **「draft で作る」と書いている** | 同じです |
| **「draft で作らない」と書いている** | **作業中は draft になります。**実装レビューが収まると外れるので、人間へ渡るときの状態は変わりません。**10周で収まらなかったときと、人間に訊くことが出て止まったときは、draft のまま残ります** |
| **「draft のまま人間へ渡す」と書いている** | いままでと同じで、外れません |

**カンバンの自動化（`Pull request linked to issue`）を有効にしている人へ。**pull request ができる時機が実装の途中へ動いたので、自動化が Status を書き換える時機も動きます。
`tracker.automated_state_rewrite` に対応を書いていれば、continuo が書き戻して続けます。**空のままだと、continuo の知らない Status になった約10分後（`tracker.unknown_state_grace_ms`）に、実装の途中で run が止まります。**
v0.2.1 までは、同じカンバンで、実装が終わって pull request を作った直後に止まっていました。
直し方は [FAQ.md](FAQ.md) の「エージェントが PR を作った直後に止まる（automated_state_rewrite）」にあります。`continuo doctor` が、対応表が空であることを出します。

**雛形の「pull request の決まり」のコメントも、この形に合わせて直しました。**あなたの `WORKFLOW.md` は書き換わりません。直さなくても動きます。
CI への影響と、途中の本文の扱いは [FAQ.md](FAQ.md) の「pull request が、実装の途中なのに作られている」にあります。

### エージェントが、push の前に issue の担当を確かめます

**なぜ足したか。**continuo は、走っている issue の担当が別の機械へ移っていないかを確かめています。**continuo が落ちているあいだは、確かめられません。**
そのあいだに担当が移ると、元のエージェントが、新しい担当の branch へ push していました。

**v0.2.2 から。**エージェントは、着手のときと push の前に、`gh api user` と `gh issue view … --json assignees` で担当を確かめます。

| 確かめた結果 | エージェントがどうするか |
| --- | --- |
| **自分が担当者に入っている** | 進めます |
| **担当者が1人もいない** | 進めます |
| **別の人だけが担当になっている** | push せずに止まります（Status が `Blocked` になります）。報告に、いまの担当と、push していない commit の在りかを書きます |
| **確かめられない**（`gh` が落ちる） | 着手のときと、作業を終える前の push の前なら、push せずに止まります。途中の push の前なら、その回の push を見送って作業を続けます |

**`tracker.provider.token_source: env` で、`gh` のログインとは別のアカウントのトークンを渡している人は、揃えてください。**
揃えないと、毎回「別の人が担当になっている」になり、着手の直後に止まります。
**走っている issue の担当を手で付け替えるときは、先に元の機械の continuo を止めてください。**理由は [FAQ.md](FAQ.md) の「走っている issue の担当を手で付け替えたら、Status が `Blocked` になり、新しい担当の作業も止まった」にあります。

### `tracker.automated_state_rewrite` は、人間が動かしたときも戻すようになりました

**当たるのは、`tracker.automated_state_rewrite` に1行でも書いている人だけです。**
空（`{}`）のままの人には、何も起きません。

**何が変わったか。**着手中の issue が、対応表の左に書いた Status へ動いたら、
**誰が動かしたかを見ずに**、右の Status へ書き戻します。

| | v0.2.1 まで | v0.2.2 から |
| --- | --- | --- |
| **カンバンの自動化が、左の Status へ動かした** | 右の Status へ戻す。**ただし GitHub が記録を残さなかった回は、戻さずに止めていました** | **右の Status へ戻す**（記録の有無に関わらず） |
| **人間が、左の Status へ動かした** | 猶予を置いて止める | **右の Status へ戻す** |
| **戻したときに issue へ書くコメント** | 「カンバンの組み込みの自動化（`github-project-automation`）が Status を動かし…」 | 動かした主体を書きません。止め方（`tracker.failure_state` の Status へ動かす）を書きます |

**なぜ変えたか。**continuo は「誰が Status を動かしたか」を、GitHub が issue に残す記録から読んでいました。
**GitHub はその記録を残さないことがあります**（2026-10-04 に確かめました）。
記録が無い回は「人間が動かした」と読むので、**対応表に書いてあっても、戻さずにエージェントを止めていました。**

**何をすればよいか。**

| 当たる人 | 何をするか |
| --- | --- |
| **左に書いた Status へ、人間が「止める」つもりで動かしている人** | **止める先を変えてください。**`tracker.failure_state` の Status（雛形では `Blocked`）へ動かせば、戻されずに止まります。左に書いた Status は、誰が動かしても戻されます |
| **左に書いた Status を、`cleanup.on_states` にも書いている人** | **片付けさせたいなら、対応表からその行を消してください。**戻されているあいだは片付きません |
| **`continuo abandon --park` に、左に書いた Status を渡している人** | **断られるようになりました**（「`--park` に指定した … は tracker.automated_state_rewrite のキーです」）。`--park` を省くか、`tracker.failure_state` の Status を渡してください |
| **それ以外の人** | 何もしなくて構いません |

**`WORKFLOW.md` に足すものはありません。**設定のキーは増えていません。

**手元の `WORKFLOW.md` の説明が古くなります。**`continuo init` が置いた雛形は、
`automated_state_rewrite` の行の横に「人間が動かしたものは戻さない」と書いていました。
**continuo は `WORKFLOW.md` を書き換えないので、その説明はあなたのファイルに残ります。**
気になる人は、次の説明へ差し替えてください（差し替えなくても動きは同じです）。

```yaml
  automated_state_rewrite: {}               # カンバンの自動化に Status を動かされても、エージェントを止めずに続けさせるための設定。
                                            # カンバンの Settings → Workflows で Status を書く自動化を1つも有効にしていないなら、
                                            # 空のままでよい。有効にしているなら書く。
                                            # 着手中の issue がここに書いた Status へ動いたら、右に書いた Status へ戻す
                                            # （組み込みの自動化は、PR を issue に紐づけた・PR をマージした等で Status を動かす）。
                                            # 誰が動かしたかは見ない。人間がその Status へ動かしたときも戻す
                                            # （止めたいときは、上の failure_state の Status へ動かす）。
                                            # 戻すのは1件の着手につき、1つの Status あたり3回まで。空なら戻さず、上の猶予を置いてから worker を止める。
```

**上の yaml は説明の文面の図です。塊ごと貼り替えないでください。**`automated_state_rewrite:` の行は
既にあるので、**貼ると front matter が重複キーになり、continuo が起動しなくなります。**
**差し替えるのは、コメントのうち次の3行だけです**（「組み込みの自動化（PR を issue に紐づけた…」
「Status を動かしたときだけ、…」「空なら戻さず、…人間が動かしたものは戻さない。」）。
**前後の行（「カンバンの Settings → Workflows で…」と「書くときは…」以降）と、
あなたが書いた対応表（`{}` の代わりに並べた行）は、そのまま残してください。**

**戻す回数の数え方が変わります。**上限は、1件の着手につき、1つの Status あたり3回のままです。
**v0.2.2 からは、人が動かした回も同じ枠で数えます**（v0.2.1 までは、人が動かした回は戻さなかったので、数えてもいませんでした）。
自動化が3回動かしたあとに人が1回動かすと、その1回で止まります。

**変わらないこと。**

- 対応表に無い Status へ動いたときは、いままでどおり猶予を置いて止めます。
- 自動化が `Done` などへ動かしたときに turn の終わりまで待つ仕組みは、GitHub の記録に頼ったままです。**記録が無い回は、待たずに止めます。**

**限りと、止まったときの戻し方は [FAQ.md](FAQ.md) の
「エージェントが PR を作った直後に止まる（automated_state_rewrite）」にあります。**

### エージェントが `CONTINUO-STATUS:` に決まり以外の値を書くと、取り得る値の一覧が返るようになりました — 設定に足すものはありません

**何が変わったか。**エージェントが `CONTINUO-STATUS: done` のように、`tracker.status_signal_map` に無い値を書いたとき、
continuo は書いた値と取り得る値の一覧をエージェントへ返します。**いままでは値を無視して「続けてください」を送っていました。**

| 変わったもの | 中身 |
| --- | --- |
| **`continuo hook` が `Stop` を差し戻すことがある** | 応答の最後のテキストに決まり以外の表明が在ると、標準出力へ `{"decision":"block","reason":"…"}` を返します。Claude Code は turn を終えず、エージェントが同じ turn の中で書き直します。**1つの turn で1回だけです。**終了コードは 0 のままで、引数（`--socket` / `--pending-dir`）も変わりません |
| **継続の指示の文面** | 決まり以外の値を書いた turn の次は、「続けてください」の代わりに、書いた値と一覧を送ります。表明が1行も無かったときの指示にも、一覧と「行頭から1行で」を足しました。**決まりどおりの値を書いた turn の次の文面は変わっていません** |
| **issue ごとのディレクトリにファイルが1つ増える** | `<実行時ディレクトリ>/issues/<issue>/status-signal.json`。hook が読む、取り得る値の一覧です。着手のときと、continuo を立て直して run を引き継ぐときに書き、片付けで消します |

**上げるときにすること。**設定に足すものはありません（下の「`status_signal_map` を自分で書いている場合」だけは確かめてください）。
**上げたあと、continuo を立て直してください。**上げる前に着手した run には `status-signal.json` が無く、
hook は何も調べません（いままでと同じ出力です）。立て直すと、引き継いだ run にもファイルが書かれ、hook が効き始めます。

**`status_signal_map` を自分で書いている場合。`working: null` が在るかを確かめてください。**
`WORKFLOW.md` に `status_signal_map` を書くと、既定の対応表は丸ごと置き換わります。`working` を書いていなければ、対応表に `working` はありません。
**いままでは、それでも困りませんでした。**エージェントが `CONTINUO-STATUS: working` と書くと、continuo は値を無視して「続けてください」を送っていたので、`working: null` と同じ動きでした。
**v0.2.2 からは、`working` も決まり以外の値として一覧が返ります。**作業は止めさせませんが（「まだ作業が続くなら、表明は書かずに、そのまま作業を続けてください」と返します）、エージェントが `working` と書くたびに書き直しを求めることになります。

```yaml
tracker:
  status_signal_map:
    review: "In Review"
    blocked: "Blocked"
    working: null      # ← これが無ければ足す。Status を動かさない値
```

`continuo init` の雛形には、はじめから入っています。

**`tracker.status_signal_map` か `tracker.status_signal_prefix` を書き換えるとき。**書き換えたら continuo を立て直してください
（もともと、立て直さないと効かない項目です）。立て直すと、引き継いだ run の hook が見る一覧も新しくなります。
**立て直しで引き継がなかった pane**（人間へ引き渡したあとに残っている pane など）**は、古い一覧のままです。**
その pane を閉じるか、その issue に着手し直すと揃います。

**v0.2.1 以前へ戻すとき。**古い `continuo hook` は `status-signal.json` を読まないので、残っていても害はありません。消す必要もありません。

**あなたが `Stop` hook を入れている場合。**`Stop` hook は並行して走るので、1本目の `Stop` では、あなたの hook と continuo の hook の両方が調べます。
両方が差し戻すと、エージェントには2つの指示が同時に届きます。**差し戻されて書き直したあとの `Stop` では、continuo の hook は調べません**
（どの hook が差し戻したあとでも同じです）。書き直した応答の値がまだ決まり以外なら、次の turn の指示で一覧が届きます。

### `blocked` か `review` を書く前に、エージェントがバックグラウンドの処理を終わらせるようになりました — 設定に足すものはありません

**何が変わったか。**continuo がエージェントへ送る組み込みのプロンプトの「3-7. 終わりを書く」に、次の決まりが入りました。

> **`blocked` か `review` を書く前に、バックグラウンドで動かしたコマンドと subagent を全部終わらせてください。**

**なぜ要るか。**continuo は、バックグラウンドの処理が1つでも残っているあいだ、turn が終わったとみなしません。
`CONTINUO-STATUS:` を読むのは turn が終わったあとなので、**残したまま `blocked` を書くと、Status がいつまでも `Blocked` へ動きませんでした。**
`working` には当てていません（バックグラウンドで回したまま応答を返してよい表明です）。

## v0.2.0 から v0.2.1 へ

**要点だけを読みたいときは、[FAQ.md](FAQ.md) の「v0.2.0 から v0.2.1 へ上げるとき」を先に読んでください。**

### 接続先の GitHub を `WORKFLOW.md` で選べるようになりました（GitHub Enterprise）

**`tracker.provider.host` というキーが増えました。既定値は `github.com` です。**
**書かなければ、起動はいままでと変わりません。**GitHub Enterprise を使うときだけ、そのホスト名を書きます。
使い方と乗り換えの手順は [FAQ.md](FAQ.md) の「GitHub Enterprise で使いたいとき・github.com から乗り換えるとき」にあります。

```yaml
tracker:
  provider:
    host: github.com        # GitHub Enterprise を使うなら、そのホスト名（例: ghe.example.com）
```

**当たる人は4通りです。**上の2つは、何もしないと着手か起動が止まります。

| 当たる人 | 何もしないとどうなるか | 直し方 |
| --- | --- | --- |
| **`ghq` の置き場所の1階層目が `github.com` でない clone を使っている人**（SSH の別名のホストで取った clone・手で置いた clone） | **その issue に着手しません。**`<owner>/<repo> の clone がありません` と出ます | 下の「clone の引き方が変わりました」 |
| **`claude.env` に、`tracker.provider.host`（書いていなければ `github.com`）と違う値の `GH_HOST` を書いている人** | **起動しません。**`claude.env の GH_HOST（"<書いた値>"）が tracker.provider.host（"<接続先>"）と違います` と出ます。同じ値なら止まりません | `tracker.provider.host` を同じ値にするか、`claude.env` のその行を消す |
| **全員** | `continuo doctor` の「未記入の項目」に `tracker.provider.host` が1行出ます（`!`。起動は止まりません） | `continuo doctor --missing-keys-patch` の差分を当てるか、`provider:` の下へ `host: github.com` を1行足す |
| **`continuo init` が置いた CI の検査ファイルを GitHub Enterprise で使う人** | 古い検査ファイルは `gh` の宛先を決めておらず、`https://github.com/` を決め打ちしているので、検査が通りません（どの段で落ちるかは、実機が無いので確かめていません） | [FAQ.md](FAQ.md) の「CI の検査ファイル（`continuo-ci.yaml`）」 |

#### clone の引き方が変わりました

**continuo は clone を `ghq list -p -e <ホスト名>/<owner>/<repo>` で引くようになりました。**
いままでは `<owner>/<repo>` だけで引いていました。

**なぜ変えたか。**`<owner>/<repo>` だけだと、`ghq` の置き場所の1階層目（ホスト名のディレクトリ）が何であっても当たります。
同じ名前のリポジトリの clone が github.com と GitHub Enterprise の両方に在ると2行返り、
**continuo は1行目を採るので、別のホストの clone から worktree を切っていました。**

**当たるかどうかの確かめ方。**`trust.repositories` に書いたリポジトリごとに叩きます。

```bash
ghq list -p -e github.com/<owner>/<repo>     # 1行返れば、何もしなくてよい
ghq list -p -e <owner>/<repo>                # 上が0行でこちらが返るなら、当たっています
```

**直し方。**`continuo trust` を叩きます。`ghq get --vcs git https://github.com/<owner>/<repo>` で
`<ghq の root>/github.com/<owner>/<repo>` へ clone を取り、承認し直します。

```bash
continuo trust ~/continuo-work
```

**`https://github.com/…` から取れないとき**（SSH の別名のホストを、アカウントの使い分けのために使っている場合など）は、
同じ場所へ手で clone を置いてから `continuo trust` を叩きます。**この場合に `continuo trust` だけで通るかは、確かめていません。**

```bash
git clone <いま使っている clone の remote の URL> "$(ghq root)/github.com/<owner>/<repo>"
continuo trust ~/continuo-work
```

**古い場所の clone は、continuo はもう見ません。**そこに worktree が残っているなら、push してから片付けてください。

#### 古い continuo で新しい `WORKFLOW.md` は読めません

**`host:` の行を書き足したら、continuo も一緒に上げてください。**
設定の読み込みは知らないキーをエラーにするので、古い実行ファイルで起動すると `unknown field "host"` で止まります。
**古い版へ戻すときは、`host:` の行を消します。**

#### 画面に出る直し方が変わりました — 設定に足すものはありません

**`gh` と `ghq` を案内する文面に、接続先のホスト名が入るようになりました。**

| いままで | これから |
| --- | --- |
| `gh auth login -s project` | `gh auth login --hostname github.com -s project` |
| `ghq list -p -e <owner>/<repo>` | `ghq list -p -e github.com/<owner>/<repo>` |
| `ghq get <owner>/<repo>` | `ghq get --vcs git https://github.com/<owner>/<repo>` |

**`continuo doctor` の出力を文字列で見ているスクリプトがあれば、直してください。**

#### エージェントの環境に `GH_HOST` が入るようになりました

**continuo は、issue ごとの設定ファイルの `env` に `GH_HOST=<tracker.provider.host の値>` を書きます。**
接続先が `github.com` のときも書きます。**エージェントが叩く `gh` の宛先が、機械ごとの `gh` の既定に左右されなくなります。**

**利用者が書いた hook（`workspace_hooks`）の環境には足しません。**

#### `continuo abandon` と `continuo prompt --show --url` が、接続先と違うホストの URL を断ります

**issue の URL のホストが `tracker.provider.host` と違うと、何もせずに止まります。**
どちらも issue を `<owner>/<repo>#<番号>` で接続先のカンバンから引くので、
断らないと、接続先のカンバンに在る同じ番号の別の issue を扱うためです。

### 枠の使用率を読めないとき、Claude Code のステータスラインへ切り替えるようになりました

**v0.1.15 までは、枠の使用率を Anthropic の usage API からだけ読んでいました。**
**読めないと（資格情報が無い・401・403 など）枠の判定を諦め、429 や 5xx のあいだは巡回のたびに叩き直していました。**
**usage API が 429 を返し続けると、入札が止まり、上限に当たった run の回復待ちの判定も効かなくなっていました。**

**この版から、usage API が誤りを返すあいだ（どの誤りでも）は、Claude Code のステータスラインから使用率を受け取ります。**
usage API はいままでどおり主に使い、読めるようになれば戻ります。**v0.1.15 の `WORKFLOW.md` のまま起動します。**

| 何 | v0.1.15 まで | v0.2.0 から |
| --- | --- | --- |
| **usage API が誤りのとき** | 資格情報の誤り・401・403 では枠の判定を諦める。429・5xx は巡回のたび（30秒ごと）に叩き直す | **Claude Code のステータスラインへ切り替える。**`rate_limit.poll_interval_ms` と `Retry-After` の長いほうのあとに読み直し、読めたら戻る |
| **`rate_limit.source` の値** | `oauth_usage_api`（既定）/ `none` | **`oauth_usage_api`（既定）/ `statusline` / `none`**。`statusline` は usage API を読まず、ステータスラインだけを使う |
| **`rate_limit.refresh_interval_ms`** | 無かった | **足しました**（既定 `300000`）。usage API が誤りのあいだ、入札に使ってよい値の古さの上限で、statusline取得の間隔でもあります |
| **continuo が起動した pane のステータスライン** | あなたのステータスライン | **あなたのステータスライン**（`continuo statusline` が使用率を受け取ったあとで、あなたの `statusLine` のコマンドを呼びます。見つからないか失敗したときだけ、固定の `continuo` の1語） |
| **`continuo allow-keychain-access` と `continuo doctor` の `資格情報`** | あった | **いままでどおりです** |

**`WORKFLOW.md` から消すキーはありません。**書き換えなくても起動します。

#### 何もしないとどうなるか

**usage API が読めているあいだは、いままでと同じに動きます。**違うのは次の3つです。

| 何が起きるか | いつ |
| --- | --- |
| **continuo が起動した pane で、あなたのステータスラインが固定の `continuo` の1語に替わる** | **あなたの `statusLine` が見つからないか、5秒で終わらない・終了コードが 0 でない・何も出さないとき**（下の「continuo の pane のステータスライン」）。**あなたが自分で起動した Claude Code は変わりません** |
| **haiku の Claude Code が短く起動する**（statusline取得。herdr の画面に `continuo statusline fetch` という workspace がしばらく現れて消える） | usage API が誤りを返していて、使用率が `rate_limit.refresh_interval_ms`（既定5分）より古いとき。**何もしていない機械で最大5分に1回、1回の入力は約600トークン**です |

#### continuo の pane のステータスライン

**continuo は、自分が起動した Claude Code の `statusLine` を `continuo statusline` に差し替えます**（使用率を受け取るため）。
**`continuo statusline` は、使用率を受け取ったあとで、あなたの `statusLine` のコマンドを同じ入力で呼び、その出力を出します。**

**どのコマンドを呼ぶかは、着手のときに決まります。**worktree の `.claude/settings.local.json` → worktree の `.claude/settings.json` →
`CLAUDE_CONFIG_DIR`（無ければ `~/.claude`）の `settings.json` の順に読み、最初に `statusLine` を持つファイルだけで決めます。
**着手のあとで設定を変えても、その issue が次に着手されるまで効きません。**`refreshInterval` などは写しません。

**あなたのステータスラインが出ないときは、issue ごとの設定ファイルの `env` の `CONTINUO_STATUSLINE_COMMAND` を見てください**（見つからなければ空です）。
置き場所と確かめ方は [FAQ.md](FAQ.md) の「continuo の pane で、自分のステータスラインが出なくなった」にあります。

#### API キーの機械は、`rate_limit.source: none` にしてください

**API キーで Claude Code を動かしている機械では、usage API もステータスラインも使用率を返しません。**
**そのままだと、usage API の誤りでステータスラインへ切り替え、statusline取得の haiku の会話が従量で課金されます。**
**課金は continuo を起動するたびに最大1回で止まります**（起動してから1度も使用率を読めていない機械では、値を受け取れなかった statusline取得を1回したところで、それ以後 statusline取得をしません）。

```yaml
rate_limit:
  source: none
```

**`none` にすると、使用率0として常に入札します**（v0.1.15 と同じです）。複数の機械で見張っているなら、全員を揃えてください（[FAQ.md](FAQ.md) の「API キーの機械が混ざるとき」）。

#### statusline取得には、信頼済みの clone が1つ要ります

**usage API が誤りのあいだ、statusline取得には、`trust.repositories` に書いたリポジトリのうち、
手元に clone があって `continuo trust` で信頼させたものが1つ要ります。**
continuo は上から見て、最初に見つかった1つを使います。**1つも無いと、次の `WARN` が出て、usage API が読めるまで使用率が入りません。**
**走っている issue が無い間は、値が1つも入らないので、自動の着手が止まり続けます。**

```text
statusline取得ができません（使える clone が無い: trust.repositories に、手元に clone があって信頼済みのリポジトリが1つもありません。1つ書いて continuo trust を叩き、continuo を立て直してください）
```

**`trust.repositories` は走行中に読み直しません。**書き換えたら、continuo を立て直してください。

**雛形の `trust.repositories` のコメントにあった「巡回のループはここを読まない。continuo trust だけが読む」は、この版から正しくありません。**
**あなたの `WORKFLOW.md` のコメントは、continuo が書き換えないので古いまま残ります。**statusline取得の clone を選ぶのにも読みます。

#### `rate_limit.refresh_interval_ms` を書くとき

**`polling.interval_ms`（既定30秒）より長くしてください。**
`source: oauth_usage_api` で短く書くと、continuo は起動し、`polling.interval_ms` の2倍として扱って、起動時に `WARN` を1回出します。
`source: statusline` で短く書くと、次のように出て起動しません。

### レビューの回し方が組み込みのプロンプトへ入りました。**subagent が毎周2つ立ちます**

**この版から、エージェントはレビューのたびに subagent を2つ並列に立てます。**
差分だけを読む役と、**そこから呼ばれる処理・呼ぶ処理・対応する文書まで見る役**の2つです。
**心配な場所があるときは3つ目が立ちます。**

**レートリミットの減り方が変わります。**いままで1つだったところが2つになるので、**レビュー1周あたりの消費が増えます。**
そのかわり、**周の数が減ることを狙っています。**同じ見落としを次の周で拾い直さなくなるためです。

**`WORKFLOW.md` の `### レビューを頼む subagent` に、名前を2つ書いてください。**
**1つしか書いていない場合は、「関連処理まで見る役」に当たる名前を足してください。**
**`security-reviewer` のように役の違う名前が並んでいる場合は、その名前を上の2つの役に合うものへ差し替えてください。**
**先に書いたほうが「差分を読む役」、後が「関連処理まで見る役」になります。**
**案内のコメント行（`<!-- … -->`）は、送る文面から取り除かれます。**そちらを直す必要はありません。

**書かないとどうなるか。**名前が1つだけなら、エージェントは**その1つを両方の役に使います。**1つも無ければ `general-purpose` です。
止まりはしませんが、**1つだけだと、周辺のコードと対応する文書を見る役がいなくなります。**
**1つも書いていないと、あなたが用意したレビュワーは呼ばれません。**

### レビュー結果を貼ったあと、**エージェントが検査の完了まで黙ります**

**この版から、エージェントはレビュー結果を貼ったあとに `gh run rerun` を叩き、`gh pr checks --required --watch` で検査が終わるまで待ちます。**
**その間、エージェントは1行も書きません。**CI の実行時間をそのぶん使います。

**`.github/workflows/` に `code-review-result` を持つ検査が無いリポジトリでは、この待ちに入りません。**
**その検査は `continuo init` が置く `continuo-ci.yaml` を `.github/workflows/` へ移すと入ります。**

**途中の周では、エージェントは結果を貼るたびに回し直してから待ちます。**
**回し直しが要らないのは、レビューが収まって終わり、エージェントが `gh pr ready` で draft を外したときだけです。**そこで検査が回り直すためです。
**判断票を前の判断票へ書き足した周も、回し直してから待ちます。**

### 判断票の形が変わりました。**件数の遷移表が付き、中身は畳まれ、1件に書き足されます**

**この版から、判断票の先頭に、CRITICAL / HIGH / MEDIUM / LOW の件数を周ごとに並べた遷移表が付きます。**
**周ごとの中身は `<details>` で畳まれます。**開けば、これまでどおりの節と指摘の表が読めます。
**指摘の表には「数えた結果」と「分類」の2列が増えます。**同じ誤りが他に無いかを数えた結果と、その指摘が前の周に在ったかどうかです。

**判断票は、issue（計画のレビュー）と pull request（実装のレビュー）に1件ずつになります。**
エージェントは周ごとに新しいコメントを足さず、前の判断票を書き換えて1周ぶんを足します。
**長さが 60,000 文字を超えるとき・前の判断票を読めないとき・書き換えに失敗したときは、遷移表を写して新しく1件にします。**
**この版より前に貼られた判断票は、そのまま残ります。**遷移表を持たないので、エージェントは書き足さず、新しく1件にします。

**issue に無いものを削ったときの記録は、別のコメントではなくなります。**削った周の判断票の遷移表の下に1行で残り、何をしたかの報告にも要約が入ります。
**「対応しない」と決めた理由も、別のコメントではなく、何をしたかの報告に入ります。**1つの run で書くコメントは、原則1件になります。

**実装レビューが収まったら、エージェントは draft を必ず外します。**誰が draft で作ったかは問いません。
外さないのは、10周で収まらずに止まったとき・質問で打ち切ったとき・`WORKFLOW.md` の本文に「draft のまま人間へ渡す」とはっきり書いてあるときだけです。
**「draft で作る」とだけ書いてある場合は、外します。**draft のまま受け取りたいなら、そうはっきり書いてください。

**`WORKFLOW.md` の本文で判断票の形を自分で指示している場合は、そちらも直してください。**
**何も書いていない場合は、エージェントが組み込みの形で書くので、直す必要はありません。**

### 新しい既定にする書き換え

**下の yaml は、どこに何が入るかの図です。塊ごと貼り替えないでください。**
**貼り替えると `permissions.allow` が消えます。**
**変えるのは、右にコメントを付けた3行だけです。**

```yaml
claude:
  kind: claude
  permission_mode: auto        # ← dontAsk から変える
  permissions:
    allow:                     # ← 触りません。dontAsk へ戻したくなったときに要ります
      - "Bash"
      - "Read"
      - "Glob"
      - "Grep"
      - "Edit"
      - "Write"
    deny: ["AskUserQuestion"]  # ← [] から変える
  tool_gate:
    mode: "off"                # ← 下の表のとおり
```

**`permission_mode` と `deny` は、必ず2つセットで変えてください。**
**`permission_mode: auto` だけを当てて `deny` を当て忘れると、`AskUserQuestion` の拒否が外れます。**
そうなると、スキルなどからその道具が呼ばれた瞬間に**質問の画面が出て pane が止まり、
continuo が次に送る指示が、その質問への回答として消費されます**（実測）。

**`tool_gate` は、いまの値によって変わります。**

| `mode:` の値 | いま何が起きているか | 何をするか |
| --- | --- | --- |
| **`public_only`**（v0.1.10 以降の `continuo init` の既定） | 公開リポジトリの issue にだけ判定が掛かっている | **`off` へ書き換える。**掛けたままにしたいなら、そのままで構いません |
| **`off`**（自分で止めた人） | 判定は掛かっていない | **何もしなくて構いません。**新しい既定と同じです |
| **`on`**（自分で強めた人） | いつでも判定が掛かっている | **何もしなくて構いません。**書き換えると、自分で強めた守りを外すことになります |
| **1行も出ない**（v0.1.9 以前の `continuo init`） | **既定がそのまま効いている** | **版を上げた時点で判定が止まります。**続けたいなら `mode: public_only` を手で書いてください。**`continuo doctor --missing-keys-patch` では戻りません**（新しい雛形の値、つまり `off` が入ります） |

### issue のコメントで出した許可が、エージェントへ渡るようになりました — 設定に足すものはありません

**この版から、continuo は Claude Code を閉じるたびに、issue へ「Claude Code を閉じました」のコメントを1件書きます。**
**次に Claude Code を起動するとき、そのコメントより後に `OWNER` / `MEMBER` / `COLLABORATOR` が AI の印を付けずに書いたコメントを、最初のメッセージに付けて渡します。**
`auto` の判定役は、こうして渡したコメントを人間の許可として読みます。**「issue を1件作ってよい」のような許可を、issue のコメントで出せるようになりました。**

```text
<!-- continuo:closed -->
Claude Code を閉じました。このコメントより後に OWNER / MEMBER / COLLABORATOR が新しく書いたコメント（AI の目印の無いもの）を、次に Claude Code を起動したときに渡します。
```

| 何 | v0.1.15 まで | v0.2.0 から |
| --- | --- | --- |
| **issue のコメントで出した許可** | 判定役に届かなかった | **「閉じました」より後に新しく書いたものは、次の起動の最初のメッセージに付けて届く** |
| **issue のコメントの数** | — | **Claude Code を閉じるたびに1件増える。**いちばん下が「閉じました」になるので、次の run は進捗の報告を新しく1件作る |
| **`agent.relay_trusted_comments`** | 無かった | **足しました**（既定 `true`）。`false` にすると、渡さず、「閉じました」も書かない |

**効くのは、`claude.permission_mode` が `auto` で、`tracker.comments.self_marker` が空でないときだけです。**
`self_marker` が空だと、continuo 自身の「Status を動かしました」に印が付かず、人間のコメントとして渡ってしまうので、動かしません（起動時に WARN を1行出します）。

**書き方。**「閉じました」が付いたのを見てから、許可を**新しいコメントとして**書き、Status を着手待ちへ戻してください。
渡らないものと、渡らなかったときの直し方は [FAQ.md](FAQ.md) の「作業の途中で確認の画面に止まりました」と出る・「issue のコメントで許可を書いたのに、また止められる」にあります。

**「閉じました」のコメントは消さないでください。**消すと、その間に Claude Code が書いたコメントまで人間の許可として渡りえます。片付けるときは隠してください（[FAQ.md](FAQ.md) の「issue に「Claude Code を閉じました」のコメントが増える」）。

**入れ替えたら continuo を再起動してください。**`agent.relay_trusted_comments` は、動いている最中には読み直しません。

**版を上げる前から止まっていた issue には、「閉じました」がまだ1件もありません。**
**そのため、上げたあとの最初の着手では、前に書いた許可は渡りません。**その回が閉じて「閉じました」が付いたあとに、書き直してください。

**同じカンバンを複数の機械で見張っている場合は、全部の機械を同じ版にし、`agent.relay_trusted_comments`・`claude.permission_mode`・`tracker.comments.self_marker`・`tracker.comments.marker` を揃えてください。**
古い版の機械や `false` の機械は「閉じました」を書かないので、新しい機械はその run のあとで「前の回が閉じられたことを確かめられない」と判断し、許可をほぼ渡しません（[FAQ.md](FAQ.md) の「揃っていないと壊れるキー」）。

**足したい人は、次のコマンドが1行を作ります。**書かなくても既定の `true` で動きます。

```bash
continuo doctor --missing-keys-patch ~/continuo-work
```

**危険の説明は [SECURITY.md](../SECURITY.md) にあります。**`MEMBER` はリポジトリを持つ組織のメンバー全員に付くこと、同じ GitHub アカウントで動く AI が印を付け忘れたコメントも渡りうること、信頼できる人が外部の人の文を引用すると引用の部分も届くことを書いています。

### 人間が pane で直接続けるあいだ、continuo が手を出さないようにできます（direct chat）

**何が変わったか。**`tracker.direct_chat_state` というキーが1つ増えました。**既定は `"Direct Chat"` です。**

> **先に読んでください。カンバンに `Direct Chat` という選択肢を既に持っている人だけ、上げると挙動が変わります**（上の破壊的変更の2つ目）。
>
> **いままでどおりにしたいときは、`WORKFLOW.md` の `tracker.direct_chat_state` を
> 空文字にするか、別の名前へ書き換えてください。**
>
> ```yaml
> tracker:
>   direct_chat_state: ""
> ```

**`Direct Chat` という選択肢を持っていないカンバンでは、この機能が使えないだけで、他の動きは1つも変わりません。**

**何が困っていたか。**何度やり直しても収束しない issue で、人間が herdr の pane に入って直接話しかけると、
**continuo がその pane を閉じて会話が切れていました。**
エージェントの返事に `CONTINUO-STATUS: blocked` の1行が入る、人間が考えている間に Claude Code が何もせず打ち切られる、
といった経路が4つあり、**どれも「continuo が手を離す」＝「pane を閉じる」だったためです。**

**どう変わったか。**カードを `Direct Chat` へ動かしているあいだ、
continuo は**指示を送らず、`CONTINUO-STATUS:` の行も読まず、Status も動かさず、pane も worktree も片付けません。**
**pane がまだ無ければ、そこで1つ用意します**（continuo がその issue をまだ抱えていないときだけです）。
`In Progress` か `Ready` へ戻すと、**たいていは同じ pane・同じ会話のまま**続きの指示を送ります。

**使うのに要るのは2つです。**

| 何を | どうするか |
| --- | --- |
| **カンバンの選択肢** | カンバンの画面で Status の選択肢を1つ足してください（名前は `Direct Chat`）。**足したら continuo を再起動してください**（カンバンの選択肢は、起動したときと20巡回ごとにしか読み直しません） |
| **担当者** | **動かす issue の担当者を、pane を開きたい PC の continuo が使っている `gh` のアカウント1人だけにしてください。**0人か2人以上だと、continuo がカードを `Blocked` へ動かして「担当者を1人に」とコメントします。**`Direct Chat` のあいだに担当者を別の1人に替えると、いまの PC の continuo は pane を閉じて手を離します** |

> **API（`gh project field-create` / `updateProjectV2Field`）で選択肢を足してはいけません。**
> **設定済みの Status の値が全部消えます。**

**何台かの PC で同じカンバンを見張っていても使えます。**pane を持つのは、担当者のアカウントの PC だけです。

**別の名前にしたいときだけ、`WORKFLOW.md` に書きます。**`continuo setup` も6つ目の質問として尋ねます
（番号 `0` で飛ばせます）。

```yaml
tracker:
  direct_chat_state: "Direct Chat"
```

**書いたら再起動してください。**このキーは動いている最中には読み直しません。

**書いた名前がカンバンに無くても、起動は止まりません。**`continuo doctor` の `Status の名前` が `!` を出します。
**この Status だけの扱いです。**他の Status の名前がカンバンに無いときは、いままでどおり起動を止めます
（そちらは、綴りがずれると issue が1件も見つからないのに正常に見えるためです）。

**`Direct Chat` に置いたまま continuo の再起動を重ねると、`Blocked` へ落ちることがあります。**
再起動して引き継いだ回数は `Direct Chat` のあいだも数えるので、**上限（`agent.max_takeover`、既定5）に届くと、
戻したあとの再起動で引き継がずに `Blocked` へ落ちます。**再起動を何度も重ねる使い方なら、`agent.max_takeover` を上げてください。

**使わないなら、`tracker.direct_chat_state` を空文字にしてください。**

**使い方と気をつけること、pane が来ないときの手順は [docs/FAQ.md](FAQ.md) の「途中から人間が直接チャットで進めたいとき（direct chat）」にあります。**

### 古い continuo で新しい `WORKFLOW.md` は読めません

**`tracker.direct_chat_state` を書き足したら、continuo も一緒に上げてください。**
設定の読み込みは知らないキーをエラーにするので、**古い実行ファイルで起動すると
`unknown field "direct_chat_state"` で止まります。**
**順番は「実行ファイルを入れ替える → `WORKFLOW.md` を書き足す」です。**

### `continuo abandon` が direct chat の Status を3通りで断ります

**`tracker.direct_chat_state` の Status をカンバンに作った人だけに関係します。**
**設定に足すものはありません。**

| どれ | なぜ断るか |
| --- | --- |
| **`--park` の行き先** | そこへ動かしても continuo は pane を閉じないので、`continuo abandon` は pane が閉じるのを待ち切れず、**結局何も消せません** |
| **`--to` の行き先** | 片付けは通りますが、**次に continuo を起動したとき、いま消したばかりの worktree と pane を作り直します。**巡回のたびに作り直されます |
| **いまの Status が `Direct Chat`** | `--force` を付けると worktree だけ消えて、**同時実行の枠を1つ持ったまま戻らなくなります。**ログにも issue にも何も出ません |

**3つとも、待つ前に理由を出して止まります。****`--force` でも通りません。**
**直し方は1つです。**カードを `Direct Chat` の外へ動かしてから叩いてください。

### エージェントのコメントの形が、4つの見出しから7つに変わりました

**v0.1.15 で入った4つの見出し**（`### 何に対する返答か` / `### 前提条件` / `### 単語の説明` / `### 何が問題なのか`）**は、この版で7つになります。**

| 順 | 見出し | 中身 |
| --- | --- | --- |
| 1 | （見出しは付きません） | **引用。**その節が答えている原文だけ |
| 2 | `### 三行まとめ` | 3行以内で結論 |
| 3 | `### 前提` | その話が成り立つために要る条件 |
| 4 | `### 単語の説明` | その節で使う語が何を指すか |
| 5 | `### 既存の構造がどうなっているか` | いまどう作られていて、何がどの順で起きるか |
| 6 | `### 何が問題なのか` | 症状と、放っておくと何が起きるか |
| 7 | `### 詳細` | 根拠・仕組み・データ |

**引用の置き方も変わります。**
**v0.1.15 は、節ごとに `### 何に対する返答か` の見出しを立て、その下に引用を置いていました。**
**この版からは見出しを付けず、節の先頭に引用を置きます。**そのすぐ下に `### 三行まとめ` が来ます。

**あわせて4つ増えます。**
**説明にシーケンス図を多用し、何を渡して何を受け取るかを具体的な値で書きます。**
**技術用語は英語のまま書きます**（`worktree` / `pane` / `hook` / `branch` / `commit`）。
**人間に決めてほしいことは、質問1つにつき1つの節で訊き、表で訊きません。**
**判断票は、指摘をまとめた表を、その節の `### 詳細` の中に置きます。**

**あなたの側に要るものはありません。**`continuo init` が置いた `WORKFLOW.md` は書き換わりません。
**`WORKFLOW.md` の本文（front matter の下）で、コメントの書き方を自分で指示している場合だけ、そちらを新しい形に合わせてください。**本文は組み込みの指示書の真ん中へ挟まり、コメントの形を決める組み込みの節はその後ろに来ます。**形が食い違うと、エージェントは2つの形を受け取ります。**

### herdr 0.9.1 に合わせました。**herdr を 0.9.1 へ上げたら、`WORKFLOW.md` の `herdr.protocol` を手で `22` へ直してください**

**この版は herdr 0.9.1 で動作を確認しています。**herdr 0.8.2 には、長い指示の本文を打ち込んだあとの Enter が届かない不具合があります。
**そうなると、エージェントは1文字も読まずに黙ったまま止まり、continuo は `claude.turn_timeout_ms`（既定60分）を使い切るまで待ち続けます。**
**この不具合は herdr 0.9.0 で直っています。**herdr を 0.9.1 へ上げてください。

**herdr を上げると、`WORKFLOW.md` を直すまで continuo は起動しません。**
continuo は起動するときに herdr へ `ping` を送り、返ってきた protocol の番号が `herdr.protocol` と1でも違うと止まります。

| herdr の版 | 返す protocol |
| --- | --- |
| **0.9.1 / 0.9.0** | **22** |
| 0.8.2 | 20 |
| 0.8.0 | 19 |

**v0.1.15 までの `continuo init` で `WORKFLOW.md` を作った人は、全員が手で直す必要があります。**
**その雛形が `protocol: 20` を書いていたためです。**書いてある値は既定値より優先されるので、continuo の既定値を 22 に上げただけでは効きません。
**逆に `protocol:` の行を消して既定値に任せている人は、continuo を上げた時点で 22 になります。**herdr を 0.8.2 のまま使うなら、`protocol: 20` を書き足してください。
**`continuo setup` でも `continuo doctor --missing-keys-patch` でも直りません。**どちらも、既にあるこの行には触りません。

```yaml
herdr:
  protocol: 22    # herdr 0.9.1 と 0.9.0 は 22。0.8.2 は 20、0.8.0 は 19
```

**直したら `continuo doctor` で確かめてください。**`herdr --version` ではなく doctor の出力を見ます。
**照合するのは、動いている herdr の server が返す値だからです。**herdr 0.9.0 以降は client だけを上げて server を古いまま残せるので、
`herdr --version` が 0.9.1 でも、server は古い版のままということがあります。

```bash
grep -n "protocol:" ~/continuo-work/WORKFLOW.md
continuo doctor
# ✓ herdr           protocol 22（設定と一致）／herdr 0.9.1／socket ~/.config/herdr/herdr.sock
```

**doctor の行に出る版が 0.9.1 でなければ、herdr の server がまだ古いままです。**herdr を立て直してから、もう一度確かめてください。

**herdr 0.9.0 から、配下に worktree を持つリポジトリの workspace を閉じると、herdr が断るようになりました。**
**continuo の片付けは、配下が残っていないことを確かめてから閉じるので、ふだんは当たりません。**
断られるのは主に、確かめてから閉じるまでの間に同じリポジトリの worktree が開いたときです。**そのときは親を閉じずに残します。**
**閉じたいときは、同じリポジトリの worktree が全部片付いてから herdr の画面で閉じてください。**配下が残っているうちに画面から閉じると、herdr は配下の pane ごと閉じます。

### コメントと pull request の本文・題名を、ファイルから渡すようになりました — 設定に足すものはありません

**エージェントは、issue のコメントと pull request の本文・題名を一時ファイルへ書いてから、`gh` へ渡します。**
**v0.1.15 までの指示書は、本文と題名を `--body "…"` や `--title "…"` の二重引用符の中へ直に書かせていました。**
**二重引用符の中では、シェルが backtick と `$( )` をコマンドとして実行します。**
報告に backtick で囲んだ語を書いたり、issue から `$(…)` を含む文を引いたりすると、それが worktree の中で走ります。

**あわせて2つ変わりました。**

- **見本をコード囲みに入れ、中身を行頭から書くようにしました。**字下げした見本をそのまま写すと、ヒアドキュメントの終わりの行が終わりと読まれず、何も投稿されないまま終わります。
- **計画・判断票・成果の報告の本文を、worktree の中の `plan.md`・`review.md`・`done.md` へ書かせるのをやめました。**残ったファイルがあると、既定の設定（`cleanup.require_clean_worktree: true`）では worktree が片付かず、issue に「コミットされていない変更が残っている」と書かれていました。

**あなたの側に要るものはありません。**
**`WORKFLOW.md` の本文で `gh issue comment … --body "…"` の形を自分で指示している場合だけ、次の形へ直してください。**

```bash
F=$(mktemp)
cat > "$F" <<'BODY'
<本文>
BODY
gh issue comment <issue の URL> --body-file "$F"
```

**`<<'BODY'` の引用符を落とさないでください。**落とすと、ヒアドキュメントの中でも backtick と `$( )` が実行されます。
**`BODY` の行は行頭に置いてください。**字下げすると、そこで終わりと読まれません。
**本文の中に `BODY` だけの行を作らないでください。**そこで本文が切れ、後ろの行がシェルのコマンドとして実行されます。入るなら、終わりの語を別のものに変えてください。

**`docs/plans/continuo_design.md` の 3-78b を写して、`WORKFLOW.md` の本文に「コードが別のリポジトリにあるとき」を置いている場合は、そこも直してください。**
v0.1.15 の見本は `commit -am "<何を直したか>"` と `--title "<何を直したか>"` でした。
v0.2.0 の見本は、メッセージを一時ファイルへ書き、`git -C <clone のパス> commit -a -F "$M"` と `--title "$(cat "$M")"` で渡します。
**直さないと、メッセージや題名に書いた backtick が、その `WORKFLOW.md` を使う全部の run で実行され続けます。**continuo は `WORKFLOW.md` を書き換えません。

### AI の印が付いたコメントを、エージェントが命令として扱わなくなりました — 設定に足すものはありません

**この版から、continuo が起動した Claude Code は、本文の先頭に AI の印があるコメントを命令として扱いません**（issue #245）。
**印は、本文の1行目に置く HTML コメントです。**`<!-- continuo:` で始まるもの（`<!-- continuo:agent -->`・`<!-- continuo:ai -->` など）と、

**書いた人が `OWNER` / `MEMBER` / `COLLABORATOR` でも、印があれば分析や記録として読みます。**

**pull request の本文も、命令として扱わなくなりました。**変更の説明として読みます。指示はコメントに書いてください。

**変わったこと。**

| 何 | v0.1.15 まで | v0.2.0 から |
| --- | --- | --- |
| **`OWNER` が書いた、AI の印付きのコメント** | 命令として扱った | **分析や記録として読む** |
| **pull request の本文** | 書いた人の立場で決めた | **命令として扱わない** |
| **「コードは別のリポジトリにある」「この branch へ出せ」** | `OWNER` / `MEMBER` / `COLLABORATOR` が書いていれば従った | **そのうえで、AI の印が無いコメントか、issue の本文に書いてあるときだけ従う** |

**あなたの決定は、あなたが自分で書いてください。**Claude Code に代筆させて AI の印が付くと、エージェントはそれを命令として扱いません。

```

**自動では新しくなりません**（third-party の marketplace は、Claude Code の既定で自動更新が切れています）。新しくするときは次の2つを叩きます。

```bash

```

**手で直すものが3つあります。**どれも、前の版の案内をあなたが写した場合だけです。

**`continuo init` が `WORKFLOW.md` の隣に置く CI の見本（`continuo-ci.yaml`）の案内の文も、同じ理由で書き分けました。**

### 計画を書いたところで、どの issue も一度 `Blocked` で止まる

**エージェントは計画を書いたら、設計レビューへ進む前に `Blocked` で止まり、あなたの確認を待ちます。**これは正常です。
**了承するときは、了承することを issue のコメントにはっきり書いてから `Ready` へ戻してください。**Status を戻すだけでは進みません。
**レビューの途中で質問して止まったときは、回答を issue のコメントに書いてから `Ready` へ戻してください。**

**実装レビューが収まると、エージェントは pull request の draft を必ず外します。**誰が draft で作ったかは問いません。
`WORKFLOW.md` の 4-4 やリポジトリの決まりに「draft で作る」とだけ書いていた場合も同じです。
**外さないのは、10周で収まらずに止まったとき・質問で打ち切ったとき・4-4 に「draft のまま人間へ渡す」とはっきり書いてあるときだけです。**

詳しくは [docs/FAQ.md](FAQ.md) の「計画を書いたところで、どの issue も `Blocked` になる」にあります。

### 枠に余裕が無いときの理由が、既定のログの水準で出ます

**v0.1.15 まで、使用率が 91〜95% の帯では1行も出ませんでした。**
新規着手を止める判定が2つあり、**先に効くほうが `Debug` の1行しか出さなかった**ためです。

**v0.2.0 からは、この帯でも `Info` で1行出ます。**

```
枠に余裕が無いので、入札の要る issue には着手しません（担当が既にこの機械にある issue は着手します。走行中の turn も止めません）。…
  理由=余裕値が0以下 5時間の枠の使用率=30 1週間の枠の使用率=92
  5時間の枠の閾値="90% に達したら止まります" 1週間の枠の閾値="90% に達したら止まります"
```

**v0.2.0 で、出る行は1巡回につき1行になりました。**
「枠が閾値を超えているので新規の dispatch を止めます」は、その判定ごと消えています。

**文面は理由ごとに3通りあります**（枠に余裕が無い／枠を使い切っている／枠を読めない）。
**直し方が理由ごとに違うので、分けてあります。**
**どれも `入札の要る issue には着手しません` を含むので、探すときはそこだけを使ってください。**

```bash
grep -F '入札の要る issue には着手しません' <ログの出力先>
```

**この行は、担当者のいない issue をこの判定が見送った巡回ごとに出ます。**
巡回は既定30秒なので、止まっているあいだは1時間で120行になります。
**候補がこの判定まで届かなかった巡回では出ません**（空きスロットが尽きた・必須のラベルが足りない・信頼していないリポジトリ・バックオフ中、のどれかで候補が全部落ちた巡回です）。**出ていないことは、枠で止まっていないことを意味しません。**

### 1週間の枠を長く待つと、担当を自分で外します

**新しい設定です。書かなければ 300分（5時間）が効きます。**

**「300分待つ」ではありません。**「**あと300分以内にリセットされるなら待つ**」という線です。
**1週間の枠は最長7日先までリセットされない**ので、**余裕が無くなった時点でこの式はたいてい成り立ちません。**
**つまり、この分数ぶん待つことは、ほとんどありません。**ただし手放すのは pane が止まってからです。先に、hook が `claude.turn_timeout_ms`（既定1時間）のあいだ1件も来ていないことを確かめます。
**この分数だけ待つように働くのは、余裕の無い1週間の枠のうち、1つでもリセット時刻を読めないときです**
（使っていない `weekly_scoped` の `resets_at` は `null` で返ります。使い切ったときにどうなるかは測っていません）。

```yaml
rate_limit:
  weekly_wait_limit_minutes: 300   # 1週間の枠が明けるのを待つ上限。単位は分。0 なら上限を設けない
```

**何が起きるか。**1週間の枠に余裕が無くなった issue を、この時間より長く待つことになったとき、
**（「使い切った」ではありません。マージンが既定の10なら、使用率90%で余裕が無くなります。）**
**continuo は `workspace_hooks.after_run` を走らせ、その issue の担当者から自分を外し、
`<!-- continuo:released -->` を1件書き、worker を止めます。**

| 何 | どうなるか |
| --- | --- |
| **worktree** | **残ります。**消しません |
| **カンバンの Status** | **動きません。**`In Progress` のままです |
| **herdr の pane** | **閉じます** |
| **`workspace_hooks.after_run`** | **設定してあれば走ります。**ここに `git push` を書いている人は、手放す前に push されます。**`continuo init` の雛形は `after_run: null` なので、書き足していない人では走りません**（issue のコメントに「push できたことを確かめられませんでした」と出ます）。ほかに走らない場合が3つあり、[docs/FAQ.md](FAQ.md) の表にあります |
| **push していない変更** | **別の機械が先に拾うと、その機械には見えません。**その機械は worktree を新しく作るので、branch が分かれます。**この機械の worktree には残っています** |

**`after_run` に push を書いていない場合、危ないのはエージェントの最後の push 以降ぶんです。**
**エージェントは `progress_interval_ms`（既定1時間）ごとに push するよう指示されています。**

**1台で動かしている場合、空いたスロットに入る issue はありません。**
1週間の枠に余裕が無いあいだは、入札の判定が新しい着手を止めているためです。
**実際に変わるのは、pane が閉じることと、担当が外れることだけです。**
**枠が戻ったら、同じ機械が拾い直します。**そのとき**会話は引き継がれます**（worktree の身元ファイルに
セッションの識別子が残っているためです）。

**5時間の枠では起きません。**この上限は1週間の枠にだけ効きます。

**待ち続けたいときは 0 を書いてください。**

```yaml
rate_limit:
  weekly_wait_limit_minutes: 0   # 上限を設けない。v0.1.15 までと同じ振る舞いになる
```

**`tracker.provider.handoff.idle_timeout_ms` と 0 の意味が逆です。**
あちらの `0` は「既定の18時間」ですが、**こちらの `0` は「上限を設けない」です。**

**複数の機械で見張っているなら、`idle_timeout_ms`（既定18時間）より短くしてください。**
**長いと、別の機械が先に担当を外すので、この値は一度も効きません。**

#### `continuo doctor` が `rate_limit.weekly_wait_limit_minutes` について何を言うか

**`WORKFLOW.md` にこのキーが書かれていないと、`! 未記入の項目` に出ます。**
**書かなくても既定で動くので、急いで足す必要はありません。**足すときは次で差分が出ます。

```bash
continuo doctor --missing-keys-patch WORKFLOW.md
```

**負の値を書くと起動しません。**`✗ 設定ファイル` に
`rate_limit.weekly_wait_limit_minutes` の名前と、なぜ不正かが出ます。

### `rate_limit.pause_above_percent` を消してください — **消すまで起動しません**

**front matter は、知らないキーがあると起動を止めます。**
このキーは `continuo init` の雛形がずっと書いてきたので、**手を入れていない `WORKFLOW.md` にも入っています。**

**まず、書いてあるかを確かめます。**

```bash
grep -n 'pause_above_percent' WORKFLOW.md
```

**1行でも出たら、その行を消してください。**

```yaml
rate_limit:
  source: oauth_usage_api
  token_source: claude_credentials
  token_env: CLAUDE_CODE_OAUTH_TOKEN
  pause_above_percent: 95                   # ← この1行を消す
  poll_interval_ms: 300000
```

**`continuo init --force` で作り直さないでください。**雛形を上書きするので、書き足した設定が全部消えます。

**なぜ無くしたか。**同じことを2つの閾値で言っていて、使い分けができていませんでした。

| 何 | いつ止まっていたか |
| --- | --- |
| **入札の余裕値**（`100 − 使用率 − マージン`） | **マージン10なら使用率90%から** |
| `rate_limit.pause_above_percent`（既定95） | **96%から** |

**担当者のいない issue には、余裕値のほうが先に効いていました。**このキーが効いていたのは、担当が自分の issue の着手です（96%以上で、その巡回の着手を全部やめていました）。**キーを消したので、96%以上でも担当が自分の issue は着手します**（下の表の「96%〜」の行）。
**マージンは5時間と1週間で別々に持てる**ので、そちらのほうが細かく指定できます。

**低い値を設定していた人へ。**`pause_above_percent: N` と書いていたなら、
**`100 − N − 1` を2本のマージンに入れる**と、止まり始める使用率が同じになります。

```yaml
tracker:
  provider:
    handoff:
      five_hour_margin_percent: 19          # pause_above_percent: 80 と同じく 81% から止まる
      weekly_margin_percent: 19
```

**`pause_above_percent: 100` と書いていた人は、この式を使わないでください。**
`100 − 100 − 1` は `-1` になり、**マージンに負の数を書くと continuo は起動しません**
（`continuo doctor` が弾きます）。**`0` を書いてください。**

```yaml
tracker:
  provider:
    handoff:
      five_hour_margin_percent: 0           # 使用率が100%になるまで止まらない
      weekly_margin_percent: 0
```

**ただし、まったく同じにはなりません。**

| 何 | いつ止まるか |
| --- | --- |
| **`pause_above_percent: 100`**（前） | **1度も止まらない。**判定が「使用率 > 100」で、100を超える値は返らないためです |
| **マージン `0`**（いま） | **使用率がちょうど100%になったら止まる。**判定が「100 − 使用率 − 0 ≦ 0」だからです |

**使い切ってもなお入札を続ける設定は、もうありません。**
**枠が0のときに入札しても、Claude Code が応答できないためです。**
**`0` が、いちばん粘る設定です。**

**1を引くのは、比べ方が違うためです。**

| 何 | 判定 | 既定でいつ止まるか |
| --- | --- | --- |
| `pause_above_percent: N` | **使用率が N を「超えたら」** | **N + 1 から** |
| マージン M | **`100 − 使用率 − M` が「0以下なら」** | **100 − M から** |

**そのうえで、2つ違うところがあります。**

| 何が違うか | 中身 |
| --- | --- |
| **入札の点数が変わります** | **マージンは余裕値から引かれ、余裕値は入札の点数のもとになります**（`5時間余裕値 × 2 + 1週間余裕値`）。**片方の機械だけマージンを上げると、その機械は入札に勝てなくなります。**`pause_above_percent` は点数に1バイトも影響しませんでした |
| **枠ごとに別々に指定できます** | 5時間と1週間で違う値にできます。`pause_above_percent` は全部の枠の最大値ひとつで判定していました |

**何台かで分担している場合は、全部の機械へ同じ値を入れてください。**

### 2本のマージンに `100` を書けなくなりました — **書いている人は下げてください**

**`tracker.provider.handoff.five_hour_margin_percent` と `weekly_margin_percent` は、0以上100未満になりました。**
**`100` を書いていると起動しません。**

```bash
grep -nE 'five_hour_margin_percent|weekly_margin_percent' WORKFLOW.md
```

**なぜ弾くか。**余裕値は `100 − 使用率 − マージン` で、**0以下なら「余裕が無い」です。**
**マージン100 だと、使用率0でも余裕値が0になります。**その機械は**永久に入札しません。**
**さらに、1週間の枠を待つ上限の判定も永久に真になるので、枠を1バイトも使っていないのに走っている run を全部手放します。**

**「枠を全部人間のために取り置く」つもりで書いていた人は、`rate_limit.source: none` ではなく `99` を使ってください。**

### 使用率の線が1本になり、90% で止まるようになりました

**既定のマージン（10）での話です。**
**「96%から90%へ」ではありません。**`v0.1.15` でも**91%から**担当者のいない issue は取っていませんでした。
**96% は、消したキー（`rate_limit.pause_above_percent`）の閾値です。**下の表の3行目と4行目を見てください。

| 使用率 | v0.1.15 まで | v0.2.0 から |
| --- | --- | --- |
| 〜89% | 取る | 取る |
| **90%** | 取る | **担当者のいない issue を取らない** |
| 91〜95% | 担当者のいない issue を取らない | 同じ |
| **96%〜** | **1件も取らない**（担当が自分のものも含む） | **担当が自分の issue は取る** |

**2つ変わっています。**

- **90%ちょうども「余裕が無い」に含めるようになりました。**余裕値0は、マージンをちょうど食い潰した状態です
- **96%を超えても、担当が既に自分にある issue には着手します。**以前は巡回を丸ごと止めていたので、
  **再起動したあとに走っていた issue を拾い直せず、期限切れの担当を外す経路も通りませんでした**

**担当者のいない issue を取らなくなる使用率を `v0.1.15` と同じ91%へ戻したいときは、マージンを `9` へ下げてください**（`five_hour_margin_percent: 9` と `weekly_margin_percent: 9`）。**96%以上で担当が自分の issue の着手も止める動きは、戻せません**（そのキーを消したためです）。

### 担当を手放すのは、Claude Code が止まってからです

**`rate_limit.weekly_wait_limit_minutes`（既定300分）を超えたときの動きが、この版で入りました。**

**手放す前に、pane が完全に止まっているかを確かめます。**hook が `claude.turn_timeout_ms`（既定1時間）のあいだ1件も来ておらず、そのうえで次の2つが揃ったときだけ手放します。

| 何を見るか | 手放してよい条件 |
| --- | --- |
| **agent の状態** | `idle` か `done` である（`working` / `blocked` / `unknown` では手放しません） |
| **agent の状態が変わった連番**（herdr の `state_change_seq`） | **2回続けて同じである**（＝その間に状態が1度も変わっていない）。**最初に読んだ巡回では手放しません**（そこからどれだけ止まっていたかが分からないためです） |

**サブエージェントも、この2つで見ています。**サブエージェントの出力も同じ pane へ出るので、
**何かが動いているあいだ agent の状態は `working` のままです。**

**連番を読めないときは手放しません。**その pane は打ち切りの判定に任せます。

**設計の途中で pane の版**（`revision`）**を使う案がありましたが、採りませんでした。**
**あれは画面を1バイトも見ておらず、端末のタイトルの本文が変わったときだけ増えます。**
**continuo が起動した pane では、タイトルが issue の識別子で固定されるので永久に増えません。**
**採っていたら「2回続けて同じ」が常に成り立ち、実質「agent の状態を2回読んだ」だけになっていました。**
**観測と観測の間に作業の山が丸ごと入っていても気づけません。**
**この判定は、配布された版に入ったことがありません**（`revision` を使う案は、この版を作る途中で試して取りやめたものです）。

**同じ理由で、打ち切りの判定も `revision` を見るのをやめました。**
**いまは agent の状態が `working` かどうかで測ります。**
**この版より前は、「画面が動いているので待ち続けます」の枝が1度も発火していませんでした。**

**待つ時間は `weekly_wait_limit_minutes` を超えることがあります。**
pane が動いているかぎり待つためです。**書きかけの編集を持ったまま pane を閉じないための待ちです。**

### `continuo doctor` が動けなかったときの終了コードが、1 から 3 になりました

**`continuo doctor` の終了コードをスクリプトで見ている人だけに関係します。**設定に足すものはありません。

**次の4つのとき、終了コードが 1 ではなく 3 になります。**どれも、検査を1件も行わずに止まる場合です。

| どんなとき | 前 | いま |
| --- | --- | --- |
| いまいるディレクトリを引けない | 1 | **3** |
| `continuo doctor --missing-keys-patch` で `WORKFLOW.md` を読めない | 1 | **3** |
| `continuo doctor --missing-keys-patch` で front matter を切り出せない | 1 | **3** |
| `continuo doctor --missing-keys-patch` で差分を書き出せない | 1 | **3** |

**1 は「検査で `✗` が1つ以上あった」だけを表すようになりました。**
**3 は「`continuo doctor` そのものが動けなかった」です**（接続先の環境変数が不正なとき・検査結果を書き出せないときは、前から 3 でした）。
**`continuo doctor --missing-keys-patch` は検査をしないので、1 を返すことはなくなりました。**成功は 0、引数の誤りは 2、動けなければ 3 です。

**「0 でなければ失敗」と見ているスクリプトは、そのまま動きます。**
**「1 なら失敗」と値を名指しで見ているスクリプトは、3 も失敗として扱うように直してください。**

### 成果の報告が無いまま `In Review` に並んでいた issue が、`Blocked` になります — 設定に足すものはありません

**エージェントが成果のコメントを書かずに終えると、continuo はセッションを復元して書かせ直します。**
その準備（worktree の身元ファイルを読む・herdr の workspace を開き直す・pane を引く・agent 名を決める）が失敗したとき、
**これまではログに警告を1行出すだけで、issue は `In Review` のままでした。**

**この版からは、Status を `failure_state`（既定は `Blocked`）へ動かし、原因を書いた引き渡しの通知を1件投稿します。**
`Done` など `terminal_states` の issue は Status を書き換えず、通知だけ付きます。

**`In Review` へ来たことを合図に何かを動かしている人は、同じ issue が `Blocked` へ移ることがある、と読み替えてください。**

### 着手の途中で失敗したとき、continuo が新しく開いた pane を閉じます — 設定に足すものはありません

**`workspace_hooks.after_create` や `before_run` の失敗などで、Claude Code を起動する前に着手が止まったとき、
これまでは herdr にシェルだけの pane が残りました。**
**この版からは、continuo が新しく開いた pane を閉じます。**

**次の場合は、これまでどおり閉じません。**

| どんなとき | なぜ閉じないか |
| --- | --- |
| 既に開いていた workspace の pane | 人間が自分で開いた pane かもしれない |
| `herdr.worktree.create_via_herdr: false` の設定 | herdr が pane の ID を返さない |
| herdr が worktree を開いた直後に、continuo の検算が失敗した | continuo が pane の ID を控える前に止まる |

### `Done` にした issue の worktree が片付かなかったとき、issue にコメントが1件付きます — 設定に足すものはありません

**`In Review` で終わった issue を `Done` へ動かすと、巡回が worktree を片付けます。**
commit していない変更や、push していない commit が残っていて片付けを見送ったとき、**これまではログにしか出ませんでした。**

**この版からは、issue に「worktree を片付けずに残しました」のコメントを1回だけ書きます。**
**ログの警告は、これまでどおり巡回のたびに出ます。**

**投稿に失敗したときは、やり直しません**（同じコメントが2件付くのを避けるためです）。
そのときは、continuo を再起動するか、その issue に着手し直すまで、コメントは付きません。
`cleanup.enabled: false` の機械では、何も変わりません。

| **途中経過の報告だけで終えた run に、continuo が成果の報告を書かせ直すようになりました** | **要りません**（下の節） |
| **`continuo init` が置く雛形の「書く言語」が、front matter の `language` に連動するようになりました** | **要りません。**既にある `WORKFLOW.md` は書き換わりません（下の節） |
| **成果がこの worktree の外にあるとき、commit と push の指示を `WORKFLOW.md` の本文で上書きできるようになりました** | **要りません。**使いたい人だけ書きます（下の節） |
| **`continuo init` が2枚目（`continuo-ci.yaml`）を置くようになりました** | **もう一度 `continuo init` を叩いてください**（下の節）。**`--force` は要りません** |
| **エージェントが、実装のレビュー結果を pull request のコメントへ貼るようになりました** | **要りません。**組み込みの指示書が変わっただけです（下の節） |
| **エージェントが、設計のレビュー結果を issue のコメントへ貼るようになりました** | **要りません。**ただし**その目印を数える CI を置くかどうかは、あなたが決めます**（下の節） |
| **`continuo doctor` の項目が16から18に増えました** | **要りません。**増えたのは `自動化` と `agent teams` の2つです（下の節） |
| **continuo が issue へ出す「対応表を足してください」の案内が変わりました** | **要りません。**貼ると起動しなくなる形だったのを、**雛形に既にある行を書き換える形へ直しました**（下の節） |
| **グループでまとめて直したとき、代表以外の issue にもコメントが付くようになりました** | **要りません。**設定にも `WORKFLOW.md` にも足すものはありません（下の節） |
| **エージェントが、計画そのものを issue のコメントへ書くようになりました** | **要りません。**組み込みの指示書が変わっただけです（下の節） |
| **`--port` の画面に「run をまたぐ累計」の表が増え、JSON に `cumulative_totals` が増えました** | **要りません。**既存の表も `totals` も1つも変わりません（下の節） |
| **エージェントが、計画に mermaid の図を入れ、人間へ読ませるコメントの節の形を揃えるようになりました** | **要りません。**組み込みの指示書が変わっただけです（下の節） |

**1台だけで動かしているなら、表のいちばん上の1行は読み飛ばしてかまいません。**
**`WORKFLOW.md` に足すキーも、消すキーもありません。**

### 同じカンバンを複数の機械で見張っている場合 — 全部同時に入れ替えてください

**何が変わったか。**v0.1.14 まで、continuo は「どの機械が担当しているか」を
issue のコメントに書いた機械の名前（`os.Hostname()` の値）で見分けていました。
**v0.1.15 からは、その機械の `gh` がログインしている GitHub アカウントで見分けます。**

**機械の名前は重複します。**WSL のディストリは既定が Windows のホスト名なので、
`/etc/wsl.conf` に書かないかぎり2つとも同じ名前になります。社内で命名規則に沿って
配られた PC も衝突します。**重複すると、2台とも「自分が勝った」と読みます。**

**そのため、issue に書かれるコメントの中身が変わります。**

```
（v0.1.14 まで）
<!-- continuo:bid -->
{"host": "mac-studio", "five_hour": 87, "weekly": 16, "score": 190, "at": "2026-08-29T16:45:00+09:00"}

（v0.1.15 から）
<!-- continuo:bid -->
{"five_hour": 87, "weekly": 16, "score": 190, "at": "2026-08-29T16:45:00+09:00"}
```

**誰が書いたかは、GitHub がそのコメントに付ける投稿者で分かります。**JSON には入りません。
**hold のコメントからも `host` が消えます**（`assignee` は残ります）。

#### 古いコメントは、そのまま読めます

**v0.1.15 の continuo は、v0.1.14 が書いたコメントを読めます。**
JSON は知らないキーを無視するので、`host` があっても無視されるだけです。
**走っている issue の担当も、そのまま引き継がれます。**

#### 混ざっていると何が起きるか

**v0.1.14 の continuo は、v0.1.15 が書いた入札を1件も数えません。**
古いほうは「機械の名前の無い入札は数えない」という決まりを持っているためです。

**そのため、2台とも「自分が勝った」と読む回が出ます。**
そうなると**その issue の担当者が2人になり、両方が同じ名前の branch で作業を始めて、片方の push が通りません。**

**この状態は、放っておいても戻りません。**担当者が2人ある issue に、continuo は新しく着手しません。
**issue にはその理由が書かれません**ので、continuo のダッシュボードで確かめてください。
**あなたが担当者を1人に戻すまで続きます。**

**やること。****同じカンバンを見張る機械を、全部 v0.1.15 へ入れ替えてください。**
**走っている issue がある機械は、その run が終わってから入れ替えてください**（v0.1.14 のときと同じです）。

**入れ替え終わったかの確かめ方。**それぞれの機械で叩いてください。

```bash
continuo version
```

**全部が `v0.1.15` 以降になっていれば、混ざっていません。**

#### 同じ GitHub アカウントで複数の機械を動かしていた場合

**その使い方は、v0.1.14 でも `docs/FAQ.md` が「サポートしていません」と書いていました。**
**v0.1.15 では、機械を見分ける手立てが1つも無くなります。**
**機械ごとに別の GitHub アカウントを用意してください。**手順は
[FAQ.md](FAQ.md) の「同じ GitHub アカウントで、複数の PC を動かしたい」にあります。

#### issue に出る文面が変わりました — 手を動かすものはありません

**識別子が機械の名前からアカウント名に変わったので、その値を差し込んでいる文面も変わります。**
**設定に足すものも消すものもありません。**この節より下にある古い版の案内は、
**その版で実際に出ていた文面のまま残してあります。**

| どこで見えるか | v0.1.14 まで | v0.1.15 から |
| --- | --- | --- |
| **入札のコメント** | `<機械の名前>` がこの issue の担当に立候補しています | **`<アカウント名>` がこの issue の担当に立候補しています** |

### `continuo prompt --show --url` で、実際に送られる文面を先に見られます

**v0.1.14 まで。**`continuo prompt --show` は変数を展開しませんでした。
`{{.issue.identifier}}` や `{{if .attempt}}` がそのまま出るので、
**`WORKFLOW.md` の本文にテンプレートを書いた人は、それが正しく展開されるかを事前に確かめられませんでした。**
**間違いに気づくのは、エージェントが動き出したあとでした。**

**v0.1.15 から。**`--url` に issue の URL を渡すと、**その issue の値で展開した全文が出ます。**（v0.2.0 から最初のメッセージに付く、人間のコメントの節は出ません）

```bash
cd ~/continuo-work && continuo prompt --show --url https://github.com/octocat/hello-world/issues/42
```

| 何を足したか | 中身 |
| --- | --- |
| **`--url <issue の URL>`** | その issue の値で変数を展開する。**カンバンを1回読む**（104件のカンバンで2リクエスト・計8ポイント。100件ずつ読み、見つかった時点で止めるので、大きさで変わる） |
| **`--attempt <回数>`** | 何回目の試行として展開するか。**省いても `1` を渡しても1回目**（continuo は1回目に試行回数を渡さないため）。やり直しのときの文面は `--attempt 2` 以上で見る |

**番号ではなく URL です。**1枚のカンバンに複数のリポジトリの issue が載るので、
**番号だけでは、どのリポジトリの issue か決まりません。**

**`--url` を付けなければ、いままでと1つも変わりません。**GitHub も叩きません。

**`--builtin` とは同時に指定できません。**`--builtin` は `WORKFLOW.md` を1バイトも読まない道で、
**`--url` は front matter の `tracker` の設定を読まないと issue を引けません。**

**引けなかったときは、何も出さずに終わります。**変数を展開しないまま出すことはしません。
**そうすると `--url` を付けなかったときと同じものが出て、気づけなくなるためです。**
断られ方の一覧は [FAQ.md](FAQ.md) の「書いたテンプレートが、実際にどう展開されるかを先に見たい」にあります。

### エージェントが、作業を始める前に worktree の分岐元を取り込みます

**v0.1.14 まで何が起きていたか。**continuo は issue に着手するとき worktree を1つ作ります。
その worktree は、そのときの分岐元（`main` など）から切られます。
**その issue が時間をおいて再開されると、分岐元はその間に進んでいます。**
ところがエージェントは、進んだぶんを取り込まずに作業を始めていました。
**組み込みの指示書に、分岐元を取り込む指示が1文字も無かったためです。**

**何が困るか。**既に直っているものを直し直します。分岐元で構造が変わったファイルを、
変わる前の形で書き換えます。**その作業は、pull request を出したあとのマージで捨てられます。**

**v0.1.15 から。**組み込みの指示書の `## 3-1.` が、読む前に取り込ませます。

**分岐元の名前は4段で決まります。上から順に見て、決まった時点で止まります。**

| 順 | 何を見るか |
| --- | --- |
| 1 | **worktree の直下にある continuo の記録ファイル**（既定 `.continuo.json`。`workspace.identity_file` で名前を変えられます）**の `"base"` の値** |
| 2 | `WORKFLOW.md` の本文（`## 4-4. このプロジェクトの決まり` に入る部分）に指定があれば、それ |
| 3 | issue にリンクされた branch |
| 4 | リポジトリの既定 branch |

**段1 がいちばん確かです。**continuo は worktree を作るときに、実際に使った分岐元をそこへ書いています。
**本文の指定を上に置いていません。****本文は issue をまたいで同じ文言だからです。**
本文に「分岐元は develop です」と書くと、**既定 branch から切った worktree にも develop が混ざります。**
**衝突しないので、誰も気づきません。**

**`herdr.worktree.base`（worktree を切る分岐元。既定 `null`）を設定している人へ。**
**段1 がその値を持っているので、何も書かなくても当たります。**
**書く必要があるのは、`workspace.identity_file`（記録ファイルの名前。既定 `.continuo.json`）の名前を変えていて、
かつエージェントがその記録ファイルを見つけられなかったときだけです。**
そのときは段3 か段4 へ落ちるので、**`develop` から切った worktree に `main` が混ざります。**
**その2つに当てはまるときだけ、本文に1行書いてください。**
**当てはまらないなら書かないでください。**本文は issue をまたいで同じ文言なので、
**分岐元が issue ごとに違う運用では、書いたほうが外れます。**

```markdown
### 分岐元

この worktree の分岐元は develop です。
```

**落ちたときの扱いは、落ちた場所で分かれます。**

| どこで落ちたか | エージェントがどうするか |
| --- | --- |
| **取ってくるところ**（その名前が remote に無い） | **取り込むものが無いだけです。**そのまま作業を続けます |
| **マージを始める前**（commit していない変更がある） | **先に commit してから取り込み直します。**前の試行が残した作業なので、捨てません |
| **マージの途中**（衝突した） | **`git merge --abort` で取り込む前へ戻してから止まります**（Status が `Blocked` になります） |

**衝突のときだけ戻します。**組み込みの指示書は `blocked` の前に commit と push を求めるので、
**戻さないと、衝突の印が付いたままのファイルが branch へ push されます。**
**commit していない変更で断られたときに `git merge --abort` を打っても効きません**
（マージが始まっていないので `There is no merge to abort` で落ち、変更も残ります）。

### 途中経過だけで終えた run に、成果の報告を書かせ直します

**v0.1.14 まで何が起きていたか。**continuo は run の終わりに
「エージェントがこの run の報告を書いたか」を確かめ、書いていなければセッションを復元して書かせます。
**その判定が、途中経過の報告も「書いた」と数えていました。**

| 順 | 何が起きるか |
| --- | --- |
| 1 | エージェントが長い作業の途中で「まだ作業中です」と1回書く |
| 2 | **そのまま最後の報告を書かずに終える** |
| 3 | **continuo は「書かれている」と判定し、書き直させない** |
| 4 | **issue には「まだ作業中です」だけが残る** |

**`In Review` に立っているのに、何が直ったのか、どこを見ればよいのかが分かりません。**

**v0.1.15 から。**途中経過の報告（`continuo:progress` の印が付いたもの）は、成果の報告として数えません。

**設定に足すものはありません。**
**エージェントが成果の報告をちゃんと書いていれば、いままでと1つも変わりません。**

**枠の使い方は増えることがあります。**いままで静かに通っていた run
（途中経過だけ書いて終えたもの）に、セッションを復元して書かせるようになります。
**復元は Claude Code を起動し直すので、レートリミットの枠を使います。**
**それが起きるのは、次の2つのときです。**

    1. エージェントが成果の報告を書き忘れた
    2. 成果の報告を書いたが、途中経過の報告のコメントへ書き足した

**2 も「書かれていない」と判定されます。**本文のいちばん上に途中経過の印が残るためです。
**組み込みの指示書には「新しく1件投稿してください」を足してあるので、次からは 2 は起きません。**

**成果の報告の中で、この印について書くときは、山括弧を外した `continuo:progress` の形で書いてください。**
**成果の報告かどうかを見るときは、本文のいちばん上にある印の並びだけを見ます。**
本文の途中で引用しても、途中経過とは読まれません。

**ただし、囲み付きのまま（`<!` から始まる形で）書かないでください。**
**エージェント自身が「書き足す先」を探す問い合わせは、印が本文のどこにあっても拾います。**
**囲み付きで引用すると、次の途中経過の報告が、その成果の報告へ書き足されます。**
**持ち回りの死活の判定だけは、いままでどおり印が本文のどこにあっても数えます**
（そちらを厳しくすると、書き足し続けているエージェントの担当が18時間で外れます）。

**書き直しを頼むときの文面にも、「途中経過の報告へ書き足さないでください」を足しました。**
足さないと、エージェントは組み込みの指示どおり途中経過へ書き足し、
**書いたのに「書かれていない」と判定されて人間へ引き渡されます。**

### 雛形の「書く言語」が、front matter の `language` に連動するようになりました

**v0.1.14 まで。**`continuo init` が置く `WORKFLOW.md` の雛形が、
`### 書く言語` の節に「issue のコメント・pull request の本文・commit メッセージ・
コードのコメントは、すべて日本語で書いてください」を持っていました。

**continuo は OSS として配っています。****日本語を読み書きしない人も `continuo init` を叩きます。**
その人の手元でも、エージェントは issue のコメントと commit メッセージを日本語で書いていました。
**その節を消すか書き換えるまで、気づけません。**

**front matter の `language`（画面に出す文言の言語。既定 `auto` で、環境変数 `LANG` から決めます）とは
別物で、連動していませんでした。**`LANG` が英語の環境でも、
**画面は英語になり、エージェントは日本語で書いていました。**

**v0.1.15 から。**`continuo init` が、`### 書く言語` の1行を `language` から決めて書きます。
`ja` なら「すべて日本語で書いてください」、`en` なら英語の指示です。
**その1行は、書き換えても消してもかまいません。**消すと、エージェントの既定に任されます。

**組み込みの指示書は、いまのところ日本語だけです。**`language` が `en` でも、その大半は日本語のまま届きます。
**英語版を作る作業は別に立ててあります**（issue #226。
「日本語を読まない利用者が、エージェントへ送られる指示書の大半を日本語のまま受け取る」）。

#### あなたの `WORKFLOW.md` はどうなるか

**1文字も変わりません。**雛形が書かれるのは `continuo init` のときだけです。

| どうしたいか | 何をするか |
| --- | --- |
| **いままでどおり日本語で書かせたい** | **何もしません。**あなたの `WORKFLOW.md` にその節が残っています |
| **別の言語で書かせたい** | その節を書き換えます |
| **エージェントの既定に任せたい** | その節を消します |

**`continuo init --force` は使わないでください。**front matter も本文も雛形へ戻ります。

### 成果がこの worktree の外にあるときの逃げ道

**誰に関係するか。****issue が非公開のリポジトリにあり、コードは別のリポジトリ（public の fork など）にあって、
pull request は本家へ出す、という運用をしている人だけです。**それ以外の人には関係がありません。

**v0.1.14 まで。**組み込みの指示書が「`review` または `blocked` を出す前に、必ず commit して push してください」を
**例外なく求めていました。**この運用では、成果は worktree の外の clone にあります。
**`WORKFLOW.md` の本文に「この worktree の中では commit しないでください」と書いても、
組み込みの指示と正面から食い違い、どちらに従うかがエージェント次第になっていました。**

**v0.1.15 から。**組み込みの指示書が例外を1つ持ち、本文へ譲ります。
**発動には次の2つが両方要ります。**

| 要るもの | なぜ |
| --- | --- |
| **`OWNER` / `MEMBER` / `COLLABORATOR` が「コードは別のリポジトリにある」と書いていること** | **public のリポジトリでは誰でも issue に書けます。**絞らないと、外部の人が1行書くだけで worktree の commit と push を飛ばせます |
| **`WORKFLOW.md` の本文に、成果の出し方が書いてあること** | **書いていなければ、譲る先がありません** |

**片方でも欠けていれば、いままでどおり commit と push を求めます。**

**本文に書く中身の実物は、`docs/plans/continuo_design.md` の 3-78b にあります。**

### `continuo init` が2枚目を置くようになりました — **もう一度叩いてください**

**v0.1.14 まで。**`continuo init` が置くのは `WORKFLOW.md` の1枚だけでした。
**CI の設定を配る手段がありませんでした。**

**v0.1.15 から。**同じディレクトリに `continuo-ci.yaml` も置きます。
**これは設定ではありません。**continuo は起動時に1バイトも読みません。
**`.github/workflows/` へ移すための見本です。**

**既に `continuo init` を叩いた人は、もう一度叩いてください。**

```bash
cd ~/continuo-work && continuo init .
```

**`--force` は要りません。**既にある `WORKFLOW.md` には触らず、
**足りない `continuo-ci.yaml` だけを置きます。**

> **`--force` を打たないでください。**あれは `WORKFLOW.md` を本文ごと上書きします。
> **あなたが手で書いた指示が1行も残りません**（上の「`continuo init --force` で作り直さないこと」）。

**置いたあと、中身を確かめてから `.github/workflows/` へ移してください。**
**既に CI がある場合は、中身を既存の CI へ組み込むよう、お使いの AI に頼んでください。**

```bash
# 中身を読む
cd ~/continuo-work && cat continuo-ci.yaml

# 移す（リポジトリの中で叩いてください）
mkdir -p .github/workflows && mv continuo-ci.yaml .github/workflows/
```

**移さなくても構いません。**continuo は動きます。**移すと、レビューを飛ばした
pull request の検査が赤くなります。**

**赤いだけではマージを止められません。**branch protection の必須の検査へ
`design-review-result` と `code-review-result` の2つを入れて、はじめて止まります。

### 判断票を貼る先が変わりました — 設定に足すものはありません

**v0.1.14 まで。**組み込みの指示書は、実装のレビューの判断票も

### 計画そのものを issue へ書くようになりました — 設定に足すものはありません

**v0.1.14 まで。**組み込みの指示書は、判断票を書けとしか言っていませんでした。
**計画そのものを残す指示が1文字もありませんでした。**

**v0.1.15 から。****実装の前に、計画を issue のコメントへ書かせます。**
書くのは3つです。何が原因か（ファイル名と行番号つき）／どのファイルをどう直すか／決まっていないこと。

**`<!-- continuo:plan -->` を2行目に置かせます。**
**この印は、CI が数える対象ではありません。**設計のレビューを数えるのは
`<!-- design-review-result -->` のほうです。

**印が要る理由は、continuo が成果の報告と見分けるためです。**
**印が無いと、計画のコメントを「この run は成果を書いた」と数えます。**
計画は run の最初に書かれるので、その判定はほぼ必ず外れます。
外れると、turn が途中で終わった run に「何をしたか」を書かせ直す経路が飛びます。

**なぜ変えたか。**上の `continuo-ci.yaml` が数える場所と、エージェントが書く場所を
揃えるためです。**揃っていないと、エージェントが指示どおりに書くほど検査が赤のままになります。**

**本文へ足すものはありません。**組み込みの指示書は continuo の実行ファイルの中にあり、
**版を上げれば自動で新しくなります。**

**送られる文面は次で読めます。**

```bash

```

### `自動化` — カンバンの自動化が有効なのに、書き戻しの対応表が空

**カンバンの組み込みの自動化が Status を書くと、continuo はそれを「知らない Status」と読んで走行中の run を止めます。**
**止めずに続けさせる唯一の設定が `tracker.automated_state_rewrite` です。**
**これが空のままで自動化を有効にしていると、PR を issue へ紐づけた瞬間に run が止まります。**

**いままでは、止まってから初めて気づく状態でした。**この行が、起動する前に知らせます。

```text
! 自動化          Status を書きうるカンバンの自動化が 2件 有効なのに、tracker.automated_state_rewrite が空です
```

**記号は `!` までで、`✗` にはなりません。**空でも continuo は起動して走ります。
**`Auto-add …` で始まる自動化は数えません**（item を載せるだけで Status を書かないためです）。
**どの自動化がどの Status を書くかは GitHub の API が公開していない**ので、
**有効な自動化の名前を並べます。**そのどれも Status を書かないなら、この注意は無視して構いません。

**対応表の書き方は、下の「`tracker.automated_state_rewrite` — 自動化に動かされた Status を戻す」にあります。**

### `agent teams` — Claude Code の agent teams が有効になっていないか

**agent teams が有効な環境では、名前つきの `Agent` ツールの呼び出しが teammate として起動し、
その許可の確認がリードの pane に出ます。**continuo はそれを `blocked` と読み、
**pane を閉じて issue を `tracker.failure_state` へ落とします。**

**いままでは文書に書いてあるだけでした。**この行が、起動する前に知らせます。

```text
✓ agent teams     読めた出どころに agent teams を有効にする設定はありません
                  読んでいない出どころ: 組織の managed settings ／ …
```

**読むのは2か所だけです。**`claude.env` と、`continuo doctor` を叩いたシェルの環境変数です。
**残り5か所は読みません**（組織の managed settings・対象リポジトリの2ファイル・
利用者の `~/.claude/settings.json`・herdr の pane の環境）。
**読んでいない出どころは、`✓` のときも必ず並びます。**読めた範囲だけを見て断言しないためです。

**書いていないことは警告しません。**agent teams は Claude Code の既定で無効なので、
**`1` を見つけたときだけ知らせます。**

**詳しくは [docs/FAQ.md](FAQ.md) の「サブエージェントを呼んだ issue だけが `Blocked` に落ちる（agent teams）」にあります。**

**当てる必要はありません。**次に自動化が Status を動かしたときから、新しい案内が出ます

### `--port` の画面に「run をまたぐ累計」が増えました — 既存の表は変わりません

**`--port` を使っていない人には関係ありません。**既定では画面を開きません。

**何が困っていたか。**画面のトークンの合計が、**ほとんどいつも 0 でした。**
合計は「いま走っている run」だけを足しており、**run が終わると、その run のトークンも一緒に消えていた**ためです。
**turn が長いあいだは、走っている run の値もまだ 0 なので、全部が 0 に見えました。**

**何が増えたか。**

| どこ | 何が増えたか |
| --- | --- |
| **画面**（`http://127.0.0.1:<番号>/`） | 表がもう1つ。**いちばん下に「run をまたぐ累計」が並びます** |
| **JSON**（`/api/v1/state`） | 鍵が1つ。**`cumulative_totals`** |

**既存のものは1つも変えていません。**画面の3つの表も、JSON の `totals` の中身も、そのままです。
**`totals` を読んでいる道具は、書き換えなくても動きます。**

**累計の意味。**「**この continuo が起動してから、turn の終わりに読み取った transcript の合計**」です。

| 何 | どうなるか |
| --- | --- |
| **走行中の turn のぶんは入りません** | 集計は turn が終わったときに1回だけ走ります |
| **引き継いだ run では、起動より前のぶんも入ります** | continuo を再起動しても pane の Claude Code は生きたままで、transcript に前のぶんが残っているためです |
| **continuo を再起動すると 0 に戻ります** | メモリだけに持っています。**課金の明細の代わりにはなりません** |

**画面が何のためのものかは [FAQ.md](FAQ.md) の
「走っている continuo の中身を見たいとき」にまとめてあります。**

### ロックの置き場所が固定され、`runtime` の節が無くなりました — **2行消してください**

> **上げる前に、動いている continuo を止めてください。**
> **v0.1.14 で、二重起動を止めるロックの置き場所が変わります**（hook の socket と同じディレクトリ →
> `~/.continuo/continuo.lock`）。**止めずに入れ替えると、古い continuo が握っているのは古い場所のロックで、
> 新しい `continuo abandon` が見るのは新しい場所です。**そこは空いているので、
> **`abandon` は「continuo は動いていません」と判定し、走っている worktree を消しにいきます。**
>
> ```bash
> pgrep -lx continuo     # 動いているものを確かめる
> ```
>
> **最後の砦は残っています。**その worktree に herdr の pane が生きていれば `abandon` は止まります。
> **ただし `--force` はそれを越えます。**上げている最中に `--force` を付けないでください。

**v0.1.13 まで。**二重起動を止めるロックは、hook の socket と同じディレクトリに置かれていました。
socket の場所は `CONTINUO_RUNTIME_DIR` / `XDG_RUNTIME_DIR` / `TMPDIR` で動くので、
**launchd から起動した continuo と、端末で叩いた `continuo abandon` が別の場所を見ることがありました。**
食い違うと、`abandon` は動いている continuo を「動いていません」と判定し、
**生きている worktree を消しにいきます。**

**v0.1.14 から。**ロックは `~/.continuo/continuo.lock` の1本に固定されます。
**環境変数でも設定でも動きません。**

**`runtime` の節は消しました。**設定で動かせない以上、置いておく意味がありません。
**読まない項目を残すと、次に読む人が「効いている」と思って設定します。**

#### 何もしないとどうなるか

**起動しません。**front matter は未知のキーを弾くので、次のエラーで止まります。

```
front matter が不正です: [167:1] unknown field "runtime"
（`[167:1]` は、あなたの WORKFLOW.md の何行目かです。数字は人によって違います）
```

#### どう直すか

**`WORKFLOW.md` から `runtime:` の2行を消すだけです。**`continuo init --force` は使わないでください
（front matter も本文も雛形へ戻ります）。

```bash
grep -n -A1 '^runtime:' ~/continuo-work/WORKFLOW.md   # 消す行を確かめる
```

```yaml
runtime:
  lock_file: null    # ← この2行を消す
```

**消したら起動します。**ロックは `~/.continuo/continuo.lock` になります。

#### 1台で2本以上動かしたいとき

**`--id <名前>` を付けてください。**開発中に、本番を止めずにテスト版を動かすためのものです。

```bash
continuo --id e2e ~/continuo-e2e-work
continuo abandon --id e2e <issue の URL> ~/continuo-e2e-work
```

**`--id` が分けるのはロック1本だけです。**worktree の置き場所（`workspace.root`）と
socket（`claude.hook_bridge.listen`）は分かれないので、
**テスト用の `WORKFLOW.md` を別のディレクトリに置いて、そちらで書き換えてください。**

**名前に書けるのは、小文字の英数字とハイフンだけです。**先頭は英数字、32文字まで。

### 同じカンバンを複数の機械で見張っている場合 — 走っている issue があるなら、終わってから入れ替えてください

**1台だけで動かしているなら、この節は読み飛ばしてかまいません。**

**何が起きるか。**v0.1.13 までの機械は、進捗のコメントに `<!-- continuo:progress -->` の印を付けません。
**v0.1.14 の機械から見ると、その issue は「進捗報告が1件も無い」ように見えます。**
そのとき18時間の時計は、担当を取った時刻（`<!-- continuo:hold -->` のコメント）から数えます。

**18時間より長く走っている issue があると、入れ替えた機械が最初の巡回（既定30秒以内）で
その担当を外し、入札をやり直します。**走っていた機械は
`tracker.provider.handoff.recheck_interval_ms`（既定1時間）で気づいて止まるので、
**push していない変更が失われます。**

**先に走っている側を入れ替えても防げません。**引き継ぎでは1回目の指示書を送り直さないので、
**走っている run のエージェントは、その run が終わるまで新しい印を教わりません。**

**やること。****走っている issue がある機械は、その run が終わってから入れ替えてください。**
走っている issue が無ければ、順番は問いません。

### 進捗のコメントが1件にまとまります — 設定に足すものはありません

**複数の機械で同じカンバンを見張っているときだけ関わる話です。**1台で動かしているなら、
issue の見た目が変わるだけです。

**v0.1.13 まで。**エージェントは1時間ごとに**新しいコメントを1件投稿していました**
（`## 長くかかるときは、途中でも状況を書くこと`。持ち回りの18時間の時計を進めるためです）。
**18時間の作業で18件並び、issue を開いても本題が読めませんでした。**

**v0.1.14 から。****いちばん下のコメントが自分の進捗報告なら、その1件に行を書き足します。**

```
<!-- continuo:agent -->
<!-- continuo:progress -->
まだ作業中です。

- 2026-09-03T05:40:34Z いま テストを直しています
- 2026-09-03T06:41:02Z いま PR の指摘に答えています
```

**間に別のコメントが入ったときは、書き足さずに新しく1件投稿します。**
**あなたが書いたコメントを、エージェントが書き潰さないためです。**前の進捗報告はそのまま残ります。

**持ち回りの期限は、書き足しでも進みます。**
GitHub はコメントを編集しても作成時刻を動かしませんが、更新時刻は進みます。
**continuo は v0.1.14 から、コメントの更新時刻も見るようになりました。**

**同時に、18時間の時計を進めるコメントが絞られました。**
**進めるのは `<!-- continuo:progress -->` が入っているコメントだけです。**

**v0.1.13 まで。**時計は「担当者のアカウントが投稿したコメント」で数えていました。
**エージェントも continuo もあなたも、同じ GitHub アカウントで投稿します。**
**だから、あなたが無関係なコメントを1件書くたびに、時計が振り出しに戻っていました。**
**落ちて黙り込んだ機械の担当が、それだけで18時間延びます。**別の機械が拾い直せません。

**v0.1.14 から。****あなたが書いたコメントでは、時計は進みません。**
落ちた機械の担当は、進捗報告が18時間現れなければ予定どおり外れます。
**あなたがこの印をコメントへ書いても構いません。**そのぶん時計が延びるだけで、書く理由はありません。

**当たっているかは、送られる文面で確かめます。****このコマンドは `WORKFLOW.md` を読みません。**

```bash
continuo prompt --show --builtin | grep -c '<!-- continuo:progress -->'
```

**`0` より大きければ入っています。**`0` なら、v0.1.14 より前の continuo が動いています。

**知っておくこと。**担当者が古い進捗報告を1文字直しただけでも、18時間の時計は振り出しに戻ります。
**進捗報告を新しく1件書いたときも同じことが起きます**ので、同じ種類の遅れです。
**進捗報告以外のコメントは、編集しても新しく書いても、時計を1秒も進めません。**

**症状から引きたいときは [FAQ.md](FAQ.md) の
「進捗のコメントが1件にまとまり、増えなくなりました」を見てください。**

### エージェントが PR を作るようになりました — 止められません

**v0.1.13 まで。**`continuo init` が置く本文に、次の節が入っていました。

```markdown
## PR を作るか

**PR は作らないでください。**push まで行い、そこで人間へ渡してください。
```

**この既定は、誰も頼んでいないものでした。**エージェントは push で止まるので、
**branch を自分で見つけて PR を作るのは人間の仕事**になっていました。

**v0.1.14 から。**組み込みのプロンプトに `## 3-5. pull request を出す` が入りました。
**`CONTINUO-STATUS: review` を出す前に、エージェントが自分で PR を作ります。**

**止める口はありません。**本文に「PR を作らない」と書いてあっても、組み込みは「作れ」と指示します。

| エージェントがすること | 中身 |
| --- | --- |
| **既にある PR を先に探す** | いま居る branch（`git branch --show-current`）で引きます。あれば作り直さず、その branch へ push します |
| **無ければ作る** | `gh pr create` を叩きます。**draft にはしません** |
| **本文へ `Closes #<番号>` を入れる** | この1行が PR と issue を結びつけます。**次の turn がレビューの指摘を読む先になります** |
| **作れなかったら `blocked`** | 理由をコメントに書いて、人間へ渡します |

#### 調査だけ・レビューだけを頼んでいる場合

**commit する成果が無い run は PR を作れないので、`Blocked` で止まります。**

**その issue は、continuo に渡さないでください。**
`WORKFLOW.md` の本文に「PR を作らない」と書いても、この版からは効きません。

**確かめ方。**

```bash
cd ~/continuo-work && continuo prompt --show | grep -c 'この issue の pull request を作ります'
```

**`1` なら、組み込みの側に「作れ」という指示が届いています。**
**本文に「PR を作らない」と書いてあると、エージェントは反対の指示を2つ受け取ります。**
**どちらに従うかは決まりません。**確実に作らせたいなら、その行を消してください。

#### 何を変えられるか

**組み込みの決めごとを上書きできるのは、この3つだけです。**`WORKFLOW.md` の本文に書くと、組み込みより優先されます。
**付けるラベルのような、組み込みが何も言っていない決まりは、そのまま本文に書けます。**

| 変えられるもの | 本文へ書く例 |
| --- | --- |
| **draft にするか** | `pull request は draft で作ってください。` |
| **base にする branch** | `base は develop にしてください。` |
| **成果がこの worktree の外にあるときの出し方** | project ごとの手順 |

**「作るかどうか」は、この3つに入っていません。**組み込みの決めごとなので、本文では上書きできません。

### PR ができる回数が増えます — カンバンの自動化を有効にしている人だけ

**カンバンの `Workflows` を1つも有効にしていないなら、何もすることはありません。**

**カンバンの `Workflows` に `Pull request linked to issue` という自動化があります。**
有効にしていると、**PR が issue に紐づいた瞬間に Status を書き換えます。**

手元の2枚はどちらも無効でした。）
continuo は自分の知らない Status になった issue を、
`tracker.unknown_state_grace_ms`（既定10分）のあと止めます。

**v0.1.13 までは、エージェントが PR を作らなかったので、この自動化はめったに動きませんでした。**
**v0.1.14 からは、issue 1件につき1回は動きます。**
**本文に「PR を作らない」と書いてあっても同じです。**打ち消しの口は無く、
**エージェントがどちらに従うかは決まらないので、「作られない」を前提にしないでください。**

**直し方は `tracker.automated_state_rewrite` に対応表を書くことです。**
**書き換える場所の見つけ方は [FAQ.md](FAQ.md) の
「エージェントが PR を作った直後に止まる（automated_state_rewrite）」にあります。**

**左に何を書けばよいか分からないときは、書かなくて構いません。**

**「この行をこう書き換えてください」と、あなたのカンバンの Status 名を当てはめた形で書きます。**
**場所を見つける `grep` も一緒に書きます。**
**GitHub が「誰が動かしたか」の記録を残さなかった回は、この案内は出ません**（出なかったときの書き方は FAQ の同じ節にあります）。

### 送られる文面が作り直されました — 本文の見出しを `###` へ下げることを勧めます

**エージェントへ送る指示書を、7つのセクションへ並べ直しました。**

    1. 概要（処理の流れを図で）   5. 共通ルール
    2. 目的                       6. セキュリティ
    3. 手順                       7. その他
    4. 処理に必要なコンテキスト

**あなたが書いた本文は、4-4「このプロジェクトの決まり」の下へ挟まります。**

**やってほしいことが1つあります。****本文の見出しを `##` から `###` へ下げてください。**

**なぜか。**本文が挟まる `## 4-4. このプロジェクトの決まり` は `##` です。
**あなたの本文も `##` で始まっていると、エージェントから見て「4-4 の中身」ではなく
「4-4 と並ぶ別の節」に見えます。**下げると、あなたの決まりが 4-4 の中身として読まれます。

**下げなくても届きます。**内容が消えることはありません。**読み取りやすさの話です。**

### `idle_timeout_ms` を1時間以下にしている人は、起動しません — 一緒に下げてください

**`tracker.provider.handoff.idle_timeout_ms`（担当者の最後の進捗報告からこれだけ経つと担当を外して入札をやり直す間隔。ミリ秒。既定 64800000 = 18時間）を、
1時間（3600000）以下へ下げている人だけが当たります**（**`0` を書いている人は当たりません。**0 は「既定の18時間を使う」という意味です）。
**下げていなければ、この節は読み飛ばしてかまいません。**

**何が起きるか。**v0.1.14 で増えた
`tracker.provider.handoff.progress_interval_ms`（エージェントに進捗報告を書かせる間隔。ミリ秒）の既定が
**3600000（1時間）** で、**`idle_timeout_ms` より短いことを求めます。**
**あなたが1文字も書いていない新しいキーの既定値が、あなたが書いた値とぶつかります。**

```
front matter が不正です: 設定キー tracker.provider.handoff.progress_interval_ms の値 3600000 が不正です: tracker.provider.handoff.idle_timeout_ms（1800000 ミリ秒）より短くすること。長いと、エージェントが指示どおりに書いていても書く前に担当が外れる
```

**なぜ求めるか。**間隔のほうが長いと、**エージェントが指示どおりに書いていても、書く前に担当が外れます。**
そのとき別の機械が入札をやり直し、**push していない変更が失われます。**

**どう直すか。**`progress_interval_ms` を、`idle_timeout_ms` より短い値にしてください。
**60000（1分）以上にすること。**59999 までは、また起動が止まります。

```yaml
tracker:
  provider:
    handoff:
      idle_timeout_ms: 1800000        # 30分（あなたが書いていた値）
      progress_interval_ms: 600000    # 10分（これを足す）
```

**直したかどうかは、次で確かめます。**

```bash
continuo doctor ~/continuo-work
```

**`設定ファイル` の行が `✓` になれば直っています**（画面の言語が英語なら `config`）。

### 進捗報告の間隔を、設定から変えられるようになりました — 既定は1時間ですが、書かなくても起動が止まる人がいます

**v0.1.13 まで。**「1時間以上コメントを書かないまま作業を続けないでください」が、送る文面へ直に書かれていました。
**変えられませんでした。**

**v0.1.14 から。**`tracker.provider.handoff.progress_interval_ms`（エージェントに進捗報告を書かせる間隔。ミリ秒）で変えられます。

```yaml
tracker:
  provider:
    handoff:
      progress_interval_ms: 3600000   # 1時間。既定値
```

**何もしなければ、既定の1時間が使われます。**v0.1.13 と同じ振る舞いです。
**ただし `idle_timeout_ms` を1時間以下にしている人は、書かないままだと起動しません**（上の節）。

**2つの決まりがあります。**

| 決まり | 破ると |
| --- | --- |
| **60000（1分）以上にすること** | 起動しません。**送る文面へは分に直して埋めるので、59999 までは全部「0分以上黙らない」になります** |
| **`idle_timeout_ms`（既定18時間）より短くすること** | 起動しません。**長いと、エージェントが指示どおりに書いていても、書く前に担当が外れます。**`idle_timeout_ms: 0` と書いた場合も、実行時に効く18時間と比べます |

**continuo はこの値を測りません。**送る文面へ分に直して埋めるだけです。
**測っているのは `idle_timeout_ms` のほうだけです。**

### 行頭の HTML コメントが、送られなくなりました

**`WORKFLOW.md` の本文に書いた `<!-- … -->` は、エージェントへ送られなくなりました。**

**なぜか。**`continuo init` が置く雛形は、書き方の案内を HTML のコメントで書きます。
**それはエージェントへ送る情報ではありません。**v0.1.13 まではそれも送っていて、

**当てる必要があるのは、次の場合だけです。**

| こう書いていたら | どうなるか | どうするか |
| --- | --- | --- |
| **エージェントへの決まりを、HTML のコメントで書いていた** | **届かなくなります** | **コメントを外して、ふつうの文として書いてください** |

    字下げした <!-- … -->        … 4桁の字下げで書いたコード片
    バッククォートで囲んだ中     … ``` で囲んだ中身

**1つ打ち忘れると、その `<!--` は次に見つかった `-->` までを見出しごと飲み込みます。**

### 応答を差し戻す `Stop` hook との噛み合わせ — 設定は要りません

**用語です。**Claude Code の `Stop` hook は、`{"decision":"block","reason":"…"}` を返すと
**エージェントを止めずに、`reason` を指示として渡して応答を書き直させます。**これを**差し戻し**と呼びます。

**v0.1.12 まで。**差し戻しは hook の**戻り値**なので continuo には届かず、
continuo は「エージェントが止まってよいか尋ねた」という `Stop` を「turn が終わった」と読んでいました。
**書き直しの中央値は 21 秒で、continuo は 2 秒で締め切ります。**結果、
**書き直している最中の pane を閉じる／書き直した応答を読まない／遅れて届いた `Stop` を
次の turn の終わりとして数える**の3つが起きます。

**v0.1.13 から。**締め切りが来た瞬間に herdr へ「このエージェントはまだ動いているか」を1回聞き、
**動いていれば turn の終わりとせずに待ち直します。**

**あなたがすることは何もありません。****`WORKFLOW.md` は1文字も変えません。**
`Stop` hook を1本も入れていない場合も、これまでと同じ速さで turn が終わります
（締め切りの時点でエージェントは止まっているので、聞いた答えは「止まっている」になります）。

**症状から引きたいときは [FAQ.md](FAQ.md) の
「応答を書き直している最中のエージェントに、continuo が次の指示を送ってしまう」を見てください。**

### 長くかかるときは途中でも状況を書けという指示 — 設定に足すものはありません

### 入札と担当決定のコメントが、人間にも読める形になりました

**前の版まで、issue に書かれる入札と hold のコメントは JSON 1行だけでした。**
issue を開いた人には `five_hour` が何の値なのかも、次に何が起きるのかも読めませんでした。
**この版から、JSON の下に人間が読む2行が付きます**（担当を外したときのコメントと同じ形です）。

```
<!-- continuo:bid -->
{"host": "mac-studio", "five_hour": 87, "weekly": 16, "score": 190, "at": "2026-08-29T16:45:00+09:00"}

**mac-studio がこの issue の担当に立候補しています。**上の JSON は、その機械にレートリミットの枠がどれだけ残っているかです。
**担当は約3分後に自動で決まります。**締め切りまでに届いた入札のうち、枠の余裕がいちばん大きい機械が担当になります。
```

**「約何分後」は `tracker.provider.handoff.bid_window_ms` から出します。**分に切り上げるので、
既定の 180000 ミリ秒は「約3分後」になります。**0 にしてあるときは「締め切りを待たずに決まります」と出ます。**

**このコメントはエージェントへは渡しません。**今までどおり、issue を GitHub の画面で開いたときだけ見えます。

### issue にリンクした branch が、作業の起点になりました

**GitHub の issue の Development に branch をリンクしておくと、continuo はその branch を起点に
worktree を作ります**（今までは、いつでもリポジトリの既定 branch が起点でした）。
**手元の clone にその branch がまだ無ければ、その1本だけを取ってきます。**

**起点に使うのは「リンクがちょうど1本で、それが issue と同じリポジトリの branch」のときだけです。**
次のどれかに当たるときは、今までどおり既定 branch が起点になります。
**リンクを付けていないカンバンでは、何も変わりません。**

| どういうとき | 例 |
| --- | --- |
| **リンクが無い** | — |
| **リンクが2本以上ある** | どれを起点にするか決められません |
| **別のリポジトリの branch を指している** | fork の branch をリンクした |
| **branch 名に英数字・`_`・`-`・`.`・`/` 以外が入っている** | `作業/issue-42`・`feature/a+b` |

**どれに当たったかはログに WARN で1行出ます。**着手は止めないので、
**気づく手掛かりはこの1行だけです。**

```bash
grep 'リンクされた branch' <ログの出力先>
```

**リンクした branch を手元へ取ってこられなかったときは、着手そのものをやり直します。**
既定 branch へ黙って倒すことはしません（別の起点で作業が始まってしまうためです）。
**`agent.max_retries`（既定3回）まで待って試し直し、それでも取ってこられなければ
`failure_state` へ落として issue に理由を書きます。**回線が一時的に切れただけなら、
次の巡回で通ります。

**プロンプトのテンプレートで `{{.push_branch}}` が使えるようになりました。**リンクされた
branch の名前がそのまま入ります（`origin/` は付きません）。リンクが1本でないときは空文字なので、
`{{if .push_branch}}` で書き分けられます。**足さなくても今までどおり動きます。**

**上の表に当たったものが、全部空になるわけではありません。**空になるのは
**リンクが無いとき・2本以上あるとき・別のリポジトリの branch を指すとき**の3つです。
**branch 名に使えない文字が入っているとき（`作業/issue-42`）は、起点には使いませんが、
`{{.push_branch}}` にはその名前がそのまま入ります。**起点と push 先が別々に決まるためです。

### 差し替え方（branch を切り替えるな）

**`WORKFLOW.md` の「## この issue を読むこと」の行を探します。**その行の「直前」に足します。

**issue を読むより前に置くのが要点です。**エージェントが branch を切り替えるのは、
issue の本文や、そこから辿った PR のレビューを読んだ結果です。
**「## 終わったらやること」に置くと、読み終わったあとになって間に合いません。**
**#142（worktree が別の branch を出していると永久に飛ばされる）の報告では、着手の82秒後に切り替わっていました。**

**次の18行を足します**（見出しの行と、途中の空行6つも含めて18行です。
**足したあとに空行を1つ入れて、`## この issue を読むこと` の行と離してください**）。
**その行そのものと、その前後は1文字も変えません。**

```text
## worktree と branch は切り替えないこと

**continuo が用意した worktree と branch のまま作業してください。**
別の branch へ checkout したり、新しい branch を作ったりしないでください。
**切り替えると、次の巡回から continuo がこの issue に着手できなくなります。**

**issue やコメントで「別の branch の続きをやれ」と言われた場合も、切り替えないでください。**
その branch の内容が要るなら、先に取ってきてから、この worktree へマージしてください。

    git fetch origin <その branch>
    git merge FETCH_HEAD

**中身を読むだけなら、worktree を作らないでください。**取ってきた ref から直に読めます。

    git fetch origin <その branch>
    git show FETCH_HEAD:<見たいファイルのパス>

**worktree を足すと、消し忘れたときに登録だけが残ります。**continuo の片付けでは落ちません。
```

**`git fetch` の行を落とさないでください。**continuo は `git fetch` を1回も叩きません。

### `tracker.provider.handoff` — 複数の機械で同じカンバンを見張るときの取り決め

**何のためのものか。**この版から、同じカンバンを複数の機械（PC）で見張り、
**issue 1件につき、枠にいちばん余裕がある1台だけが担当する**「持ち回り」を使えます。
担当は issue の担当者（assignee）で持ち、期限は issue のコメントに書く `hold` で持ちます。
**カンバンに新しい欄は増えません。**

**1台だけで動かしていても、この5つの設定は常に効きます。**担当者のいない issue には
必ず入札のコメントを1件書き、締め切りを待ってから自分を担当者にします。
**待ちたくない場合は下の `bid_window_ms` を `0` にしてください。**

**書かないとどうなるか（＝既定の動き）。**

| キー | 既定値 | 何をする値か |
| --- | --- | --- |
| `bid_window_ms` | `180000`（3分） | 入札を締め切るまでの待ち時間 |
| `idle_timeout_ms` | `64800000`（18時間） | 担当者の最後の進捗報告からこれだけ経つと、担当を外して入札をやり直す長さ。**数えるのは `<!-- continuo:progress -->` が入っているコメントだけです**（v0.1.14 から） |
| `recheck_interval_ms` | `3600000`（1時間） | 走っている最中に担当を確かめ直す間隔。担当が移っていたら、その turn の終わりで止めて push しない |
| `five_hour_margin_percent` | `10`（%） | 5時間の枠のうち、continuo のために残しておきたい割合 |
| `weekly_margin_percent` | `10`（%） | 1週間の枠のうち、continuo のために残しておきたい割合 |

**`tracker.provider.handoff` セクションを丸ごと書かなくても、この5つの既定値がそのまま使われます。**
壊れません。**書いていないことに気づく手段は、`continuo doctor` の `未記入の項目` の行だけです**
（下の「足したかどうかの確かめ方」）。

**何が変わって見えるか。**

- **担当者のいない issue に、`<!-- continuo:bid -->` と `<!-- continuo:hold -->` のコメントが付くようになります。**
  1台構成でも付きます。**このコメントはエージェントへは渡りません**（issue を GitHub の画面で開いたときだけ見えます）
- **複数の機械で見張っている場合、枠の使用率がいちばん低い1台に処理が集まります**
  （判定の中身は [docs/FAQ.md](FAQ.md) の「複数の機械で見張っているのに…」を見てください）
- **担当している機械が `idle_timeout_ms`（既定18時間）のあいだ進捗報告を書かないと、ほかの機械が担当を外して入札をやり直します**
- **既に人間が担当者になっている issue は、上げた時点で着手されなくなります。**
  continuo は、その PC の `gh` の持ち主とは違うアカウントが担当者になっている issue には触りません。
  **着手させるには、GitHub の画面でその担当者を外してください。**
  逆に、その PC の `gh` の持ち主を担当者にしておくと、その PC が着手します
  （チームで持ち場を決める使い方です。[docs/FAQ.md](FAQ.md) の「チームで、issue ごとに担当の PC を決めたい」）
  （v0.1.11 からは、**着手されなくなったこと**を WARN で知らせます。それより前の版では**ログに INFO が1行出るだけ**です。
  詳しくは [docs/FAQ.md](FAQ.md) の「人間が担当者になっている issue が、いつまでも着手されない」を見てください）

### 足し方

### `tracker.automated_state_rewrite` — 自動化に動かされた Status を戻す

**何のためのものか。**GitHub Projects の**組み込みの自動化**（`Pull request linked to issue` /
`Pull request merged` など）が Status を書き換えたときに、**continuo が意図した Status へ戻す**ための対応表です。
新しく作ったカンバンでは、これらの自動化が有効な状態で作られます。

**書かないとどうなるか。**

| | 書かない場合 | 書いた場合 |
| --- | --- | --- |
| **自動化に Status を動かされたら** | **猶予（`tracker.unknown_state_grace_ms`、既定10分）を置いて worker を止める** | **本来の Status へ戻して、止めずに続ける**（戻すのは3回まで） |
| **人間が Status を動かしたら** | 猶予を置いて止める | **v0.2.1 までは、猶予を置いて止める**（書かない場合と同じ）。**v0.2.2 からは、対応表の左に書いた Status へ動かしたときは戻す**（上の「v0.2.1 から v0.2.2 へ」）。それ以外の Status へ動かしたときは、猶予を置いて止める |
| **起動** | 通ります | 通ります |

**壊れません。**書かないと、いままでどおり止まるだけです。**新しい機能が使えないだけです。**

**書き戻しは無制限ではありません。****同じ issue の同じ Status を戻せるのは3回まで**です。
continuo が戻すたびに自動化が書き直す押し合いになったら、**3回でその issue の書き戻しをやめ、
いままでどおり猶予を置いて worker を止めます**（そこから先は人間が決めます）。
そのとき issue のコメントに、押し合いが起きたことと、`Workflows` を切る手が案内されます。

### 足す場所と中身

**雛形には `automated_state_rewrite: {}` の行が既にあります。**その `{}` を書き換えます。
**塊ごと貼り替えないでください。**`tracker:` も `automated_state_rewrite:` も既にあるので、
**貼ると front matter が重複キーになり、continuo が起動しなくなります。**

**まず、いまあるかどうかを確かめてください。**

```bash
grep -n 'automated_state_rewrite' ~/continuo-work/WORKFLOW.md
```

**行が出たら、その `{}` を下の図のように書き換えます。**1行も出なければ、次で足してから書き換えてください
（v0.1.8 以前の `continuo init` が置いた `WORKFLOW.md` には、このキーがありません）。

```bash
cd ~/continuo-work && continuo doctor --missing-keys-patch WORKFLOW.md | patch -p0 WORKFLOW.md
```

**下の yaml は、どこに何が入るかの図です。**

```yaml
tracker:
  # …（ほかの設定）
  automated_state_rewrite:            # 既にある行。末尾の {} を消す
    "Todo": "In Progress"             # ← これを足す（自動化が書く Status: 戻す先の Status）
```

**Status の名前は、あなたのカンバンと `WORKFLOW.md` に合わせて置き換えてください。**上の例は
「自動化が `Todo` を書いたら、`In Progress` へ戻す」という意味です。
**`Todo` は GitHub が既定で作る選択肢です。**カンバンから消してあるなら
`! 対応表のキー` が出ますが、**起動は止まりません**（下の「足したあとの確かめ方」を見てください）。

**左に、`tracker` の他のキーで使っている Status 名を書くと起動しません。**
雛形のままなら `Ready` / `In Progress` / `Done` / `Blocked` / `In Review` の5つが該当します。
たとえば `"In Progress": "AI In Progress"` を足すと、`continuo doctor` がこう言います。

```text
✗ 設定ファイル    … 設定キー tracker.automated_state_rewrite のキー の値 In Progress が不正です:
  tracker の他のキー（active_states / terminal_states / running_state / dispatch_state /
  failure_state / status_signal_map の遷移先）に無い Status 名にすること
```

**自動化が書く Status が `tracker` の他のキーに既に書いてあるなら、対応表は要りません。**
continuo が知っている Status なので、そもそも止まらないからです。

### 左と右の決め方

| どちら | 何を書くか | 守らないとどうなるか |
| --- | --- | --- |
| **左（キー）** | **`tracker` の他のキーに名前が出てこない Status。**自動化が書く Status 名です | **continuo が起動しません** |
| **右（値）** | **`tracker.active_states` に入っている Status** | **continuo が起動しません** |

**「`tracker` の他のキー」は6つです。**`active_states` / `terminal_states` / `running_state` /
`dispatch_state` / `failure_state` / `status_signal_map` の遷移先。
**`tracker` の外（`cleanup` など）は見ません。**

**どちらも起動時に弾かれます。**貼ってから気づけるので、当てずっぽうで書いても手元は壊れません。

**左が `active_states` などに書いてあると、その行は1度も効きません。**
書き戻しを引くのは「continuo が知らない Status になったとき」だけだからです。
**右が `terminal_states` だと、戻した瞬間に片付けが走ります。**だから両方とも弾きます。

### 左に何を書けばよいか分からないとき

**書かなくて構いません。**空のままにしておいてください。

**次に自動化が Status を動かしたとき、continuo がその issue のコメントに
「この行をこう書き換えてください」と、あなたのカンバンの Status 名を当てはめた形で書きます。**
**場所を見つける `grep` も一緒に書きます。**
誰が Status を書いたか（人間か、カンバンの自動化か）は continuo が見分けるので、
**自動化だったときだけ、その案内が出ます。**
**ただし、GitHub がその記録を残さなかった回は、案内が出ません**
（[FAQ.md](FAQ.md) の「エージェントが PR を作った直後に止まる（automated_state_rewrite）」に、出なかったときの書き方があります）。

```bash
gh issue view https://github.com/<owner>/<repo>/issues/42 --comments
```

### 足したあとの確かめ方

**`continuo doctor` の `対応表のキー` の行を読みます。****記号だけで判断しないでください。**
**1行も足していなくても `✓` が出ます**（照合するものが無いためです）。
**足せたかどうかは、記号のうしろの文で見分けます。**

```bash
cd ~/continuo-work && continuo doctor; echo "exit=$?"
```

| 記号のうしろに出る文 | どう読むか |
| --- | --- |
| `tracker.automated_state_rewrite は空です（書き戻しを行わない設定です）` | **足せていません。**別のファイルを編集したか、`tracker:` の下に置けていません |
| `tracker.automated_state_rewrite のキーはすべてカンバンの Status の選択肢にあります（1件）` | **足せています。**括弧の中の件数が、書いた行数と合っているかも見てください |
| `tracker.automated_state_rewrite のキーに、カンバンの Status の選択肢に無いものがあります（1件）` | 足せてはいますが、**綴りがカンバンと違うか、その Status をカンバンで使わなくなっています** |

**上の2つは `✓`、いちばん下は `!` です。**
**`!` のままでも continuo は起動します**（終了コードも 0 です）。
直し方は [FAQ.md](FAQ.md) の「continuo doctor が赤くなるとき」にあります。

**`✗ 設定ファイル` が出たときは、対応表そのものが弾かれています。**
左右の決め方をもう一度読んでください。**この場合 continuo は起動しません。**

**書き換えたら continuo を再起動してください。**動いている最中は設定を読み直しません。

### 足したくない場合

**カンバンの側で自動化そのものを止める手もあります。**
カンバンの `Workflows` の設定から、動いてほしくない自動化を無効にしてください。
**そうすれば Status は横取りされないので、対応表も要りません。**

**どちらか一方でかまいません。**両方やっても構いませんが、片方で足ります。

**ただし、そのカンバンを人間も使っているなら、対応表のほうを勧めます。**
`Workflows` を切ると、continuo と関係なくカンバンを見ている人の使い勝手も変わります。
**continuo を入れたことが、人間の設定を変える理由になってはなりません。**
